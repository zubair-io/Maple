# M4 · Color & Output Qualification — design spec

Milestone 16 · Color & Output Qualification. Epic: #2446. Sub-issues: #2439 (C0–C5 suite), #2440 (camera/lens support tiers), #2441 (rendering modes), plus the standing color-quality backlog this milestone also owns: #2333, #1710, #1625, #1626, #379/#825/#828, #1338/#3190/#3191, and — parked in the Icebox until this milestone's SDR bar is met — #1697 (soft proof) and #1702 (HDR).

This document is the thing #2439/#2440/#2441 cite as `docs/strategy/milestones/m4-color-output.md` and did not previously exist. Unlike the rest of `docs/`, which derives from code as it stands, this is a forward-looking design spec — see the note in `docs/README.md`.

## 1. Outcome

Today "does Maple render this camera correctly" has one answer: a ΔE number from `src/scripts/test_color_pipeline.sh` against an Adobe Camera Raw render, computed for 20 fixtures, checked by a human reading a table. There is no per-camera qualification status, no lens axis, no rendering-intent contract a user can reason about, and no gate at all for two of the four platforms this pipeline ships on.

"Qualified" after this milestone means a camera body (and, on a separate axis, a lens) has passed a fixed, versioned set of evidence gates — C0 through C5, defined below — and that evidence is recorded immutably and consumed by a generated support-tier registry. A camera cannot claim a tier it hasn't measured; a release cannot promote a tier without the C-suite passing for it. That registry is what the product bar cashes out to: "color quality a working photographer will trust" becomes, concretely, "every qualified camera passes fixed sensor-colorimetry and reconstruction thresholds, on every platform we ship, with the evidence checked into git." The performance bar (16 ms slider tick) is unaffected by this milestone — C5's platform-parity suite proves the fast and slow paths agree pixel-for-pixel, not that either is fast.

The milestone closes when: every launch-priority camera has an evidence-backed tier; qualified cameras pass fixed C1/C3 thresholds; Neutral rendering is content-stable and isolated from the creative-fit path; every released surface (Apple, Web, Windows) passes the same platform-parity suite instead of only Apple having one; output management (profile conversion, gamut warning) has fixed vectors even though soft-proof/HDR themselves stay iceboxed; and the methodology is public and matches the code. Those are the epic's own exit criteria, restated per-suite in §3.

## 2. Current state, with paths

### The one harness that exists

`src/scripts/test_color_pipeline.sh` renders every case in `test-fixtures/references/manifest.json` through `maple-cli batch`, diffs each candidate against an ACR-rendered PNG with [`compare_images.py`](../../../src/scripts/compare_images.py) (CIEDE2000 mean/p95/max + per-channel bias, optional `--zones`/`--hue-bins`), and checks the result against `test-fixtures/budgets.json` — a `{fixture: {case: {mean, p95, max, bias}}}` table, 20 fixtures × ~44 cases. Budgets are a **one-way ratchet**: [`tools/check_budget_ratchet.py`](../../../tools/check_budget_ratchet.py) fails a raised ceiling and fails a removed cell, and a legitimate re-baseline covers each raised cell with a `RE-BASELINE:` marker in the commit message (see `docs/testing.md` § "The one-way ratchet"). This is the whole of `docs/testing.md`'s "no eyeballing" rule made concrete, and it is the mechanism §3 reuses rather than replaces.

Alongside it, four closed-form gates never touch ACR and never skip: `test_synthetic_grey.sh`, `test_synthetic_color_chart.sh`, `test_grey_adjustments.sh` (closed-form predictors per scene-linear slider), and `test_grey_dcp.sh` (DCP code-path coverage — ColorMatrix1/2, ForwardMatrix1/2, PTC). `test_banding.sh` gates second-difference spikes in the AgX and display-encode compressors. These, plus `raw-core/tests/color_chart_invariants.rs`, are the repo's only unconditional color regression net — the ACR harness is strictly better signal but needs fixtures that CI doesn't have.

### Why CI is green while the harness is red locally

`test-fixtures/raws/` and `test-fixtures/references/` are gitignored (multi-GB RAWs, operator-rendered PNGs). `raw-pipeline.yml`'s `color-pipeline` job runs the same script CI-side, but the script's own preflight skip-passes when the manifest or budgets file is absent — and on a stock GitHub runner the RAWs never exist, so the job reports green having compared zero images. This is documented behavior (`docs/testing.md` § "Fixtures and the skip-pass convention"), not a bug, but it means **the only place the color gate has ever actually run is an operator's own machine**, and "CI is green" carries none of the weight the badge implies for this specific gate.

Run locally today, `test_color_pipeline.sh` is red on two fixtures, tracked in [`test-fixtures/BUDGETS_DRIFT.md`](../../../test-fixtures/BUDGETS_DRIFT.md) as fourteen deliberately-frozen cells:

- **`test_0013` (#2774, milestone 7, open).** iPhone ProRAW's `ProfileGainTableMap` parser was fixed in `698483457` to actually apply the gain (it previously silently parsed to `None`); applying it per spec moved the render brighter and roughly doubled ΔE against April's ACR references, on `baseline`, `baseline_auto`, and all ten full-res `sharpen_*`/`nr_*` cases. Root cause is unresolved — either Maple's `profile_gain_table_map.rs` application is wrong, or the references need re-rendering with the corrected pipeline. Not yet attributed to either.
- **`test_0018` tint (#2333, milestone 7, open).** `tint_max`/`tint_min` breach 38–46% against ceilings #1893 ratcheted down and validated at zero breaches. Something in the post-#1893 color work moved tint with nothing catching it, because CI has no fixtures to catch it with. Needs a bisect.

Both block honest C1/C2 measurement on those fixtures. Neither is this milestone's to fix directly — they're milestone-7 tickets — but §5 treats them as a hard prerequisite: a qualification suite cannot report a status for evidence it knows is compromised.

### The fixture-provenance problem

Every reference PNG in `test-fixtures/references/` is operator-produced: someone with Adobe Camera Raw on their own machine renders a RAW + a specific slider XMP and commits the PNG. No agent can produce one. This has stalled real work — #368 (parametric tone-curve calibration) has had its five sidecars authored and committed since June with zero ACR renders to calibrate against; #1710's Phase 3 (per-slider calibration against 33 ACR preset renders) is iceboxed partly for this reason; #1741 tracks a still-outstanding 5DS R fixture (`test_0021`) that needs the operator. §4 treats "does ACR stay the ground truth" as an open decision precisely because this bottleneck is structural, not incidental — a qualification suite that gates releases cannot depend on an unbounded operator queue.

One correction to the premise this milestone might otherwise inherit: #1710's own audit trail (see its comments) already resolved the "was test_0018 ever re-rendered correctly" question — it was, the four previously-flagged ceilings (`contrast_min`, `temperature_max`, `wb_shade`, `whites_max`) are stale text, not a live blocker, and #2317 exists to ratchet them (open, unblocked, needs only #2774/#2333's harness to be trustworthy first, per its own sequencing note).

### `AcrMatch` — already gone, not "still wired"

The premise that `Profile::AcrMatch` is still wired into raw-core/Swift/TS despite #2312's closure does not hold against current `main`. `render_enums.rs` defines `Profile` as exactly two variants, `Auto` and `Neutral`; PR #2324 removed the third. What remains in raw-core, raw-gpu, Apple, and web is deliberate: a comment at each retired call site explaining why, plus an explicit `"AcrMatch" → Profile::Auto` migration arm in every sidecar parser (`raw-core/src/xmp/fields.rs`, `XMPSerialization+ParseAttrs.swift`, the web parser's fallback) so a sidecar written by an old CLI build (`maple-cli --profile acr-match`) still loads. That migration code is correct and should stay; there is no removal work left here. §4 treats "should the new Camera Match mode reuse AcrMatch's model" as the live open question — it is not the same as "AcrMatch is still live."

### The view transform, as it actually runs today

`pipeline/render/mod.rs` runs one display tail regardless of `Profile`: AgX (`view/agx.rs`, a baked 512-entry sigmoid LUT) → `color_grade` → `film_look` (optional baked `.mlut`) → `grain` → `rec2020_to_display` (primaries + Oklab soft gamut compress) → `srgb_gamma_encode` →, only when `Profile::Auto`, an embedded-JPEG-fit curve plus a residual 3D LUT plus a post-fit Oklab gamut guard → quantize. `Look` (formerly `DisplayLookCurve`, #371) was retired to a no-op in #443 and is kept only so pre-#443 sidecars round-trip — it has zero effect on rendered pixels today (`tests::look_field_is_no_op`). Full stage-by-stage detail is in `docs/pipeline.md` § "The view transform and output"; this spec does not restate it beyond what §3.3 needs.

Two properties matter for #2441: `Profile::Neutral` runs the same `auto_exposure` scene-anchoring stage as `Auto` — a deterministic function of the RAW's own decoded pixels (geometric-mean midtone → 0.18 mid-gray), not of any external oracle — so its brightness legitimately varies by scene even though its _algorithm_ is fixed and content-independent in the reproducibility sense. `Profile::Auto` additionally fits a per-image curve against the camera's own embedded JPEG preview and caches the result keyed on `(raw identity, mtime, quality)` (`view/auto_profile/`). Today `Auto` is the _default_ profile a user gets with no visible indication they are looking at a per-image creative fit rather than a stable transform — this conflation is exactly what #2441 exists to unwind. §3.3 works through the mapping in detail.

### Camera/lens support has no product-facing tier today

The closest existing thing to #2440's tier registry is `ProfileSource`, an internal enum `profile_for_with_source` (`color/dcp.rs`) reports per render: `EmbeddedFull` (DNG ships CM+FM+HSM), `BundleConfident` (matched in the bundled ~1,406-body table), `EmbeddedCmOnly`, `RawlerFallback` (no calibration data at all — a generic D65→Rec.2020 matrix, logged once per model). This is a _resolution_ tier, computed silently at render time; it has no user-facing surface, no evidence trail, and no lens axis. `test-fixtures/raws/` holds 20 physical fixtures against ~1,406 bundled profiles, so the overwhelming majority of "supported" cameras have never been measured against anything — only decoded and matrix-matched. Lens support is entirely DNG-embedded `OpcodeList3` correction (`types/adjustment/lens_correction.rs`); there is no Maple-maintained lens profile database and no lens-specific test surface at all, which is consistent with #2440 treating lens as "a separate axis" rather than assuming it inherits camera tiering.

`src/raw-pipeline/raw-core/src/color/profiles/COVERAGE.md` is the nearest thing to a registry today — a hand-maintained table of the 20 test fixtures' bundle-hit status. It is prose, not data, and nothing consumes it programmatically.

## 3. Per sub-issue

### 3.1 · #2439 — the C0–C5 qualification suite

**Scope.** Replace "one blended ΔE score" with six distinct suites, each with its own inputs, its own pass/fail semantics, and its own place in CI. This is substantially a _reclassification_ of gates that already exist plus targeted new coverage for the two suites (C4, C5) that barely exist.

**Design — mapping the six letters onto real scripts:**

| Suite                                                                                    | Existing coverage                                                                                                                                                                                                     | Gap                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C0** — ramps, primaries, neutral axes, negatives, monotonicity, transform domains      | `test_synthetic_grey.sh`, `test_banding.sh`, `raw-core/tests/color_chart_invariants.rs` (`rec2020_chart_patch_means_match_targets_within_gain`, `camera_chart_round_trips_to_rec2020_targets`)                        | None structural — these already never skip and assert exactly this class of property. Work is packaging: tag them as the `C0` job in CI, one name, one required check.                                                                                                                                                                                                                                                                                                            |
| **C1** — measured targets under known illuminants                                        | `test_grey_dcp.sh`, `test_synthetic_color_chart.sh`, the DCP invariant tests                                                                                                                                          | The "measured target" today is a synthetic chart Maple itself generates (`raw-core/src/test_support/synth_chart.rs`) — internally consistent but not an independently-measured colorimetric truth. §4 asks whether that's acceptable as C1's definition of "known."                                                                                                                                                                                                               |
| **C2** — controlled scene rendering, predeclared blind preference / non-inferiority      | `test_color_pipeline.sh` (the ACR ΔE harness)                                                                                                                                                                         | Real gap: the harness measures ΔE-vs-ACR, not preference or non-inferiority. Nothing today runs a predeclared human-evaluation protocol. §3.1 sequencing below treats the ΔE gate as C2's automated floor and treats blind evaluation as a separate, lower-frequency addition — not a replacement, since ΔE-vs-ACR is cheap, already exists at 20-fixture scale, and blind studies do not run per-commit.                                                                         |
| **C3** — detail, false color, zippering, halos, highlight reconstruction, noise spectrum | `test_halo_detection.sh` and `test_hue_stability.sh` (both diagnostic-only, not CI gates today), the `sharpen_*`/`nr_*` cases inside `test_color_pipeline.sh`'s manifest                                              | Real gap: promote the two diagnostics to gates with committed ceilings (they already print the right numbers, they just don't fail), and there is no false-color or zippering metric at all — net-new.                                                                                                                                                                                                                                                                            |
| **C4** — output profiles, proof simulation, intents, gamut warnings, SDR, HDR            | `--target-primaries {srgb,p3}` end-to-end via #1339 (closed) plus `raw-core/src/icc.rs` tagging                                                                                                                       | Soft-proof, gamut-warning-as-overlay, and HDR/EDR output (#1697, #1702) don't exist — they're Icebox, deliberately, per the epic's own non-goal "No HDR release before SDR output correctness." C4 in this milestone is scoped to what's real: primaries conversion vectors and ICC-tag correctness. Soft-proof/HDR stay out of scope until a future milestone de-ices #1697/#1702.                                                                                               |
| **C5** — Rust reference, Metal, real browser GPU backends, preview, export               | `cargo test -p raw-gpu` / `-p raw-wasm` against **lavapipe**, a software Vulkan target (`raw-pipeline.yml`'s `raw-gpu` job); Apple's `SliderMatrixUITests`/`MapleUITests` (local-only, need an unlocked macOS screen) | Real gap, and the largest one: lavapipe proves raw-core↔WGSL agreement but says nothing about the real Metal backend or a real browser's WebGPU implementation (`docs/testing.md` says this explicitly). There is **no** web or Windows equivalent to Apple's ACR-parity UI tests at all — confirmed by grep, zero hits for any CIEDE2000/ACR-parity harness under `src/web` or `src/windows`. Two of four shipping platforms have never been checked against a reference render. |

**Acceptance, restated per the ticket's own criteria against the mapping above:**

- Fixed release ceilings (budgets.json-style, one-way ratchet) stay separate from regression ratchets that track drift without gating a release — C0/C1/C3 are release ceilings; C2's blind-evaluation layer (once it exists) is a non-blocking regression signal, since preference results are noisier than ΔE and shouldn't gate merges the way ΔE does.
- Fitting and scoring corpora must be disjoint. **Not true today**: the same 20 ACR fixtures are both the thing operators fit calibration work against (#1710 Phase 2/3, #825's HSM tuning) and the thing the release gate scores. Closing this needs either a second, held-out fixture set (more operator renders — expensive) or a documented exception that any fixture used for _fitting_ a specific stage is excluded from that stage's _scoring_ row. Recommend the latter as the pragmatic default; flagged in §4.
- Every result records immutable fixture + pipeline metadata — already true in spirit (git SHAs, `budgets.json` version) but not machine-enforced; add a `pipeline_output_version` and fixture content hash to the harness's JSON output so a qualification record can't silently drift.
- Required jobs execute exact non-zero counts — the skip-pass convention (§2) means a CI run with no fixtures currently reports success on zero comparisons. C1–C5 jobs that claim to be "required" must assert `cases_compared > 0` when they claim to have run, the same fail-closed rule `test_color_pipeline.sh` already applies once both the manifest and budgets exist (`docs/testing.md`).
- Default vs. extreme-control cases report separately — map onto the existing `--zones`/`--hue-bins` breakdown in `compare_images.py`, surfaced as a separate summary row rather than folded into the grand mean.
- Public reports state unknowns, no un-protocoled external ranking — a documentation and process requirement, not code; the public methodology doc (epic exit criterion) must say explicitly which suites have known gaps (C4 HDR, C5 non-lavapipe backends) rather than imply full coverage.

**Sequencing.** C0/C1 first (pure reclassification + CI wiring, no new engineering, unblocks the registry in #2440). C2 next (wrap the existing ACR harness as the C2 release gate; defer blind-evaluation as a stretch item). C3 promotes two diagnostics to gates and adds false-color/zippering metrics — moderate new work. C4 is scoped down to what's real (small). C5 is the largest lift — a Metal-backend CI gate and a first-ever web/Windows ACR-parity harness — and should land last, after C0–C3 give it something meaningful to be parity-_of_.

**Non-goals.** No blind human-evaluation infrastructure in this pass (design only — see §4). No soft-proof or HDR output (#1697/#1702 stay Icebox). No attempt to fix the two red fixtures (#2774, #2333) as part of this ticket — they're prerequisites, tracked separately in milestone 7.

### 3.2 · #2440 — camera and lens support tiers

**Scope.** A generated, evidence-linked registry exposing `Qualified | Profiled | Matrix-only | Decode-only | Unsupported` per camera body, with lens support as an independent axis, consumed by every surface that currently treats "rawler can decode it" as equivalent to "fully supported."

**Design.** The tiers map cleanly onto data that already exists, once §3.1's C-suites are wired to produce pass/fail evidence per body:

| Tier            | Definition                                                                                                                                          | Backed by                                                                         |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **Qualified**   | Has a physical fixture; passes C1 (measured colorimetry) and C3 (reconstruction) thresholds                                                         | `test-fixtures/raws/` fixture + green C1/C3 rows in that fixture's harness output |
| **Profiled**    | `ProfileSource::EmbeddedFull` or `BundleConfident` — real calibration data, no fixture to prove it against                                          | `color/profile_loader/` resolution + `profiles.bin` coverage                      |
| **Matrix-only** | `ProfileSource::EmbeddedCmOnly` — a DNG-embedded matrix, no HSM, no bundle hit                                                                      | Same resolution path                                                              |
| **Decode-only** | Decodes via rawler but resolves to `ProfileSource::RawlerFallback` — an identity-ish matrix, "visibly imperfect but bounded" per `docs/pipeline.md` | Same                                                                              |
| **Unsupported** | rawler cannot decode the format at all                                                                                                              | Decode failure, not a color-pipeline concept                                      |

This is a strict widening of the existing internal `ProfileSource` enum plus a fixture-evidence layer on top — no new resolution logic, just a generator that reads harness output and `profiles.bin`'s coverage index and emits a versioned registry (JSON, checked into git like `budgets.json`, or generated at build time like the `codegen` crate's outputs — §4 asks which). `src/raw-pipeline/raw-core/src/color/profiles/COVERAGE.md` — currently hand-maintained prose for 20 fixtures — is superseded by this registry's data; keep the doc only as the human-readable rendering of the same generated table, the same relationship `docs/server-api.md` has to the route sources.

**Acceptance, per the ticket:**

- Each body/lens entry links to immutable evidence (harness run SHA + fixture hash) and the profile version (`profiles.bin`'s own version stamp) it was measured against.
- The registry is _generated_, never hand-edited, from qualification outputs — same discipline as `tools/codegen.sh`'s drift check (`.github/workflows/cross.yml`'s `codegen-drift` job) applied to this artifact too.
- Unsupported/limited paths produce a deterministic user-facing explanation — today a `RawlerFallback` body just renders with a logged warning and no UI signal at all; this ticket is what makes "why does this look off" answerable in-product.
- Profile fallback order (`EmbeddedFull` → `BundleConfident` → `EmbeddedCmOnly` → `RawlerFallback`) is versioned and testable — it already is, as Rust unit tests on `profile_for_with_source`; extend those tests to assert the tier registry agrees with the resolver rather than drifting from it.
- A release cannot promote a tier without passing its fixed requirements — wire the tier-registry generator into the same CI path C0–C3 report to, so a tier bump requires green evidence, not a manual edit.
- Firmware and metadata-indistinguishable cases need explicit policy — e.g. two firmware revisions of the same body reporting an identical `UniqueCameraModel` but different real-world calibration. No such case is known to exist in the current 20-fixture set; document the policy (most-conservative-tier-wins, or explicit firmware-range pinning) as a decision rather than leaving it implicit, since the bundle's `UniqueCameraModel`-keyed lookup (`profile_loader/`) has no version dimension today.

**Sequencing.** Depends on §3.1's C1/C3 producing structured pass/fail output per fixture (not just a printed table) — build the registry generator against that output once it exists, not against today's free-text harness log.

**Non-goals.** No attempt to acquire new fixtures for the ~1,386 bundled-but-unmeasured bodies — the registry reports `Profiled`, not `Qualified`, for all of them honestly, rather than pretending fixture coverage exists. No lens profile database beyond what DNG `OpcodeList3` already carries — lens qualification in this milestone is "does the embedded correction apply correctly," not "does Maple maintain third-party lens profiles."

### 3.3 · #2441 — Neutral / Camera Match / Auto Tone / Auto Look modes

**Scope.** Replace the current two-value `Profile { Auto, Neutral }` — where `Auto` silently conflates "the default users get" with "a per-image creative fit" — with four explicit, independently versioned states matching the ticket's four named modes.

**Design — mapping each mode onto the pipeline that exists:**

- **Maple Neutral** = today's `Profile::Neutral`, unchanged: AgX + the fixed display tail, no embedded-JPEG dependency, no residual LUT. Already satisfies "camera characterization plus stable published view transform" as-is. The one thing to fix, not add: its stability claim needs a documented caveat that `auto_exposure`'s scene-anchoring gain (§2) is a deterministic function of the RAW's own pixels, so brightness legitimately varies by scene — "stable" means reproducible and free of external-preview dependence, not "flat regardless of content." Recommend the acceptance criterion text be tightened to say exactly that, so a future contributor doesn't read "stable" as "auto_exposure must go."
- **Camera Match** = new. Not a resurrection of the retired `AcrMatch` (§2) — that model over-exposed real bodies and was correctly deleted. This mode needs its own implementation decision (§4); the honest scope for this milestone is the _contract_ (a named, versioned `Profile::CameraMatch` enum value, XMP field, cache key, and UI string) with the underlying render model either deferred to a follow-up ticket or, if product wants something shippable now, backed by the vendor JPEG-preview reference the way `Profile::Auto`'s fitter already works (`view/auto_profile/`) but _without_ the residual-LUT creative step — i.e., curve-fit only, explicitly labeled and capped, not marketed as pixel-identical to any specific vendor renderer.
- **Auto Tone** = the existing `stages/auto_adjustments.rs` one-shot recommendation (already exposed via FFI as `maple_compute_auto_adjustments`), not `Profile::Auto`. It already matches the ticket's description exactly — "visible global-control changes with one committed action" — because it's a probe-develop that returns eight slider values the caller writes into the model once, same as any manual slider edit, rather than a continuous per-render transform. The work here is UI/wiring (surface it as a distinct, discoverable action) not pipeline math.
- **Auto Look — Experimental** = today's `Profile::Auto` render-time behavior: the embedded-JPEG curve fit plus residual 3D LUT, applied automatically and invisibly on every render. This is the mode that most needs a behavior change, not just a rename: it must become opt-in with visible provenance (the ticket's own words) rather than the silent default. Whether it _stays_ the default while merely being labeled, or the default flips to Neutral, is a product call — §4.

**Acceptance, per the ticket:**

- Distinct version identifiers, cache keys, sidecar fields, UI descriptions per mode — mechanical once the four-value enum lands; follows the same `Profile`-field pattern already in `xmp/fields.rs`.
- Neutral output stable across image content — see the clarified reading above.
- Auto Tone changes only visible controls, one Undo entry — already true of `auto_adjustments`'s contract; verify the UI wiring doesn't fan it out into per-slider undo entries.
- Experimental creative state removable, cannot contaminate neutral qualification — critical for §3.1's C1/C2/C3: those suites must run exclusively against Neutral (and, once it exists, Camera Match), never against Auto Look, or a passing qualification result would be measuring a per-image fit rather than the stable transform. `test_color_pipeline.sh` already pins `--profile neutral` for its fidelity pass and `--profile auto` only for the separate `baseline_auto` row (§2) — this is the right existing pattern to keep, now with Auto Look renamed and clearly out of the qualification path by construction.
- Existing sidecars migrate deterministically, no silent intent change — the `Auto → Auto Look`, `Neutral → Neutral` rename needs the same explicit migration-arm treatment the retired `AcrMatch → Auto` mapping already demonstrates (§2's confirmed-correct precedent); no new design needed, just the same pattern applied once more.
- Preview and export resolve the same mode/version — already structurally true (`ChainOptions`/`AdjustmentModel` are shared inputs to both paths); regression-test it explicitly once the fourth value exists.

**Sequencing.** Land the four-value enum + migration arms first (mechanical, low risk, unblocks nothing else but itself). Auto Tone's UI surfacing can proceed in parallel — it touches no pipeline math. Auto Look's default-vs-opt-in behavior change is the one item that should wait on a product decision (§4) before shipping, since it changes what every existing user sees by default. Camera Match's underlying model is the largest open scope in this whole milestone and should be sequenced after Neutral/Auto Tone/Auto Look are settled, since it's the one mode with no existing implementation to lean on.

**Non-goals.** No attempt to make Camera Match pixel-identical to any named third-party renderer as a committed acceptance bar — per the epic's own non-goal, "No best-color claim from one reference renderer." No change to the underlying AgX math for any mode.

## 4. Open decisions

**Does ACR stay the reference baseline, or does a synthetic-chart truth replace it for C1?**
Recommend: keep both, split by role. C0/C1 use Maple's own synthetic chart (`synth_chart.rs`) as a closed-form, unlimited-supply truth for algebraic and colorimetric invariants — it never needs an operator and never skips. C2 keeps ACR as the practical, sunk-cost, already-built competitive-fidelity gate; #1710's Phase 3 (fully replacing ACR-as-truth with per-slider chart calibration) stays iceboxed, since its own investigation found the chart's clipped-primaries problem (9 of 54 ColorChecker channels hard-clip in ACR's own render) makes it a worse ground truth for saturated color than ACR itself in its current form. Revisit only if product decides the ACR-render operator dependency (§2) is untenable at scale.

**Does the new Camera Match mode reuse anything from the retired AcrMatch model, or start from zero?**
Recommend: start from zero, reusing only the retained `view/acr_fit/` solver infrastructure (deliberately kept by #2312 for exactly this kind of reuse) rather than the deleted baked LUT. AcrMatch's failure was chart-fitted coefficients baked once and applied uniformly; a per-image JPEG-fit approach (reusing `Profile::Auto`'s existing machinery, minus the residual LUT) avoids that specific failure mode by construction, at the cost of Camera Match no longer being a single fixed transform. This is a real product trade-off, not an engineering detail — flag for explicit sign-off before Camera Match's implementation ticket is scoped.

**Does Auto Look stay the default profile, or does the default flip to Neutral once it's correctly labeled?**
Recommend: flip the default to Neutral. The ticket's own acceptance criteria ("Experimental creative state ... cannot contaminate neutral qualification") reads awkwardly if the thing most users see by default is the experimental one. This is a user-visible behavior change for every existing install and needs the `PIPELINE_OUTPUT_VERSION` bump discipline (`docs/pipeline.md` § "Pipeline output version") plus explicit product sign-off — flagging rather than deciding unilaterally here.

**Is the C0–C5 tier registry a committed JSON artifact (like `budgets.json`) or a `codegen`-style generated-and-checked file?**
Recommend: generated-and-checked, following the existing `codegen-drift` CI pattern (`.github/workflows/cross.yml`) rather than the manual `budgets.json` update flow — the registry's whole value proposition is that it can't silently drift from the evidence, and codegen's drift check is the mechanism the repo already trusts for exactly that property.

**Does C2's "fitting corpus" vs "scoring corpus" disjointness (a stated #2439 acceptance criterion) require new operator-rendered fixtures, or a documented per-stage exclusion rule against the existing 20?**
Recommend the exclusion-rule approach initially (cheap, no new operator dependency) with a note that it's a known-imperfect stopgap; revisit if a specific stage's fit-then-score overlap turns out to matter in practice (i.e., a stage whose fit conspicuously improves its own scoring fixture more than held-out ones).

**Does the predeclared blind preference / non-inferiority protocol C2 asks for get built in this milestone, or deferred?**
Recommend: design-only in this milestone (a written protocol: sample size, predeclared corpus, non-inferiority margin), with actual execution as a separate, non-blocking ticket. It's explicitly not a per-commit gate (§3.1), and the epic's own non-goal — "no external product ranking without a shared predeclared corpus and protocol" — means getting the protocol right matters more than getting it running fast.
