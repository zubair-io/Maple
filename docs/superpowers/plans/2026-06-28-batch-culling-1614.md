# Batch Culling Implementation Plan

**Goal:** Add rating / flag / color-label support to the batch metadata route and panel so photographers can cull multiple images at once, with the culling state written to each XMP sidecar and projected to the DB the same way individual culling edits are.

**Architecture:** Culling (rating 0–5, flag pick/reject/unflagged, colorLabel red/orange/yellow/green/blue) already flows through the single-image XMP sidecar layer. The batch metadata route (`POST /api/xmp/batch`) handles the sidecar merge path but `XmpMetadataInput` only accepts IPTC/EXIF fields; the serializer has no awareness of culling attributes. This plan adds culling fields to the serializer, the input type, the batch route's Elysia schema, the DB reconciliation, the snapshots API, the web panel types/component, and the Apple M4 batch VM — following existing patterns in each layer with no new abstractions.

**Tech Stack:** TypeScript (API/Web), Angular 21 signals+standalone, Swift/SwiftUI, Bun test runner, Vitest/TestBed (web specs).

## Design constraints

This change is non-destructive: originals are never modified and all edits go to `.xmp` sidecars.

The XMP tags follow the existing web serializer encoding exactly (`src/web/projects/maple-common/src/lib/xmp/xmp-serializer.service.ts:113-122`): `xmp:Rating` is an integer 0–5, `papp:Flag` is pick/reject/unflagged, and `papp:ColorLabel` is a color name or empty string. The DB top-level fields match `ImageDoc` (`src/api/src/db/schema.ts:296-301`): `rating: number`, `flag: -1|0|1`, `color_label: string`, where flag encodes pick→1, reject→-1, unflagged→0 (the `LibraryIndex.flag` string→int convention) and color_label stores the raw sidecar string ('red', 'orange', …) or '' for none.

Only touched fields are written; untouched fields already present in the sidecar survive a partial edit (the batch-merge invariant). The scope is minimal (YAGNI): no generic "culling stage" abstraction — the smallest change per layer.

The top-level `ImageDoc.rating/flag/color_label` fields are the search/sort surface; `metadata_override` is the IPTC/EXIF override bag. Culling belongs on the top level (already there) rather than inside `metadata_override` — but the sidecar-metadata-index stage currently has no mechanism to write top-level fields. The cleanest approach matching the existing arch: extend `MetadataOverride` to carry culling so `xmpMetadataToOverridePatch` can populate it, then in the stage handler, after building the `override`, additionally write the culling fields directly to the top-level doc via a targeted `updateOne`.
