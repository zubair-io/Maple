## What was verified and holds

- Access tokens are HS256 with the algorithm pinned, so `alg` confusion is not possible. Step-up tokens carry `purpose: step_up` and no role, so neither token type can be used as the other.
- Refresh rotation is one transaction. A reused token revokes the whole family, a replay inside the 60 second grace window re-mints only while a live sibling exists, and logout cannot be raced into leaving a live token in a revoked family.
- Native PKCE codes and LAN handoff codes are stored as hashes, are single use, expire in 60 seconds, and a wrong verifier does not burn the code. Issuing either needs a live refresh token or a fresh passkey step-up, so a leaked 15 minute access token cannot mint a 90 day session.
- The first-owner claim is a single sentinel insert, invited registrations cannot win ownership, and invite codes are single use with an atomic spend.
- Credential add and remove, invite create and rescind, device-session revoke and service key create and revoke all require step-up. Role and user roster routes are owner-only with a last-owner guard.
- The events WebSocket checks the Origin, authenticates with a first-frame token (not the URL) and closes at token expiry.
- Slug-addressed routes (`resolveAddress`) reject absolute paths, backslashes and `.`/`..` segments and then compare the real path to the real root, so symlinks cannot escape. Static UI serving rejects traversal.
- Migrations run one per transaction with their sentinel row, under an exclusive lock, with ordering enforced; a failed migration leaves nothing behind and stops the boot.
- Worker pause, resume, retry-dead and config routes validate the worker name against a static set.
