# Caching

Maple caches four kinds of thing: **thumbnails** (small grid images), **previews** (a 1280-px developed still), **decoded/intermediate pixel state** (in memory, per session), and **API responses** (folder listings, counts, geocodes). The first two are written into a `.maple/` folder that sits next to the photos, so they travel with the library and are shared by the Mac app, the Windows app, the web client, and the Self-Hosted server. Everything in a cache is derived and disposable — an original file is never a cache entry, and losing the whole cache costs time, never data.

Two rules explain most of the design. First, **thumb and preview cache filenames are derived from the photo's own filename**, not its content or its database id — so the cache resolves with no database lookup and survives being copied to another machine, but nothing survives a rename or a move (the fix is to regenerate at the new path, never to relocate cache files). Second, **shared thumbnails and previews are never versioned**: their names, HTTP identities and server stages carry no pipeline version, so a pipeline change never regenerates, re-syncs or rejects one. They are refreshed only when the original or its sidecar changes (see [No pipeline version](#no-pipeline-version)).

The one cache that tracks a photo's _edits_ is Apple's rendered-preview cache, and the adjustment-version proxy it uses is the modification time of the [XMP sidecar](xmp-canonical-format.md) — see [The adjustment-version proxy](#the-adjustment-version-proxy).

## The shared `.maple/` folder

Every layer agrees on this layout, sitting inside the folder that holds the photos:

| Path                                  | Contents                                                       | Written by                                               |
| ------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------- |
| `.maple/thumbs/<filename.ext>.avif`   | 512-px AVIF grid thumbnail                                     | Apple, Android, Windows, Web, API indexer, pano stitcher |
| `.maple/previews/<filename.ext>.avif` | 1280-px AVIF display preview                                   | Apple, Android, Web, API indexer, pano stitcher          |
| `.maple/index.json`                   | Per-folder file list + culling state (Apple cold-open)         | Apple only                                               |
| `.maple/id-cache-<writer>.json`       | `path → maple_id` rows with size/mtime validation              | Apple (`-apple`), Web (`-web`)                           |
| `.maple/trash/…`                      | Trashed items plus `<basename>.trashed-YYYY-MM-DD` marker dirs | Apple (local + SMB)                                      |

Both tiers keep the original filename, including its extension, and append `.avif`: `IMG_1234.CR2` has the thumbnail `.maple/thumbs/IMG_1234.CR2.avif` and the preview `.maple/previews/IMG_1234.CR2.avif`. Neither carries a hash or a pipeline version (#4793). Assets with no source filename (Apple's sourceless, opaque-id keys) use `<key>.avif`. Path composition lives in `src/apple/Packages/MapleCore/Sources/MapleCore/FileProvider/MapleSidecarPaths.swift` and `src/api/src/fs/xmp.ts` (`resolveThumbPath` / `cachePathFor` / `cachePathForAsset`).

### Legacy names and rename-on-miss

Two retired schemes are still on disk in existing libraries: thumbnails named `<sha256_prefix16(filename)>.avif` or `<sha256_prefix16(filename)>.v<N>.avif`, and previews (plus Web's fallback artifacts, descriptors and source identities) named `<filename.ext>.v<N>.<kind>`. `sha256_prefix16` is the first 16 lowercase hex characters of `SHA-256` over the basename with its extension. It survives only to find these files.

The only remaining legacy handling is in readers, and it is a rename, never a regeneration. On a miss a reader tries exactly one frozen legacy name and renames it into place: `<filename.ext>.v25.avif` for a preview, `<sha256_prefix16(filename)>.v25.avif` for a thumbnail. Every install that wrote versioned names did so at version 25, so this costs one extra stat, on a miss only. On the server this lives in `src/api/src/fs/legacy-derivative.ts` and runs inside the shared freshness check, so routes, stages and the derivative audit all adopt the old file rather than regenerate it.

The server's cache sweep (`src/api/src/workers/cache-gc.ts`) no longer migrates anything (#4928): the production library was already renamed by a one-time pass that has since been removed. The sweep now leaves every retired hashed or versioned name exactly where it is — never renamed, never deleted — whether or not its photo still exists. Originals are never touched.

### The on-share write contract

Because an existing `.maple/thumbs/` entry is served as-is by every other client with no self-healing re-render, a wrong-parameter write permanently degrades that thumbnail everywhere. Any client writing to the shared path must render at exactly **512 px long edge, AVIF quality 55** (`THUMB_LONG_EDGE_PX` / `THUMB_AVIF_QUALITY` in `src/api/src/thumbs/render.ts`; mirrored as `onShareThumbLongEdgePx` / `onShareThumbAVIFQuality` in `MapleThumbCacheKey.swift` and pinned by a test that reads the TypeScript values). Apple's own grid tier renders smaller (256 px, quality 0.5) for local use, so `ThumbnailLoader` re-encodes the _same_ decoded image a second time at the contract parameters before writing back to the share — writing the local-grid bytes would downgrade the entry for everyone.

Previews have their own agreed parameters: **1280 px long edge, AVIF quality ~0.7** (`PREVIEW_LONG_EDGE_PX` / quality `70` in `src/api/src/indexer/previewer.ts`; `displayPreviewLongEdge` / `displayPreviewAvifQuality` in `src/apple/Packages/MapleCore/Sources/MapleCore/Cache/ThumbnailLoader+DisplayPreview.swift`).

## No pipeline version

There is no pipeline output version. The monotonic counter that once answered "the pipeline now produces different pixels for the same RAW + sidecar — how does every derived artifact know it's stale?" was retired in #5007: shared derivatives had already been decoupled from it in #4793, and its remaining consumers (evidence records, generated mirrors) cost more in re-recording and PR serialisation than they returned. Derivatives are refreshed only when the original or its sidecar changes; a colour-only pipeline change deliberately does not invalidate a shared thumb or preview until that asset is next edited or regenerated. What remains is the state #4793 established, and it must not be re-coupled:

- **Shared thumb and preview filenames** carry no `.v<N>`, and neither do Web's JPEG/WebP/PNG fallback artifacts, descriptors and source identities. Legacy versioned names are renamed into place by readers on a miss (see [Legacy names and rename-on-miss](#legacy-names-and-rename-on-miss)).
- **HTTP.** Clients send no `?pv=` and no `X-Maple-Pipeline-Version` upload header. The server ignores `pv` if an old client sends it, never answers a derivative read with `409` for a version, and accepts `PUT /api/preview` with or without the header. Derivative responses carry no version header, and ETags are content-based only.
- **Server stages and derivative audit** share `THUMB_TARGET_VERSION` and `PREVIEW_TARGET_VERSION`, frozen literals (`src/api/src/workers/derivative-versions.ts`), so nothing re-arms on a pipeline change.
- **The edge cache** keeps its existing R2 keys (see [R2 mirror and the Cloudflare Worker](#r2-mirror-and-the-cloudflare-worker)), so there is no mass re-upload.
- **Apple's `RenderedPreviewCache`** does not include it: its key is the asset's own state only.

Apple's former local counter, `RenderedPreviewCache.viewTransformVersion` (8), was a pipeline-version proxy and was removed with #4793; the rendered-preview cache carries no version. (The 512²-grid `TileManager` compositor and its `viewTransformVersion` (5) were retired in #3288.)

## Apple

Caches under `src/apple/Packages/MapleCore/Sources/MapleCore/`.

`RawRenderSource` holds one temporary RAW copy per active byte-backed edit session. Native-size metadata, decode, Auto Profile fitting and export share its creation task instead of independently fetching the original from PhotoKit or SMB. Scene-linear RAW decode and Auto Profile use the same staged URL so the native decoded-mosaic cache sees the same path key; byte consumers map the staged file without adding a retained full-RAW memory cache. Releasing the session removes the file. It is never a writable original or a sidecar store, and it does not persist between sessions. Local files use their existing URL without a copy (#3357, #3363).

The connected SMB workflow writer holds an exclusive server handle on each
`<sidecar>.maple-lock` while reading, validating and publishing full XMP. It
writes a unique sibling temporary file, flushes it, then requests replacing
rename through the same connection. The persistent lock file has no ownership
by itself: the open handle owns publication and disconnect releases it. A lost
acknowledgement retries the same semantic UUID and checkpoint; an already
accepted action preserves any later confirmed document. First publication must
match the full document adopted when the editor loaded the sidecar. Subsequent
queued saves advance this expectation through their own confirmed publications;
recognizing an accepted UUID does not implicitly adopt another client's newer
model. Ordinary saves retry their identical full document. Named variants bind a
writer to one immutable variant UUID and a session-owned confirmed XMP file for
render/export. This temporary render file is refreshed only after confirmed
publication or reads and is removed with its owner (#4065).

Secondary color-curve LUTs retain one baked set per render thread (`raw-gpu/src/color_curves/inputs.rs`). The key is the exact f32 bits of all six knot lists, including their order; a knot edit or a different active image updates the entry in place. Each entry holds those point snapshots and a fixed 1,536-float LUT. Snapshot capacity starts at the editor's 16-knot bound and is retained across edits and resets; imported curves can grow it without truncating their points. Both CPU and GPU hosts compile the same pure LUT baker from `raw-core/src/stages/color_curve_lut.rs`. Its per-thread knot and spline scratch reserves the authoring bound during warmup, grows for larger imports, and reuses that capacity for changed-point ticks. Stable duplicate-knot ordering is preserved with original ordinals and an allocation-free sort. FFI inputs borrow the host's flat point arrays for the render call, while model hosts retain their existing owned point buffers. These caches hold no image pixels and release with their render thread.

The Rust core also keeps a **single decoded-mosaic `Arc<RawImage>`** in `src/raw-pipeline/raw-core/src/decode_cache.rs`, keyed by canonical path plus original mtime, or a prefix/suffix/length byte hash for byte-only FFI callers. This is distinct from Swift's deep-zoom `RawImageCache` and the session's developed `CIImage`. It avoids repeat rawler demux while its key remains resident; a new `EditSession` still has to demosaic/develop a scene-linear viewport buffer. The Apple f32 file FFI entries check this cache before reading RAW bytes, so a mosaic hit skips that full-file read and rawler demux (metadata stat and Auto's preview-eligibility check still run). Concurrent misses for the same key share one decoded result; different keys do not hold each other behind a decode lock. The registry keeps only active flights and removes its keys after the final caller returns, while the completed mosaic cache remains capacity one.

`raw-ffi` also interns the **HueSatMap endpoint wire** each decode exports for the live white-balance drag (#5099, `wb_frame_flat::intern_hsm_wire`): one immutable copy per distinct profile table pair (the wire carries only the profile's tables and calibration CCTs; the per-photo as-shot CCT and exposure gain travel as separate scalars), kept for the life of the process and never freed, so `MapleSceneLinearBufferF32.wb_hsm_data` stays valid after the buffer is released and Swift and C# keep the pointer itself rather than copying or pinning it. The key is the table content; nothing invalidates it because a profile's tables never change. The set grows only with the number of distinct dual-HueSatMap camera profiles opened, tens of kilobytes each. On the GPU the same tables ride a pooled data buffer whose retained snapshot skips the upload on every tick after the first.

`DevelopedImageRevision` publishes an asset-specific revision after the editor exit has awaited the sidecar, thumbnail and display-preview writes. Grid and filmstrip tasks include it in their decode keys; the retained iPhone Preview page cancels its old loads and resets its display-tier refinement state before reloading. Files-backed saves hold the bookmark-resolved parent security scope through the final writes, and the local display-preview sink also claims it for idle saves (#3957).

`EditorComparison` retains one developed `CIImage` for the active editor's opening adjustments. Its immutable request key includes that model with the current effective crop, viewport pixel size, native image size and the legacy white-balance anchor. Changing a key field replaces the entry; leaving the editor releases it. SwiftUI task cancellation and request equality reject stale completion. It decodes/develops through the existing `RenderActor` and shared RAW source, without replacing the live decoded slot; no disk comparison cache or per-slider-tick work is added.

`LiveHistogramState` retains one in-flight task or completed 768-bin result per `EditSession`, keyed by its presented-frame revision. Every CPU/GPU frame publication cancels old work and invalidates the entry, including refinement and crop-tool transitions; session destruction releases it. Two histogram views share this one entry. GPU statistics occupy fixed 3 KB output and 3 KB staging buffers per live GPU session and are refreshed by the existing present encoder. They are independent of the ping-pong render buffers, so a preview-cache or export readback cannot replace the displayed histogram. There is no disk histogram cache on this path.

GPU-live sessions populate `RenderedPreviewCache` from the existing awaited editor-exit readback, reusing the bytes that refresh the browse thumbnail and display preview. Cold-open readiness does not queue an additional chain render/readback on the GPU actor. Exit joins ordered sidecar updates and flushes the final transaction before capturing the cache revision, drains an older pending preview write, and verifies the uploaded crop/decode identity before reusing GPU pixels. The queued JPEG write retains its original cache key and folder and is discarded if the original or sidecar timestamp changed; an old session cannot capture a newly configured unrelated folder. A successful GPU readback supersedes a pending CPU preview; failed or stale GPU reads preserve that fallback. These derived writes never modify the original.

The shared Rust GPU `FramePool` (`src/raw-pipeline/raw-gpu/src/frame_pool.rs`) retains the **four most recently used chain signatures** per GPU context. A signature includes live-session identity, dimensions, active stages and dispatch-shape inputs; each bucket owns its scratch buffers and ordered uniform/bind-group entries. Four buckets keep fast/refined slider zero-threshold transitions warm while bounding accumulated scratch images when many different controls are enabled. Opening a fifth shape evicts the oldest bucket. New sessions retain the bounded LRU; their unique signature salt keeps image bindings isolated while fast and refined views reuse their own warm resources. Buckets hold a weak session-lifetime token; the next live frame or session open reclaims retired sources without flushing other live views. An evicted shape rebuilds its own resources, never another session's bindings.

Each pooled uniform and read-only data buffer also retains its last uploaded byte content. Equal bytes skip `queue.write_buffer`, which otherwise creates backend staging storage even when the destination buffer is pooled. Changed bytes upload before dispatch and update the retained snapshot in place; snapshot allocation occurs on a cache miss. Data buffer size or lease-kind changes miss, and handing a data buffer out as writable scratch invalidates its snapshot. This preserves changed tone curves and LUTs without using host pointer identity as content identity. These snapshots share the four-bucket lifetime; they add no disk cache. Present-pass bind groups are separately bounded to four dispatches covering both final ping-pong directions of fast and refined sessions. Entries are keyed by the existing monotonic live-session identity, final ping-pong direction and source/destination dimensions. Each surface retains its bind-group layout for the cache lifetime; replacing that layout invalidates the cache. Retired wgpu wrapper addresses are not resource identities (#4355). Apple retains its existing eager invalidation on a session switch, releasing the previous session’s dispatch bindings; its fast/refined switches are not promised to retain four warm dispatches. Geometry values update the retained uniform without replacing its bindings. Closing a Windows GPU session clears these dispatch bindings so they cannot retain retired image buffers; the swapchain itself remains configured.

The session decoded-image cache (`RenderActor.swift`, `RenderActor+DecodedCache.swift`) is the one place where sidecar mtime is deliberately **not** the freshness key. The decoded scene-linear buffer is a pure function of the RAW bytes plus the _stripped_ model — the Apple-GPU stages (exposure, noise-reduction colour, sharpen amount, and so on) are removed before decode and re-applied live per tick, so editing one of them cannot change the decode. Keying on mtime forced a full re-decode (measured at ~15 s on a large RAW) on the first edit after every drag pause, because the 750 ms-debounced sidecar autosave had moved the mtime. The cache now stores and value-compares the stripped model itself, with the sidecar mtime kept only as a fast-path gate: an unchanged mtime proves the file is byte-identical, so the per-tick hot path skips the XMP parse entirely and only falls through to parse-and-compare when a save actually landed. Mtime can therefore make the actor do more work, never serve a stale buffer.

The stripped model deliberately KEEPS every decode-product field, because those are the ones the decode is a function of: `chroma_prefilter`, `deep_denoise`, `hot_pixel_suppression`, the four lens-correction scales, the imported `lens_profile` reference (#2435, which selects the LCP calibration the decode applies), capture sharpening, and — since #3409 — `retouch_spots`, the clone / heal brush's spot list. The repair stage runs inside the decode (`stages::retouch`, first in the capture stage's fixed as-shot Rec.2020 basis, ahead of white balance and before the chroma pre-filter) and has no per-tick counterpart on either the GPU or the CPU chain, so the decode is the only place it can be applied. Placing, moving or deleting a spot therefore re-decodes and, on the GPU live session, re-uploads the base — exactly what changing `deep_denoise` does; a slider drag afterwards reuses the repaired decode. Web's stripped GPU prefix (`raw-wasm/src/gpu_render/model.rs`) keeps the list for the same reason, and its 19-scalar live fast path refuses a model carrying spots so a just-placed spot cannot be missed by a params-only tick.

White-balance names and provenance are excluded from the decoded-model key alongside the live temperature/tint pair. Apple normalizes the live WB scale and metadata in `stripAppleGPUStages`; Web normalizes source, sample point and algorithm version in its stripped GPU prefix. Selecting a named preset, applying AUTO, or switching to a manual adjustment must not cause a new decode solely because its provenance changed. The full live model and saved sidecar retain that provenance.

After a changed timestamp validates the same baked model, the cache accepts the timestamp captured before parsing. Subsequent ticks return to the stat-only fast path; a later write still changes that timestamp and triggers validation. Pending decode ownership is checked after native completion and after normalization, so a late result cannot clear or replace a newer profile/quality request for the same asset.

An absent sidecar uses a precomputed stripped default model in this cache (#4266), matching the native decode prefix. Creating the first sidecar with only GPU-live edits therefore retains the same buffer and generation. A first nondefault baked edit or removal of a nondefault baked sidecar still invalidates by semantic model value; sidecar existence remains relevant to disk derivatives and persistence, rather than this decoded-prefix identity.

Named variant switching (#4063) also compares the selected sidecar path before accepting the decoded-cache timestamp fast path. Equal timestamps on two siblings do not establish equal baked models. Switching to an equal stripped model shares the existing decoded pixels; a different stripped model invalidates them. In-flight decodes are bound to their selected sidecar path. `RenderedPreviewCache` includes a named sibling's path and modification time, while preserving existing primary keys. Queued preview writes retain that selected path and revision; invalidating the RAW clears all its branch previews.

Apple keeps at most two settled variant previews per editor session, bounded to 4096 pixels on the long edge. Reuse requires the same selected UUID, complete confirmed XMP, adjustment model and viewport width. Photos and API sources share the original session-owned RAW download across switches; API decode reads an atomically written, session-owned copy of confirmed branch XMP. The selected writer owns save errors and queued edits. A canceled decode loses join eligibility immediately, even while its native task is still finishing. Named branches cannot seed from the primary embedded, grid or canonical display preview, or overwrite those primary derivatives.

The Web CPU canvas transfers ownership of at most two existing viewport bitmaps at a branch boundary. A hit requires the same source scope, asset ID, original bytes object, selected UUID, render XMP and viewport width; eviction and teardown close unused bitmaps. Admission adds no bitmap copy or allocation to slider ticks. GPU switching retains the existing live session and RAW bytes, while render-generation guards reject stale publications. Both Web backends keep canonical thumbnail/display-preview persistence scoped to Primary.

`ThumbnailDiskCache` has **no disk eviction** — the on-disk thumb store is unbounded and the memory tiers use the FIFO/count bounds in the table above.

Sourced from `src/apple/Packages/MapleCore/Sources/MapleCloudKit/`, the Self-Hosted client adds four more, all under `~/Library/Caches/app.justmaple.aperture/`: `CloudThumbCache` (AVIF bytes keyed on absolute server path, LRU with a 2 GB soft cap and coalesced eviction sweeps), `CloudBucketsCache` and `CloudPagesCache` (JSON `/api/search` responses, stale-while-revalidate, no cap), `CloudFoldersCache` and `AuthUserCache` (last-known folder list and account metadata per `host:port`, used as an offline fallback).

`ForYouCache` (#4595) holds the For You row for the iPhone Search tab and tvOS Memories: one JSON file per library under `for-you/<sha256(cacheHostKey)>/<sha256(libraryID)>.json`, so two servers that share a library id never share a set. Each file holds the generated-search cards in the order they were shown, plus each card's snapshot first page, whose first photo is the cover. It is stale-while-revalidate, like `CloudPagesCache`. `GeneratedSearchCollectionsViewModel.load()` renders the file before any request, then rewrites it from the server's answer. That rewrite drops retired collections and replaces a cover the server's filters no longer return; an empty filtered page clears the cover. Three more bounds limit how long a stale cover can show. Trashing a cloud photo or a fully successful folder removes every cached first page on that server that shows it (`forgetAsset`, `forgetFolder`); a partially successful folder trash removes successful rows under that folder in one cache pass, preserving failed asset IDs and covers at surviving locations. Each removal bumps that server's epoch, and a refresh that began under an older epoch is neither written nor shown, so it can't bring the photo back; a later refresh, after a restore for example, caches it normally. Covers older than three days don't render: the cards show placeholders until the server answers. A replacement cover that fails to fetch or decode leaves the old page in place. The cover's pixels are not in this file; they come from `CloudThumbCache`. A file whose `version` doesn't match the build reads as absent.

Cloud bucket/page scopes include the selected owner ID as well as the folder prefix. An owner-specific scope uses a separate filename/directory from All owners and every other owner. Absent or empty owner IDs retain the shipped unfiltered layout, so existing offline entries remain readable. Clearing a bucket scope removes only that owner/folder entry; clearing a library's page cache removes every owner/folder scope under it.

### File Provider and Quick Look

The File Provider extension (`.../MapleCore/FileProvider/`) is a separate process with its own caches:

- **`RemoteCatalog` ETag cache** — in-memory `(etag, decoded payload)` keyed by absolute URL, LRU-bounded to **256** entries. Without the bound, a Finder spacebar-walk through a 10 k-asset folder pinned ~1 GB in the extension. `invalidateETagCache()` drops it wholesale. Unified folder pages include cursor/limit in their URL keys. Changing the File Provider server rebuilds its registered-root resolver and clears conditional pages; a generation guard prevents an older in-flight response from repopulating the cleared cache.
- **`QuickLookThumbDiskCache`** — AVIF thumb bytes at `<AppGroup>/QuickLookThumbs/<assetID>.<sha1(etag)[:16]>.avif`, so the short-lived Quick Look extension doesn't re-download on every spacebar press. Last-seen ETags live as one tiny text file per asset under `etag-pointers/` (per-file granularity avoids a cross-process read-modify-write race). Eviction is a **7-day TTL** swept at most once every 5 minutes, plus a **200 MB** size cap evicting oldest-by-mtime; pointer files are capped at **1024**. A payload larger than the whole cap is passed through without a write. Reads still revalidate with `If-None-Match` every time.
- **`FileProviderMetaStore`** — a WAL-mode SQLite mirror in the App Group so Quick Look can resolve an asset id the File Provider wrote; rows carry a soft TTL because every `fetchContents` inserted a new UUID-keyed row.
- **`LibraryRootCache`** — library-roots list held for the extension's process lifetime and persisted to App Group `UserDefaults`, with background revalidation and a generation counter so a slow in-flight fetch can't repopulate a cache that was just invalidated.

### Display-preview freshness, and when it's written

Apple never writes the canonical `<filename>.avif` preview per slider tick. `EditSession+DisplayPreviewPersist.swift` captures the latest full-canvas frame and arms a **1.5 s idle debounce** (deliberately longer than the 150 ms refine debounce and the 750 ms sidecar autosave), plus a flush on editor exit. Destination is the session's sink: a local file write, or `PUT /api/preview?path=…` with an `image/avif` body for Self-Hosted assets (`Cache/DisplayPreviewSink.swift`).

On read, freshness is checked rather than keyed (`ThumbnailLoader+DisplayPreview.swift`): the preview must be at least as new as the original file, and it is rejected as superseded when the sidecar is more than **10 seconds** newer than it _and_ the sidecar parses to visual (non-white-balance) edits. An unparseable sidecar counts as edited — serving camera-original pixels over an unknown edit state is exactly what that gate prevents.

On a cold Files-backed RAW, Browse and Preview first display an embedded camera JPEG through the shared Rust extractor, before sidecar parsing or develop. This seed is transient: it is never stored under an edited thumbnail or preview revision. A successful authored render replaces it; a sidecar failure retains the camera seed and logs the failure. Seed extraction has a separate two-request gate so multi-second RAW develops cannot block first pixels. Persisted unedited RAW thumbnails and display previews use that same extractor and the canonical AVIF tier sizes and qualities.

### Memory pressure

`MapleApp.installMemoryPressureObserver` responds to macOS memory-pressure events and iOS memory warnings by shrinking `ThumbnailDiskCache`'s in-memory tiers to 25 %, dropping `RenderedPreviewCache`'s memory front entirely (disk untouched — the next read just pays a JPEG decode), and bumping a `MemoryPressureSignal` that `AppShell` fans out to every inactive edit session.

### Resident CPU editor preview (#4352 / #4112)

The Web worker retains one immutable RAW source and decoded `RawImage` for sized

the whole tick allocates nothing.

## API and edge

### On-disk derivatives

The `thumb` and `preview` stages (`src/api/src/workers/stages/`) write the same shared `.maple/` files described above. Both resolve their output path from `fileinfo[0]` — the library root, the relative directory, and the filename — with no EXIF read, no content hash, and no extra database round-trip (`cachePathForAsset` in `src/api/src/fs/xmp.ts`). Neither path is stored in the database, deliberately: a persisted `thumb_path` column would be exactly the dependency that path-keying exists to avoid. The cost of that cheapness is that neither artifact survives a rename or a move.

A third artifact shares the previews directory: the histogram sidecar at `.maple/previews/<filename.ext>.histogram.json`.

Orphans are reclaimed on two paths. Synchronously, wherever a `fileinfo` entry is removed, `cleanPreviewsCacheForLocation` runs from the missing-reaper (`src/api/src/workers/missing-reaper.reconcile.ts`) and the dedupe hook (`src/api/src/workers/dedupe.ts`) — **previews only**; thumbs rely entirely on the sweep. As a backstop, `src/api/src/workers/cache-gc.ts` sweeps each registered library once at boot: a `thumbs` file is live only if it is `<filename.ext>.avif` for a live filename in that exact directory; a `previews` file is live only if its name matches a live location in that directory. Older retired schemes — 32-hex `<maple_id>` thumbs from the content-addressed era, non-hashed `.jpg` thumbs, `<filename>.1280.avif` previews, and `<sha16>_1600.jpg` pano pre-seeds — are always orphaned and reclaimed here. The #4793 hashed and versioned names are the exception: the sweep skips them entirely (see [Legacy names and rename-on-miss](#legacy-names-and-rename-on-miss)). Two guards keep it safe: files written within the last **60 seconds** are skipped (a file could be mid-write while the sweep reads the directory), and three consecutive unlink failures with the same errno abort the pass, on the assumption that a read-only or permission-denied mount is an operator problem rather than something to grind against. If the library id can't be resolved because the database is momentarily unavailable, the previews sweep counts files but makes no delete decisions at all — a transient failure can never mass-delete live previews. Writes go through `src/api/src/fs/mirrored.ts`, so a library with a configured backup mirror reclaims orphans on the mirror too rather than accumulating dead files there.

### In-process search index

With `search_engine = in-process`, the search child (#4463) keeps a Tantivy keyword index at `<database dir>/.maple/search/text/`, next to the library database rather than in any library's `.maple/`. It is a rebuildable cache of the embedder template text and the `search_blob` for every row of `asset_vectors` written by the configured embedding model. The bge-m3 model it queries with is downloaded once into `<database dir>/.maple/models/fastembed` (or `$MAPLE_MODEL_DIR/fastembed`) — the data volume in the production container, so a rebuild keeps it. `state.json` beside it records the index version (`EMBEDDER_TEMPLATE_SHAPE_VERSION` plus a layout revision) and two catch-up watermarks (`embedded_at` and `text_changed_at`); a version mismatch deletes the directory and rebuilds it, and a text count that disagrees with the vector count after catch-up rebuilds it too. The vectors themselves are never cached on disk — they are reloaded from SQLite on every child start (about 1.4 GB for 335k assets).

Folder and legacy directory listings (`/api/folders`, `/api/fs`) set no `Cache-Control` but do emit a body-hash ETag with a 304 short-circuit. Unified `/api/folder/:slug[/...]` listings likewise emit a body-hash ETag, with `private, max-age=0, must-revalidate`. The hash covers the returned page, including original size/mtime, indexed EXIF/identity, and paired sidecar size/mtime; a matching `If-None-Match` returns 304. Clients cache each page by its complete URL (including cursor/limit). The body is deterministically ordered before hashing, so filesystem enumeration order does not cause needless refreshes.

Unified thumbnail responses use the same body-derived validator before and after indexing. The URL identifies a library location, so a `maple_id` for original content cannot make an edited thumbnail immutable. Conditional requests validate cache freshness against the original and present XMP sidecar before comparing validators; a newer sidecar regenerates the derivative through the shared renderer. Cache files are opened with `O_NOFOLLOW`, and symlinked `.maple` or tier directories are refused before reads or generation. A warm video derivative does not require a decoder; a cold read with no native core or runnable ffmpeg returns an actionable 503.

The preview ETag is deliberately **not** floored to whole milliseconds: the file is overwritten in place, so two rapid re-saves of identical byte size within one millisecond would collide under a floored mtime and wrongly serve a 304 with stale bytes. And the preview is never `immutable` — it lives at a stable URL and changes whenever the editor saves, so a client that cached it forever would never see an edit. Helpers are in `src/api/src/routes/library/shared.ts` and `src/api/src/runtime/http-etag.ts`.

`PUT /api/preview?path=…` (`src/api/src/routes/preview.ts`) is the write half — the remote editor already holds developed pixels, so it publishes them straight to the cache path, atomically via temp-then-rename. It accepts uploads with or without the legacy `X-Maple-Pipeline-Version` header and never gates on it. It takes **AVIF or JPEG** bodies: current browsers' canvas `convertToBlob` cannot genuinely encode AVIF, so a JPEG body is transcoded server-side through the same isolated-child-process decoder the indexer uses. Both branches converge on a real decode validation before publish; a truncated or mis-tagged result is rejected `422` and never reaches the cache path. There is no mtime precondition or conflict-copy dance, unlike the XMP write — a preview is a pure cache.

### R2 mirror and the Cloudflare Worker

The `cf-thumb-sync` stage mirrors each indexed asset's on-disk thumbnail into an R2 bucket. It starts `pausedOnFirstBoot: true` because Cloudflare credentials are operator-entered on Settings → Cloudflare, and unpausing processes the whole backlog — the stage _is_ the backfill. It depends on `thumb` at `minVersion: THUMB_TARGET_VERSION`, and the `thumb` stage resets it to version 0 on every rewrite, so a re-rendered thumbnail always re-uploads instead of leaving a stale edge copy. Hidden assets are excluded, and `src/api/src/cloudflare/hidden-cleanup.ts` actively deletes an already-synced object from every write path that flips `hidden` to true — the Worker checks only token validity, not per-asset visibility, so R2 residency alone determines exposure.

R2 objects are deleted **only** on a false→true `hidden` transition. Nothing deletes the old object on delete, trash, or relocate: a relocate resets the thumb stage, which cascades a `cf-thumb-sync` reset and uploads at the _new_ key, leaving the old key resident in R2 with no equivalent of `cache-gc` to reclaim it. R2 objects also carry no expiry — they live until explicitly deleted.

The Worker (`src/cloudflare/src/index.ts`) fronts `GET /api/thumb/*` only — everything else, including the legacy `/api/fs/thumb`, must be routed straight to the origin. It ignores any `pv` query parameter and never rejects an origin response over a version header. Hidden-asset cleanup deletes every key suffix an object may have been uploaded under, from the bare key through `/v25`. Note that **R2 itself is the cache**; the Worker never touches Cloudflare's Cache API. It verifies an HS256 bearer token before touching R2, then derives the object key from the URL alone — no database access — as `thumbs/<slug>/<relDir…>/<filename>/v25`, each segment URL-encoded. The `/v25` is a frozen literal, not a pipeline version: it is the suffix every object already in the bucket was uploaded under, so keeping it leaves the whole edge cache addressable with no re-upload. The key is built from the photo's path, never the on-disk thumbnail name, so the thumbnail rename changes nothing at the edge. The derivation mirrors `src/api/src/cloudflare/thumb-key.ts` by hand (there is no shared import between the two deploy units). Because the key is path-based, a re-render simply overwrites the object; there is no separate invalidation step.

An R2 hit streams back with `public, max-age=31536000, immutable`; R2's `onlyIf: { etagDoesNotMatch }` turns a matching client `If-None-Match` into a bodyless 304. A miss forwards to the origin with the same bearer token and conditional headers, streams the response to the client, and `tee()`s a copy into R2 via `waitUntil` — but **only for a confirmed 200 with a body**, so 202-unindexed, 304, 404, and 5xx pass through uncached. Every request requires a valid bearer before reading R2 or contacting the origin; a 401 is marked `no-store` so an intermediary cannot keep rejecting a client that later authenticates. A `?format=jpg` request decodes the AVIF and re-encodes JPEG in the Worker, dropping the `etag`, `content-length`, and `content-encoding` headers that no longer describe the bytes; the stored object stays AVIF.

### Regeneration on the server

Each pipeline stage (see [indexer and enrichment](indexer-enrichment.md)) carries a `targetVersion` (`src/api/src/workers/stage-config.ts`). There is no boolean "done" marker — the marker _is_ the integer `stages.<name>.version`, and the claim query is a `<` comparison against `targetVersion`, so raising the constant makes every previously-complete asset eligible again without deleting anything from the database. A bump on deploy also triggers a dead-row reset at boot.

`thumb` and `preview` are frozen at 29 (`derivative-versions.ts`), sharing those constants with the audit and edge dependency, and must never be bumped for a naming or pipeline change. Their historical bump lineages are recorded in each stage file: thumb v2 baked orientation into the embedded preview, v3 moved JPEG → AVIF, v4 moved the cache key from `maple_id` back to the path-keyed `sha256_prefix16(filename)`; preview v3 was the path-keyed AVIF migration and v4 collapsed `<filename>.1280.avif` to `<filename>.avif`. Files from those schemes orphan out through `cache-gc`. The later move to unhashed, unversioned `<filename.ext>.avif` names (#4793) is different: those files are renamed into place by readers on a miss, never regenerated, and `cache-gc` leaves them alone.

The `thumb` stage also cascades: every successful write resets `cf-thumb-sync` to version 0 (clearing attempts, last error, processed-at, and the dead flag) so a re-rendered thumbnail re-uploads instead of leaving a stale edge copy. That reset is atomic with marking the thumb stage complete.

The derivative audit imports the same thumb and preview targets used by the stages, so its freshness decision cannot trail a pipeline bump.

## Dehaze haze maps (#3287)

Dehaze's frame-global half — atmospheric light, guided-filter coefficients and sky mask — is a `FrameHaze` measured on a fixed 2048-texel proxy grid ([pipeline](pipeline.md)). It depends only on the pixels dehaze receives, so every holder below keys it on the chain upstream of the maps (`dehaze::haze_key`): the model with every stage after the last measured map reset to its default — global finishing stages such as contrast, whites, sharpen, NR, vignette, grain and colour grading, layers after the last engaged dehaze layer, and that layer's own sharpness, noise and defringe controls — and each dehaze amount reduced to whether it engages. A dehaze drag, or a drag on any of those downstream controls, reuses the map; an upstream edit (exposure, tone, a mask before the dehaze layer) measures again. The window-chain memo digests the whole base buffer on every request that reaches it, which is only a host-cache miss. All are memory-only and write nothing to disk or to the shared derivatives.

## Invalidation on move, rename, and relocate

**Cache files are never physically relocated.** Both sides delete the old entry and let regeneration happen at the new path, because the key is path-derived and the new path simply has no entry yet.

On the server, `src/api/src/library/relocate-asset.ts` resets `stages.thumb` and `stages.preview` to version 0 (clearing attempts, last error, and the dead flag) inside the same atomic update that repoints the `fileinfo` document, so the workers regenerate at the new location. `src/api/src/workers/discover/rename-reconcile.ts` does the same when the discovery sweep matches a vanished file to a new one by fingerprint — file size plus EXIF `DateTimeOriginal` plus camera serial, with a structural guard that yields a pairing only when both fingerprint buckets hold exactly one member. `src/api/src/fs/relocate.ts` itself never touches cache files at all — that is the caller's job inside its `onVerified` hook.

Only those two cheap raster stages reset. `describe`, `geocode`, `face-detect`, and `face-embed` keep their versions and timestamps, and `src/api/src/library/cache-invalidation-on-move.test.ts` asserts that explicitly: a move doesn't change pixels, so a caption, a reverse-geocode, or a face embedding computed before it is still valid, and re-running them would turn an O(1) filesystem operation into an O(inference) one. The same test also pins that re-running the thumb stage handler for that single asset — never a folder-wide rescan — is enough to produce a correct thumbnail at the new path, and that the old thumb is never served for it, because the two are different filesystem paths by construction rather than one cache slot being repointed.

On Apple, `LocalFileOperations.invalidateDerivedCaches` (and its SMB twin) removes the old `.maple/thumbs/` and `.maple/previews/` files **and** awaits `RenderedPreviewCache.invalidate(assetURL:)`. That second call is load-bearing: the rendered-preview cache is an Apple-local cold-open cache with its own `<urlHash>_<variantHash>.jpg` naming in the same folder plus a 20-entry memory front, and a bare file removal never touches it. Nothing ever revisits a moved asset's old URL, so without the explicit call the old entry leaks in memory and on disk indefinitely — not a bounded wait for eviction. `refreshLibraryIndexAfterMove` separately carries the old `.maple/index.json` row's stars and flag across so a moved photo doesn't transiently read as unflagged.

**One deliberate cross-platform difference in mtime handling.** Apple's `copyVerified` explicitly restores the source's modification date onto the copy, because a plain move must not look like an edit to the mtime-keyed rendered-preview cache (or to the trash-date bookkeeping, which is why `TrashMarker` uses a companion `<basename>.trashed-YYYY-MM-DD` directory instead of repurposing the file's mtime). The API's `relocateFile` does **not** preserve mtime — its destination carries a fresh write time — and `src/api/src/library/cache-invalidation-on-move.test.ts` records that as expected and in fact desirable: a relocate always changes `primary_mtime`, so a stale-adjustment entry can never be served under a reused key. What that test pins as load-bearing is that the _content_ crossing to the new path is byte-for-byte identical.

## Android

Android folder libraries read and write the shared `.maple/thumbs/` and
`.maple/previews/` tiers through the OS document provider, including network
folders exposed by that provider. `FolderDerivativeCache`, `CacheDocuments` and
`SharedCacheContract` use the portable basename hash and unversioned
512-pixel/quality-55 AVIF thumbnails and 1280-pixel/quality-70 AVIF previews.
Fresh shared hits are copied byte-for-byte into bounded private read-through
leases without staging or developing the original. The cache also reads Hosted
preview descriptors for JPEG/WebP/PNG; a newer canonical AVIF takes precedence.
Actual format, bounded dimensions, payload completeness, original/XMP mtimes and
current source identity are validated before reuse. Older/future cache versions
are not selected. Originals and XMP remain the source of truth.

Cold derivatives use the existing core renderer and AVIF encoder. A complete
provider sibling is synced and renamed into place; replacement retains a backup
until publication succeeds. Source and sidecar snapshots are rechecked around
rendering and publication, and descriptor identity checks prevent a provider alias
from truncating or deleting an original or sidecar. Read-only providers, unknown
mtimes, and providers without safe regular-descriptor/rename support use a private
fallback. Android 10/11 decode the bounded AVIF with the core decoder into a private,
sRGB-tagged PNG display bridge after publication. This keeps decoded pixels and
alpha without applying edits again; JPEG/WebP/PNG candidates display directly.
Single-file imports retain private caching, and cloud derivatives retain their
conditional authenticated HTTP cache. `PhotoLibrary.kt` owns the following state:

| Cache                           | Key / identity                                                                                                                                                                                                  | Invalidation / bound                                                                                                                                   |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Staged original                 | SHA-256 of URI, original size and mtime, plus the verified content digest for single-file imports; HEIF/AVIF add `platform-rgb-v2` plus preview edge/full-resolution identity and stage source-gamut float TIFF | 512 MiB plus the currently leased original; a process-wide lease protects all library instances while Rust reads it                                    |
| Single-file thumbnail / preview | Android thumbnail version 4, original identity, requested edge and complete current sidecar text                                                                                                                | 64 MiB shared LRU; metadata-only RAW sidecars reuse the embedded preview                                                                               |
| Cloud derivative                | Original identity and edge → atomic ETag/content-hash index → immutable payload                                                                                                                                 | Same 64 MiB bound; conditional authenticated GET revalidates each load, 304 reuses bytes, changed validators replace the index                         |
| Folder snapshot                 | One parent URI → names, document URIs, types, sizes and mtimes from one provider query                                                                                                                          | Replaced on folder listing/photo open; refreshed during baseline checks; invalidated after XMP publication/recovery. Sidecar contents are never cached |
| Decoded RAW / GPU session       | Current photo session plus one GPU context per serial worker                                                                                                                                                    | Photo changes close the active image; worker teardown releases the device, shader caches and frame pool                                                |

Single-file edits persist in `filesDir/sidecars/` under the SHA-256 of
`private-sidecar-v3:` plus `Photo.key` (URI, original size, modification time and
SHA-256 of the imported bytes). A single-file open streams a fresh provider read
into a temporary file and digest, then publishes that verified snapshot under
the original-cache lease. Rendering uses those same bytes, including when the
provider later replaces the URI. A lost snapshot requires reopening; it cannot
silently read a replacement under the old identity. The import reports progress
and checks cancellation. These durable XMPs have an explicit export. Earlier URI/metadata-only private sidecars
remain untouched; their asset identity cannot be safely inferred for migration.
Private cache hits update recency without enumerating the private cache; shared folder reads revalidate provider metadata and the current XMP snapshot.
Cloud derivative indexes pair validators with immutable payloads so concurrent responses cannot mismatch an ETag and image. Missing/evicted bodies trigger an unconditional fetch; previews and thumbnails have separate entries.
Eviction treats an index and its currently referenced payload as one LRU entry;
superseded orphan payloads remain independently evictable. A new response protects
both its returned bytes and index, with their cost reserved before retaining other
entries, so a cache-limit boundary cannot split the pair. Publication, opening the reader,
and eviction share one short process-wide critical section. A thumbnail reader
opens its descriptor before eviction can unlink the path and closes it after
bitmap decoding, including cancellation. The descriptor keeps its original bytes
readable through eviction and conditional HTTP validation; network requests and
decoders remain concurrent. Missing bodies before acquisition require a fresh
fetch; an already-open reader does not redownload bytes that it still owns.
Eviction runs after new bytes are published; the original's lease serializes
staging and use so its file stays protected while Rust reads it.

The navigation tree keeps activity-scoped child-folder listings by URI, fetched
only when expanded (cloud server library groups load when connected). The current
Browse listing refreshes its matching branch; changing registered sources clears
the tree. UI teardown discards it. Sidebar enumeration uses a separate batched
query and never evicts the active grid’s sibling snapshot. Folder ancestry is
navigation state derived from actual listings, not a parsed document-ID path.

The app-private `sidecar-transactions` journal is persistent edit-recovery state,
not a cache. It is synced before moving an existing canonical XMP to a backup.
An interrupted replacement is recovered before reads/writes; original photos
are never modified or treated as disposable cache data.

## Windows

`src/windows/Maple.WinUI/Services/ThumbnailService.cs` runs two tiers. The **512-px grid tier** writes the cross-app shared `.maple/thumbs/` cache via `ThumbCachePaths`, and reuses an entry only when it is newer than the original and its sidecar. A cold render develops a present sidecar through the Rust recipe renderer, including its selected film and restored lens profile; malformed XML or an unavailable LUT fails without publishing camera-original pixels. When the photo folder is unwritable (read-only media, a share without write permission), it falls back to a machine-local copy so thumbnails still work.

The **2560-px full-screen JPEG preview tier** has no cross-app contract, so it stays machine-local under `%LOCALAPPDATA%\Maple\local-cache`, keyed on `SHA-256(path|rawMtimeTicks|size|sidecarMtimeTicks|maxPx)[:32]`. Edits and moves therefore orphan entries naturally; a **30-day age sweep** on construction is what keeps that bounded, alongside a one-shot deletion of the pre-shared-cache `%LOCALAPPDATA%\Maple\thumbs` directory. The shared tier's old entries are cleaned synchronously by `LocalFileOperations.FinalizeRelocate`.

## The adjustment-version proxy

**Sidecar mtime is the adjustment-version proxy, and Apple's rendered-preview cache and Windows' local derivative cache key on it.** Verified in code:

- `RenderedPreviewCache.cacheKey` hashes `"<primaryMtime>_<sidecarMtime>_<screenWidth>"`, with no version component (#4793). Because every sidecar write bumps the file's mtime, any slider change changes the key. `primaryMtime` is in there too, so a change to the RAW's own bytes that leaves the sidecar untouched — a re-import, an external sync tool, a filesystem restore — also misses, rather than serving a preview developed from the old bytes under an identical key.
- (The retired `TileManager`'s `TileKey` also carried `sidecarMtime` directly as a field — #3288.)

Shared filenames carry no pipeline version and omit an edit token. Clients validate freshness against the original and sidecar mtimes, and the editor overwrites the shared artifacts after a develop render. Apple's `ThumbnailLoader.updateThumbnailFromRender` updates the grid thumbnail; its idle-debounce persist updates the 1280px display preview. Windows' machine-local derivative key also includes sidecar mtime. The server preview ETag — the preview file's own `mtimeMs` and size — propagates replacement bytes to HTTP clients.

And one cache deliberately rejects the proxy: the session decoded-image slot on `RenderActor` keys on the stripped adjustment model instead, because most slider moves don't change the decode at all and treating a sidecar write as a decode invalidation cost a full re-decode on every drag pause. Sidecar mtime survives there only as a cheap gate that decides whether the XMP is worth re-parsing.

## Backup transfer state

The durable backup records are described in [Cloud backup](cloud-backup.md). They contain deletion obligations and recovery ownership as well as reusable transfer state, so they must travel with the server database backup rather than be cleared with derivative caches.

`backup_coverage_counts` is a durable materialized counter used to keep the backup destinations status route off the full location scan. Its key is `library_id`; its value counts locations with neither `deleted_at` nor `missing_since` whose asset is not reaped. Migration `0016-cloud-backup-destination-status` backfills a row, including zero-valued rows, for every existing library. SQLite triggers maintain it on location insert, update and delete, and on asset reaping and deletion. New libraries acquire a row on their first live location; an asset reaping transition also reconstructs a missing row from current library state. This is derived query state, but it lives in the database and must remain transactionally consistent with its source rows.

## Comparison with the previous version of this document

Five things the old document stated that the code does not support:

1. **The decode caches in old §4 and §5 no longer exist under those names.** Old §4 described `EditSession.decodedImage` as "a lazy CIImage backed by a CIRAWFilter graph"; old §5 described `EditSession.cachedFileData` holding whole SMB file bytes. Neither symbol exists. Decoding never goes through `CIRAWFilter` — that type is used only to read as-shot metadata, and `ImageMetadataReader.swift` says so explicitly. What replaced them is a pair: `RawImageCache`, a single-entry in-memory hold on the rawler decode handle keyed on `(URL, mtime)`, and the `RenderActor` decoded-image slot keyed on the _stripped_ adjustment model rather than sidecar mtime. A third, disk-backed decoded-buffer cache with its own `rustVersion` counter also existed and was removed; its version lineage survives only as commentary inside `RenderedPreviewCache.swift`.
2. **Thumbnail naming, format, and size.** Old §2 gives the on-disk thumbnail as `.maple/thumbs/{original_filename}.jpg` at JPEG quality 0.8. It is `.maple/thumbs/<filename.ext>.avif`, and the shared write contract is 512 px at AVIF quality 55 — distinct from Apple's 256-px local grid tier, which is why the Apple writer re-encodes the same decoded image a second time before writing back to a share.
3. **Thumb eviction.** The old doc claimed LRU-by-mtime with a 500 MB / 10,000-entry cap. There is no such code. The on-disk thumb store is unbounded on Apple; the memory tiers are FIFO-capped at 100 entries with a 2000-entry `NSCache` for synchronous peeks. Likewise old §1's `ThumbnailLoader.memoryCache` — a 500-entry `LRUCache<String, CGImage>` keyed `"{assetID}_{maxDimension}"`, with `prime(assetID:size:image:)` and `invalidate(assetID:)` — does not exist; no `LRUCache` type is defined in MapleCore at all.
4. **Where rendered previews live.** Old §3's body correctly says `.maple/previews/`, but its own flow diagram and its "Clearing Caches" table both say previews persist to `~/Library/Caches/` and are lost when the OS purges it. They do not; they sit next to the photos and travel with them. (Apple's Self-Hosted client caches — cloud thumbs, search buckets, folder lists, account metadata — _are_ the things under `~/Library/Caches/app.justmaple.aperture/`.)
5. **The five-cache framing.** The old "five caches at a glance" table describes an Apple-only world. It omits the layers that carry most of today's behavior: the shared filenames and per-platform memory keys, the R2 and Cloudflare Worker edge tier, the File Provider and Quick Look caches, the ten web IndexedDB stores and the byte-bounded in-memory tiers, the API's per-stage `targetVersion` regeneration and its `cache-gc` sweep, and the server-side TTL caches for search counts and reverse-geocodes.

Two things the old doc got right and this one preserves: the `RenderedPreviewCache` key composition, including sidecar mtime as the adjustment-version proxy, and the Hosted preview cache's descriptor-based validation. Separately, the `<sha16>_1600.jpg` naming that sometimes gets attributed to the preview cache is a retired scheme on both sides — `cache-gc` reclaims it as an orphan and nothing writes it, and Apple's reader never consults the equivalent old path.

### Maple TV Top Shelf

`TopShelfCache` stores up to five JPEG covers and an atomic JSON manifest in the
App Group's `TopShelf/<SHA256(server URL + library ID)>/` directory. The app and
extension share this cache; disk reads and writes run on its actor. A manifest is
fresh for six hours. Refresh publishes only covers downloaded successfully and
removes images no longer referenced. The extension requires a paired server with
Keychain credentials before reading a cache, so unpairing hides the shelf.
Selecting another server or library uses a separate cache directory.

## Linux native-detail session (#4317)

The native Linux worker reads one immutable source-byte snapshot at image open
and decodes its RAW mosaic from those same bytes. CPU previews, GPU preparation
and native detail share that snapshot; later file changes cannot pair an old
mosaic with new embedded-preview bytes. Opening another image (including a
reload) reads a fresh snapshot. Preview/I/O and the independent CPU detail
worker share the existing mosaic and byte allocations via immutable Arc
ownership. The preview worker releases its old source before decode; an
already-running detail operation may retain that old snapshot until it finishes.
No disk derivative is written by this path.

| Entry                                                 | Key                                                                          | Lifetime and invalidation                                                                                                                                |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decoded RAW and source bytes                          | Active source snapshot identity                                              | Preview ownership replaced before image decode; in-flight detail ownership released on completion; all ownership released on joined shutdown             |
| Native raster linear Rec.2020 RGBA                    | Active source snapshot identity                                              | One buffer, decoded lazily on the independent detail worker under shared raster decode limits; replaced on source change and released on joined shutdown |
| Native-detail full-frame anchors and bounded CPU base | Source identity plus full adjustment model                                   | One reference on the detail worker; replaced on source/model change, cleared after patch rejection/closed source, released on joined shutdown            |
| Canvas base texture and native patch texture          | Image session, detail request generation, source rectangle and current edits | One base and one patch; edits, Fit or image change clear the UI entry; obsolete results cannot publish                                                   |

Every successful patch carries shared ownership of its bounded base pixels.
Raster patches use the same window chain as the full-frame non-RAW renderer,
including source coordinates and a conservative pad from the shared spatial
overlap calculation. Their 8,388,608 working-pixel limit bounds the patch and
its halo, separately from the retained native source buffer. Raster base pixels
are keyed by the full model; source pixels are reused across edits and pans.
Subsequent pans reuse the same base allocation and full-frame AE/Auto artifacts;
dropping the first superseded result cannot leave its successor without a base.
The published source rectangle includes a pan margin; pans contained in it need
no new develop. The core includes its exact filter overlap in the 8,388,608
working-pixel limit. A single latest pending snapshot bounds pan requests;
in-flight CPU detail completes through the existing core API, and stale results
are discarded. GPU previews and XMP saves run independently of this CPU detail
queue. Shutdown joins both workers; old in-flight source memory and shared CPU
contention still require hardware qualification. This is not a latency guarantee.
