# Adversarial review — AI object-removal draft (PR #4239)

Branch `codex/ai-object-removal`, head `44d342ac`, merge base `23cc6377` (2026-10-10). Reviewed 2026-11-04 by four independent read-only passes (Apple; Rust; Web/API/Windows; cross-cutting), each briefed with the #4495 landing-plan comment so that already-known items are not repeated. Findings below are new relative to that comment. "Confirmed" means the reviewer read the full code path and the coordinator re-verified the cited lines on the branch; "plausible" means the mechanism is read from code but not executed.

Companion to the landing plan on #4495. This PR does not merge; the findings feed the slice plan.

## Verdict

The prototype's safety core holds: no path writes, renames, truncates or deletes RAW bytes; the removal commit is a real compare-and-swap; models are user-imported and pinned by SHA-256 and size; companion names are digest-derived, so no path traversal. Everything else is in worse shape than the landing plan assumed, in three ways:

1. **Saved removals render wrong or not at all** in common cases (lens-corrected RAWs at 100% zoom, a single deactivated record, legacy schema-2 records on Web, PhotoKit histograms), and generated patches are not reproducible between native and browser.
2. **Removal machinery taxes every photo, including ones with no removals**: full-RAW hashing on every cold open and up to seven times per move, lock inodes left beside every moved photo, fail-closed file operations on malformed hidden files, a whole-XMP DOM parse on every 2D render tick.
3. **The three platforms disagree** on what a valid record list is, where companions go on trash/restore, and which write paths are guarded, so a photo edited on one platform can be silently damaged or made unrenderable by another.

An attempt to merge `main` into the branch (2026-11-04) stopped at 69 of 132 conflicts: both sides restructured the develop pipeline, the sidecar store, the Apple editor bars and the Web render worker. Bringing the branch level with `main` is the S10–S16 re-derivation, not a chore. Keep the draft at its 10 Oct base.

## P2 — robustness, performance, security boundary

**Cost imposed on photos with no removals**

- Apple: `LocalRemovalRelocation.open` is unconditional in `planRelocate`, case-rename and OS-trash. Every move creates `.<raw>.xmp.lock` (source, left behind) and `.xmp.lock` + `.relocation.lock` (destination), never unlinked; existence of a lock file makes every later ordinary save take the `flock` path, which fails on non-flock mounts. Every move hashes the whole RAW with SHA-256 up to seven times (500 × 200 MB on SMB ≈ 700 GB of reads). (`LocalFileOperations.swift:109,273`, `+Trash.swift`, `LocalRelocationLease.swift:34-36`, `XMPSidecarStore+Coordination.swift:45-48`)
- Rust/FFI: `blake3` over the full RAW on every `maple_open_raw_handle{,_bytes}` (70–150 ms of the 250–1000 ms cold-open budget); `removal_records::parse` re-parses every sidecar read with a second `NsReader`. (`handle_open.rs:92,173`; `xmp/reader.rs:113`)
- API: the whole RAW is read into memory ~8× per move (`verifyFile` ×5 in `relocateUnderLease`, ×3 per Keep). (`raw_ffi-removal-assets.ts:84`, `relocate-removal.ts:141-226`)
- Web: non-removal full-XMP GPU renders ship an empty bundle and force a redundant Rust `prepare_saved_removals`; `publishGpuDimensions` now allocates fresh signal objects and rewrites styles on every scalar tick. (`image-canvas.gpu-present.ts:386-405`, `session-handler.ts:304-316`)
- Opening the Remove tool reads the whole RAW into memory and opens a Rust session before checking whether a model exists, on all platforms; the tool is unconditional on iOS. (`RemovalSession.swift:116-161`, `NativeRemovalEditorEngine.swift:78,90`)

**Fail-closed in the wrong places**

- Apple: file operations now fail on any unparseable sidecar containing the substring `InpaintRemovals`, and on any malformed `.<raw>.relocation.json` (`RemovalXMPRecords.swift:38-46`, `LocalRelocationJournal.swift:84-112`).
- Rust: any schema-2 record or non-`LinearCalibrationV1` plate fails the whole stack rather than that record (`removal_resolved.rs:144-148`); an explicitly serialised default `"plate"` on a schema-3 record is refused (`types/inpaint.rs`); region equality is bit-exact f32, so a host rounding in f64 fails the record.
- Windows: `RequireStoredRemovalHistory` catches only `FileNotFoundException`; a sharing violation from OneDrive/antivirus fails every decode for non-removal photos (`RenderEngine.DecodeOwned.cs:20-29`).
- API: malformed existing `InpaintRemovals` → 500 with a parser message, not 409/422 (`removal-authoring.ts:235,248-253`).

**Cross-platform disagreement**

- TS accepts any JSON array as a record list; Swift validates through Rust and fails the sidecar. `[{"kind":"removal","schema":9}]` → Swift can't open, Rust render fails, Web opens and re-emits. `[1]` → Rust empty stack, Web non-empty. (`xmp-parser.service.ts:141-144` vs `RemovalRecords.swift:11`)
- Web normalises empty arrays to `'[]'`; API and local Keep compare the literal string. A foreign `[ ]` makes the photo permanently unsaveable through CAS. (`sidecar.store.ts:150-151` vs `removal-authoring.ts:157,204`)
- Removal actions never enter the persisted workflow history on any platform; a first-edit removal leaves the History panel empty after reopen. (`EditSession+RemovalHistory.swift:176-205`)

**Security boundary (API)**

- `/api/removal/*` has `requireAuth` only; every other library-writing route gates on `file_access`. A `file_access:false` user can fill `.maple/inpaint` with unbounded valid ~33 MB `.f16` patches and download any companion. (`routes/removal.ts:24-25,72-79` vs `routes/assets/relocate.ts:107`) Confirmed.
- Discover sweeper `restore()` deletes destination files on the authority of an on-disk JSON journal: a hand-written `.<victim>.removal-relocation.json` naming a sibling with `backup:null` and `incoming = sha256(victim)` removes `victim.dng` on the next sweep. Needs write access to the library dir (sync client, create-only ACL). Reachable from data, not from a user action. (`removal-relocation-journal.ts:143-190`; `discover/removal-recovery.ts:17-39`) Plausible.
- Active relocation recovers journals without the root check the passive path has; a journal `source` outside registered roots gets flocked and lock files created beside it. (`relocate.ts:420-446`, `removal-relocation-journal.ts:261-268`) Plausible.
- `commitRemovalSidecar` writes client XML verbatim, bypassing `prepareWorkflowWrite`'s primary-variant identity check and server-checkpoint re-embed (#4036/#4051). (`removal-authoring.ts:211-213`)
- Companion publication, relocation and journaling require `fs.link()`; fails with EPERM/ENOTSUP on CIFS without unix extensions, exFAT, many FUSE/NFS mounts — the NAS targets Self Hosted serves. Companions are never reclaimed; `.maple/inpaint` grows monotonically.

**Editor regressions**

- Apple: any programmatic `model` write while `workflow.isBusy` is silently reverted (late auto-fit landing, WB-frame adoption, preset application); `resetAutoFitStatus()` still fires first. (`EditSession.swift`, `EditSession+RemovalHistory.swift:99-107`)
- Apple: a commit failure between rename and directory fsync leaves the removal on disk, absent in the UI, and wedges all ordinary saves with `saveConflict` until the identical attempt is retried. (`XMPSidecarStore.swift:413-414`, `LocalRemovalCommitRecovery.swift:30-36`)
- Apple: `finalizeRelocate` reports success with `primaryPath` = destination when the source changed between plan and finalize; the index then lists a stale copy while the newest edit lives on an orphaned source. (`LocalFileOperations.swift:134-162`)
- Web: `updateAdjustment` throws synchronously on any full-model patch whose `inpaintRemovals` differs (paste develop settings); `removalSavingAsset` early-return drops legitimate slider writes during a save. (`library-state.service.ts:343-348`)
- Web: removal session fully reopens (re-read RAW, re-decode, seconds at 100 MP) on any serialized-model change while armed, including As-Shot WB / auto-fit / lens seed landing after open. (`removal-editor-session.service.ts:122-175`)
- Web: saved-removal load failure on cold open is reported as a GPU fallback, then the 2D fallback fails the same way → blank canvas with a misleading notice. (`image-canvas.gpu-present.ts:230-272`)
- Rust/FFI: `maple_histogram_bytes` passes `directory = None`, so any PhotoKit asset with a removal has a permanently broken histogram (pinned by a test). With a stack, tiles bypass the handle's `FrameCache` and rebuild the ~480 ms highlight prior per tile. Each `MapleSavedRemovals` retains a full copy of the RAW bytes. ORT `init_from` is process-global first-set-wins, so pano and removal may silently run different dylibs. `InpaintCompositePass` + WGSL + parity gate have no caller; the shipping composite is CPU-side.

**Documentation and layout**

- `docs/caching.md` places `.maple/inpaint/` (non-regenerable edit pixels, "never cache-purged") inside the folder CLAUDE.md defines as disposable derivatives; the suffix is documented as `.mimf` but the code uses `.mask` (`removal_assets.rs:22`). `docs/features.md`'s support table contradicts `docs/server-api.md` and the doc's own prose on Self Hosted removal.
- `.maple/trash-staging/` is created and never removed; on `trashItem` failure a whole recovery folder (RAW copy, XMP, companions, locks) stays behind. Not tabulated in `docs/caching.md`.

## P3 — hygiene (selected)

- "Durable" publication is `fsync`, not `F_FULLFSYNC`; on APFS the drive cache is not flushed, so the asserted durability boundary does not hold across power loss.
- All model-backed Swift test classes skip-pass in CI (14 classes gated on uncommitted paths); iOS inference has a bare `throw XCTSkip`. Only the 774-byte synthetic DNG corpus runs. `removal-self-hosted/**` e2e leaks into the default Playwright suite without `test.skip` and hard-fails locally; no workflow runs `e2e:removal*`.
- `tools/removal/*_test.py` (34 files) use bare sibling imports, so they fail under `python3 -I`; two tests hard-code `Path.home()/.cache/...`. Exporters `sys.path.insert` an upstream checkout and import third-party Python by design (pinned, offline).
- Full-sensor mask FFI (`combineMasks`, `refineSelection`) runs synchronously on `@MainActor` despite the bridge comment.
- `develop/mod.rs` still inlines the camera prefix that `camera.rs` duplicates verbatim; identical today, a silent-divergence hazard. `unsafe` blocks without `// SAFETY:` in maple-ort and raw-ffi. `render_display_scene_with_removals` dropped the leading cancel check. Stale `native-removal-probe.rs` example always fails.
- Records cite the retired ACR colour gate (`MANIFEST=... test_color_pipeline.sh`, retired by #5000).

## What is sound

- No path writes, renames, truncates or deletes RAW bytes on any platform. Relocation is copy → verify → publish via temp sibling; companions are published with `linkItem`/`fs.link` (refuses replacement) and treated as immutable; recovery never unlinks the only copy.
- The removal commit is a genuine CAS on every platform that has it: `expectedRecords` compared under the writer lock, companions verified and fsynced before the XMP rename, precondition re-read on entry, before publish and after publish.
- Model integrity: user-imported only, SHA-256 + size pinned at install and again before `InferenceSession.create`; no network fetch anywhere; `torch.load(weights_only=True)`, `from_pretrained(local_files_only=True)`.
- Codecs (MIMF/MIPF) and bundle manifests validate header → layout (`checked_add/mul`) → length → NaN/Inf before any allocation. Companion names are digest-derived and regex-confined; `lstat` + symlink refusal on every sidecar/companion path.
- XMP field parity across TS/Swift/Rust/C#: identical attribute name, namespaces, attribute-rank sort, escaping and JSON keys; `papp:InpaintRemovals` kept out of `KNOWN_ATTRIBUTES` so byte-for-byte passthrough holds.
- The NLM bounded path is gated bit-for-bit against the strip kernel across 1/3/7/23 threads and four noise profiles (still feature D; needs the 20-fixture colour run). WB-presence flags do not perturb the decoded-cache key. The live Web GPU path keeps its zero-alloc shape on scalar ticks.
- No new `#[repr(C)]` struct reaches C# or bun; all 50 referenced `maple_*` symbols are exported; removal failures return rc 8, not the rc 7 raster fallback.

## Implications for the #4495 slice plan

- S11/S12 (confirmed sidecar commit, relocation/trash) must be re-derived on main's `assetDestinationOccupied` and lifecycle hooks, scoped to photos that actually carry removals, and must define trash/restore semantics for companions before any lock or journal lands beside a photo.
- S14 (develop/render) must fix the composite-vs-warp ordering and add an OpcodeList3 saved-tile parity test before the tile path is trusted; the native-vs-WASM RNG fix is a one-line prerequisite for any cross-host digest claim.
- The record-validation contract (schema versions, explicit default plate, empty-array literal, f32 region equality) needs one spec and three conforming readers before S10 ships; today each platform has its own.
- Features B, C, D remain ride-alongs needing their own tickets and 20-fixture colour evidence; C is not Mac-only.
- Qualification evidence must be re-recorded against committed revisions with in-repo inputs, or dropped.
- Open legal question before any model ships: Places2 dataset terms for LaMa weights.

## Does any finding apply to `main`?

No. Every confirmed defect is in code that exists only on `codex/ai-object-removal`. `main` carries four early slices, all inert — no platform writes or exposes removals (`docs/features.md` says so explicitly): the `papp:InpaintRemovals` record decoder (`raw-core/src/types/inpaint.rs`, read in `xmp/fields.rs`), the patch type and `.f16` codec (`pipeline/inpaint_store.rs`), the composite seam at the start of the scene-linear chain (`scene_linear_chain/patches.rs`), and two `maple_apply_scene_linear_chain_*_with_patches` FFI entries with no caller (#1486 staging). Swift, TypeScript and C# pass the field through; raw-wasm ignores it.
