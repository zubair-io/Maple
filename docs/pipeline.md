# The Rust raw pipeline

Every pixel Maple shows on any platform comes out of one Rust cargo workspace at `src/raw-pipeline/`. A RAW file is decoded to a sensor mosaic, demosaiced into camera-native RGB, colour-corrected into a scene-referred working space (linear Rec.2020 at D65, f32, unbounded), pushed through ~20 editing stages that never clip, and only then compressed into a display image by a single view transform (AgX) plus a gamma encode and a quantizer. That whole chain lives in `raw-core` as portable Rust with no platform dependencies; `raw-gpu` re-implements the interactive subset as wgpu/WGSL compute kernels gated against the Rust functions; `raw-ffi` and `raw-wasm` wrap the same code as a C ABI and a WebAssembly module so the Apple, Windows, server, and browser shells all render identical pixels; `maple-cli` drives it headlessly for the parity harnesses; and `codegen` emits the constants and schema mirrors the other languages compile against.

The two invariants that shape everything below: nothing before the view transform clips, and the CPU implementation in `raw-core` is the reference every other implementation is measured against.

## Decode

`raw_core::decode` wraps **rawler 0.7** — `decode_bytes(bytes, ext)` is the primary entry and `decode(path)` is a `std::fs::read` wrapper over it, so the browser (which has no filesystem) and native callers share one code path. The extension is passed to rawler as a filename hint because several formats are not magic-byte-distinguishable. Foveon X3F is detected on that hint and rejected with a structured "unsupported format" error rather than rawler's internal stub message.

Decode produces a `RawImage` (`raw-core/src/image.rs`): the mosaic `Vec<u16>`, black/white levels per CFA position, the CFA pattern, and the metadata the colour chain needs — `AsShotNeutral` (inverted from rawler's reciprocal WB multipliers so it matches the DNG spec's semantics), `UniqueCameraModel`, `BaselineExposure`, `ColorMatrix1/2`, `ForwardMatrix1/2`, `ProfileHueSatMapData1/2`, `ProfileToneCurve`, `ProfileGainTableMap`, `DefaultCrop*`, EXIF orientation, ISO, noise profile, aperture and focal length.

Four decode-path details are worth knowing:

- **Embedded matrices are only trusted from real DNG tags.** `color_matrices` is populated only when the source file itself shipped `ColorMatrix1`/`ColorMatrix2`. Vendor RAWs (`.cr2`, `.arw`, `.nef`, `.fff`, …) leave it empty even though rawler substitutes its own dcraw-lineage matrices internally, because surfacing those measurably regressed colour.
- **`LinearizationTable` is not applied by Maple.** rawler already applies it inside the decoder; `raw_core::linearize` documents this explicitly so nobody double-remaps it.
- **Two mosaic shapes.** `CfaPattern::LinearRgb` marks a LinearRaw/DNG-Converter file whose data is already interleaved RGB; it skips the mosaic path entirely via `linearize::linearraw_to_camera_rgb`. `CfaPattern::XTrans` routes to the X-Trans demosaicers. Everything else is Bayer.
- **Masked margins are refilled before demosaic (#4657).** The mosaic keeps the whole sensor frame and its coordinates, but each strip outside the active area is replaced by the nearest active sample of the same CFA phase, so optical-black columns and zero padding never reach demosaic or the wide spatial stages as scene content. A DNG's ActiveArea tag is always honoured; a decoder's own rectangle is refilled per strip only when its content is at black, because some (Panasonic's SensorBorder) still hold image data. DNG sensor gains reach the refilled samples through the same mapping.

DNG `OpcodeList2` sensor `GainMap` corrections and `MapPolynomial` transfers are parsed into `RawImage.sensor_gain_maps` and applied in list order after black normalization, before CFA demosaic (or after LinearRaw linearization); transfer output is pinned to [0, 1] as in the DNG SDK. 8-bit lossy LinearRaw keeps its gamma 2.4 guess instead of its declared transfer until #5081 re-derives the lossy white balance. An opcode entry Maple cannot run never drops its list: it is skipped, and every skipped required opcode is reported by `RawImage::skipped_required_opcodes` and logged once (#4647; error policy in `pipeline/pano/opcodes/mod.rs`). Gains may produce values above sensor white. Highlight detection scales its per-channel ceilings and ripple floors by the spatial calibration; full, sized and tiled renders use the same sensor coordinates, including the frame evidence used by guided recovery. Known channels retain their original values. This runs in the shared Rust decode prefix before the GPU receives scene-linear pixels.

DNG `OpcodeList3` (tag 51022) is parsed at decode time by `raw-core/src/pipeline/pano/opcodes/` and applied post-demosaic by `pipeline/pano/opcode_apply/`. Three opcodes are implemented: `GainMap` (id 9, a bilinearly-interpolated per-plane gain lattice — vignette/shading), `WarpRectilinear` (id 1, geometric distortion + lateral CA with the Adobe SDK’s A=-0.75 cubic kernel and sticky borders, using its 32-phase lens-warp table), and `FixVignetteRadial` (id 3). Highlight recovery precedes these OpcodeList3 gains so they do not masquerade as sensor saturation. Partial-clip reconstruction uses the same surviving-channel mean for each target and its valid neighborhood witnesses; it preserves known channels and leaves targets without usable known signal untouched. The supported estimate blends with the existing brightest-known neutral fallback at the unchanged neighborhood confidence. A frozen clipping mask excludes reconstructed pixels from witness reads. Targets and witnesses are restricted to the physical sensor `ActiveArea`, scaled to the actual demosaic resolution; valid scene pixels outside `DefaultCrop` remain witnesses, while masked sensor borders do not. The tile path translates the same bounds into its padded window. The opcodes run in list order, in `ActiveArea`-relative coordinates, and — unlike the DNG SDK — the result is deliberately _not_ clamped to 1.0, because the working space is unbounded. `ProfileGainTableMap` (tag 52525, DNG 1.6 § 6.8; found in a SubIFD by `raw-core/src/dng_ifd_walker.rs`) is parsed onto `RawImage` but not applied: the spec pairs it with the profile's `ProfileToneCurve` as a vendor look layer, which #425 dropped (see `color/profile_gain_table_map.rs` and #2774).

`decode_cache.rs`, `preview.rs` (embedded-JPEG extraction, shared by native and browser), `jpeg.rs`, `png.rs`, `tiff.rs`, `avif.rs` and `icc.rs` round out the I/O surface.

Stages 9a–9d form the **capture half** and stages 10–12 and 16–17 the **creative half** of the capture-first split ([below](#capture-first-the-capture-and-creative-halves-5213)).

The develop function captures a bounded-sample P99 luminance statistic from the as-shot camera buffer projected through linear DCP, before user white balance and auto-exposure, stored as `Image.whites_anchor_ev` in EV relative to 0.18. Positive Whites uses this retained full-frame value to resolve its bounded AgX bump strength. FFI and WASM hosts retain it with decoded pixels and forward it to CPU, GPU, and detail tiles; tiles must not derive a new anchor from their crop. No percentile is computed during an ordinary cached slider update. Negative Whites is independent of the anchor.

The develop function returns the scene-linear `Image` (and, on the `_with_gain` entries, the scalar gain auto-exposure applied — the tile path threads that back in so a tile reproduces the full-image anchor).

`RenderQuality` (`pipeline/mod.rs`) picks the demosaic: `Preview` uses the half-res quad kernel (4× fewer pixels downstream, and the buffer comes back at half dimensions — callers scale it themselves), `Full` uses **RCD** (#3412), `Amaze` uses the tiled AMaZE kernel and is `maple-cli`'s default, and `Auto` (#3413) asks `demosaic::policy` which kernel this particular frame wants. Quality is caller-selected: Web CPU/GPU live preparation and Apple scene-linear cache preparation explicitly use `Amaze`; callers requesting `Full`, including the deep-zoom tile chain, receive RCD. A CPU parity oracle must use the same quality as the binding under test; flat fields conceal a demosaic mismatch (#3633).

All four Bayer dispatch sites call one selector, `pipeline::bayer_kernel`, so they cannot drift apart. It resolves the quality level's own default kernel against the sidecar's `papp:Demosaic` override, and at `Auto` against the policy below. `Preview` is the exception and returns `HalfRes` unconditionally: that path bins 2×2 before any reconstruction runs, so there is no kernel choice to make and the override is deliberately inert there. The FFI/wasm quality integer gained `3 → Auto` by appending, so every existing caller's number keeps its old meaning.

#### Noise-adaptive selection (#3413)

Before #3413 the kernel was a constant per quality level, so a 12800-ISO handheld frame got exactly the same treatment as a tripod-mounted base-ISO landscape — even though the two want opposite things from a demosaic. `RenderQuality::Auto`, which export and native-detail patches now request, applies three rules in order (`demosaic/policy.rs`, one named constant each):

1. **Noisy frame → LMMSE.** "Noisy" means a mean per-plane noise standard deviation at mid grey of `LMMSE_SIGMA_MID_GREY` (0.008, i.e. 0.8 % of full scale — roughly ISO 3200 on a current full-frame body) or more, read from the DNG `NoiseProfile`'s `variance = scale · signal + offset` pairs. Files without that tag — most vendor RAW formats — fall back to `LMMSE_ISO_FALLBACK` (ISO 3200). The fallback is deliberately not derived from the synthetic noise model in `stages::nlm`: that model is calibrated for a denoiser's strength knob, not for absolute variance, and reading an absolute threshold off it would be a guess dressed as a measurement.
2. **Large frame → dual AMaZE + VNG4.** At or above `DUAL_MIN_PIXELS` (20 MP).
3. **Small frame → AMaZE alone.** The dual mode's second kernel is a real cost, and on a frame small enough that the whole demosaic is already cheap it buys a difference measured over too few pixels to matter.

Nothing in the policy looks at whether the frame "seems" detailed — that decision is per-pixel and belongs to the dual mode's contrast mask, which measures it directly. The policy only picks which pair of kernels the mask gets to choose between. A user who has picked a kernel by hand (`papp:Demosaic`, surfaced as the Detail → Basic picker on Apple and Web) always gets that kernel instead.

**RCD** (`demosaic/rcd/`) is Ratio Corrected Demosaicing, written from the published description of Luis Sanz Rodríguez's method rather than from the GPL implementations that ship in RawTherapee and darktable. Four steps: a chroma-immune 7-tap roughness measure per axis whose vertical/horizontal ratio becomes a soft blend weight; green at R/B sites by transporting each green neighbour to the centre through the centre channel's own half-step ratio (the ratio correction — exact on a flat field and on a linear ramp, and incapable of overshooting a step edge); the opposite chroma on the two diagonals; then red and blue at green sites from all four orthogonal neighbours. Both chroma steps are bounded to the range their own contributing samples span, because the unbounded colour-difference form extrapolates across a hard edge into a near-zero-green patch. Bands of 64 output rows run over rayon against the shared read-only CFA plane, so there is no tile fill and no seam risk; the outer 6-px ring the stencil cannot reach takes the bilinear reconstruction, as does any frame under 13 px per side.

**VNG4** (`demosaic/vng4/`, #3413) is the smooth counterpart, a four-direction variable-number-of-gradients kernel written from Chang, Cheung and Pan's published description (SPIE 3650, 1999). Per site it measures a roughness along each of N/E/S/W as a sum of absolute differences between same-colour sample pairs, keeps every direction scoring at or under `K1·gmin + K2·(gmax − gmin)`, and averages only those directions' gradient-corrected green estimates. In a flat region all four qualify, so green is the mean of four independent estimates and chroma the unweighted mean of four colour differences — the noise reduction a detail-first kernel cannot offer, because committing to one direction is the whole point of those kernels. Chroma completion is shared with LMMSE (`demosaic/chroma_diff.rs`) and is deliberately unweighted for the same reason.

**LMMSE** (`demosaic/lmmse/`, #3413) is the high-ISO kernel, written from Zhang and Wu's published description (IEEE TIP 14(12), 2005). It is the only kernel here with an explicit noise model. Along any single row the Bayer samples alternate between green and _one_ chroma colour, so `G − C` is well defined at every site; the same holds down any column, giving two "primary difference signal" planes. Over a 9-tap window along each direction the total variance of that signal is split into signal and noise — the noise part estimated from the mean squared second difference divided by 6, which is exactly its variance for white noise, so no separate filtered plane is needed — and the estimate is the classic shrinkage `μ + var_x/(var_x + var_n)·(d − μ)`. The two directional estimates fuse weighted by the inverse of their own mean-square errors. On clean data the gain is 1 and the signal passes through untouched; as noise takes over the reconstruction relaxes toward the local mean instead of tracking read noise.

**Dual** (`demosaic/dual/`, #3413) runs a detail-first kernel and VNG4 and cross-fades them per pixel. The mask (`dual/weight.rs`) is the gradient magnitude of the _smooth_ kernel's green plane divided by its local mean, smoothstepped between `CONTRAST_THRESHOLD` (0.03) and `EDGE_RATIO`× that. Relative rather than absolute contrast, so one threshold constant holds across every fixture: a bright sky and a dim sky are equally flat, and an absolute threshold would route highlights to the detail kernel and shadows to the smooth one purely on exposure. The smooth kernel's green is what the mask reads because green is sampled on a quincunx — a gradient operator on the raw plane alternates between measured and missing sites and reports a checkerboard. A 3×3 dilation runs before the 3×3 smooth, and is not optional: a gradient operator reports a hard edge on a two-pixel-wide ridge, and smoothing that directly would average a weight of 1 with two zero neighbours and hand a third of the sharpest edge in the frame to the smooth kernel.

Only the detail-first reconstruction is materialised full-frame — it is also the output buffer. VNG4 is rendered one 64-row band at a time into per-task scratch, reading the shared CFA plane directly, and blended in place. The obvious implementation instead holds two full-frame `[f32; 3]` planes, which on the 100 MP reference is 1.2 GB _twice_ on top of everything the develop chain already holds — the same peak that jetsam-killed iOS on large RAWs before #1637.

Cancellation is cooperative: `CancelToken` is threaded into demosaic, BM3D, capture sharpening, sharpen and both NR stages, and checked between the heavy stages, so a superseded cold open unwinds mid-stage instead of finishing an 8-second denoise nobody wants.

Global sharpening radius is measured in developed-frame pixels. Reduced previews convert it using the carried output-pixel density before constructing the Gaussian kernel, with the existing 0.5–3 pixel kernel clamp. Native detail stays at density 1; cropping does not change density. CPU develop, both CPU live-buffer formats, and GPU full/live composition use this conversion. The ABI retains the `nr_sampling_scale` name for the density already used by chroma NR. Local-mask sharpening retains its separate fixed-radius contract. The isolated evidence in `windows-sharpen-order313.json` demonstrates the resolution mismatch; it is not a replacement for the production display-parity gate.

### Capture-first: the capture and creative halves (#5213)

There is one develop order for every photo. In plain terms:

1. **Capture, before white balance.** After DefaultCrop, the camera buffer moves into a fixed colour basis that depends only on how the photo was shot. The repair and cleanup stages (retouch, chroma pre-filter, BM3D deep denoise, capture sharpening) run there. The user's white balance never reaches them.
2. **Exposure anchor from the as-shot render.** Auto exposure is measured on the as-shot render of that capture result, so it no longer moves when white balance moves.
3. **Creative, every render and every tick.** The capture result is mapped through the user's white balance and the camera profile, then Oklab highlight recovery and the exposure gain are applied, and the rest of the chain (stage 18 onwards) runs as before.
4. **Live equals refine.** On a host that keeps the capture decode (Apple and Windows), a fresh develop, the CPU per-tick chain and the GPU live chain all run the same creative stage over the same capture result, so a white-balance drag never re-runs denoise and the live frame agrees with the refined one by construction.

The code is `raw-core/src/pipeline/capture_first/` (`mod.rs` for the capture half, `creative.rs` for the creative half, `creative_plan.rs` and `transport.rs` for the per-tick GPU and FFI forms, `export.rs` for the capture decode). Full and sized develop share both halves through `pipeline/develop/colour.rs`, and the tile chain through `pipeline/tile/colour.rs`.

#### The capture basis

The basis is `dcp::camera_to_rec2020_matrix` of the as-shot render profile (`color/dcp.rs`): the profile's linear camera → ProPhoto D50 core (the ForwardMatrix path, or the ColorMatrix path when the profile has no ForwardMatrix or its white balance was not pre-applied, as for 8-bit lossy LinearRaw), followed by ProPhoto → Rec.2020. It deliberately leaves out everything non-linear in the DCP: no HueSatMap, no LookTable and no soft floor. Values in the basis are therefore signed: an out-of-gamut camera colour arrives with negative channels, and a dark frame can have negative luma.

When no capture stage is engaged (`capture_first::engages_capture_stage`, at the thresholds the stages themselves early-return on), `capture` skips the basis and hands the camera buffer straight to the creative half. The creative half then sees exactly the camera buffer it would have seen with no capture half at all, so a photo with no capture control set renders as the plain camera WB → DCP → recovery → exposure order. The capture decode (`export_capture`) and the capture tile (`capture_in_basis`) always move their result into the basis, engaged or not, because the per-tick creative stage always starts from it (`export.rs`).

#### Guards on signed input

The capture stages see signed values, so each is guarded for them. The basis, retouch, chroma pre-filter and BM3D guards were added for the signed basis; capture sharpening's predates it and already covered negative luma:

| Stage              | Guard                                                                                                                                                           | Code                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| Basis              | A singular basis is refused before any capture stage runs, not after seconds of denoise; the capture decode refuses it too, since the creative stage inverts it | `capture_first/mod.rs`, `export.rs` |
| Retouch (heal)     | The heal floor follows the destination down when it is already negative, instead of clamping at zero                                                            | `stages/retouch/patch.rs`           |

| Capture sharpening | Pixels whose luma is below `1e-6`, including every negative-luma pixel, are left untouched by the Richardson–Lucy ratio                                         | `stages/capture_sharpening.rs`      |

`capture_first/tests_signed.rs` pins all four stages on signed, out-of-gamut input: every output stays finite, a uniform out-of-gamut field is a fixed point of every stage, the pre-filter keeps luma and only removes chroma, a clone spot copies signed values unchanged, and BM3D still engages on a frame whose median is negative.

#### The exposure anchor

Auto exposure keeps its hybrid anchor (`stages/auto_exposure/`), but the image it is measured on is always the **as-shot render of the capture result**: the capture result through the as-shot DCP (HueSatMap, LookTable, soft floor) and Oklab highlight recovery, before any user white balance. In full and sized develop (`CreativeAnchors::Measure`) the creative stage measures it directly on its own scene when the white balance is at as-shot, and through `as_shot_anchor_gain` when it is not; that function renders the as-shot image a slab of about one million pixels at a time and keeps only luma, so no second full-size image is allocated. The uncalibrated tiers apply their fallback white balance after auto exposure, so their anchor is the as-shot render as well. The capture decode measures the same anchor once (`export_capture`) and carries it as `ae_gain`; tiles and per-tick renders take it as given (`CreativeAnchors::Given`) and never re-measure. Moving white balance therefore never changes exposure. The Whites anchor (`whites_anchor_ev`, above) is separate and is measured on the as-shot camera buffer before the capture stages.

#### The creative stage

`CreativeStage` (`capture_first/creative.rs`) holds the as-shot render profile, the camera-space slider frame (absent for the LinearRaw and `RawlerFallback` tiers), the as-shot neutral and the exposure anchors. Its CPU form, `CreativeStage::render`, runs the following (`CreativeStage::render_basis` is the same function over a buffer in the basis, exposed as the GPU gates' oracle):

1. the inverse basis, back to camera RGB (skipped when the capture half skipped the basis);
2. the user's camera-space white balance (`wb_camera::apply`, or `apply_delta` against a decoded pair) and the ForwardMatrix re-interpolated at the target (`retargeted_render_profile`);
3. `dcp::apply_colorimetry`: camera → ProPhoto D50, the target HueSatMap, then the LookTable, then ProPhoto → Rec.2020, then the soft floor;
4. post-DCP Oklab highlight recovery (`highlight_recovery_oklab::apply_post_dcp`), testing the pre-exposure ceiling;
5. the exposure gain;
6. for the uncalibrated tiers only, the post-DCP CAT16 white balance (`white_balance::apply`).

The per-tick GPU form folds steps 1–3 into `T_to_pro = M_target · diag(g_wb) · M_fixed⁻¹` followed by the same tables, Rec.2020 and soft floor, then recovery, then `ae_gain · W_post` (see "The creative stage (#5376)" under [the GPU path](#the-gpu-path)). The tables and the clip test must see pre-exposure values, so the gain is always applied last.

### Oklab secondary colour curves (Stage 22b, #5041)

`stages/color_curves.rs` runs in scene-linear Rec.2020 immediately after the 8-band `hsl` stage and before `clarity`, working in Oklab. It evaluates six curves, each a `papp:ColorCurve*` point list in `[0, 1]` where `y = 0.5` is neutral and an empty list is identity: **Hue vs Hue** (rotates hue by up to ±60°), **Hue vs Sat** (chroma ×0–2), **Hue vs Luma** (L ×0.7–1.3), **Luma vs Sat** (over a scene-referred log-EV lightness axis), **Sat vs Sat** and **Sat vs Luma** (over normalised chroma `C / 0.32`). Hue curves are periodic splines (Fritsch–Carlson Hermite), the others clamped; the Hue vs Hue editor limits the slope between adjacent knots so the hue map cannot fold. The stage reuses `hsl`'s neutral-axis chroma gate (`C < 0.05` returns the pixel bit-for-bit, smooth ramp to `0.10`) and bounds out-of-gamut results with the same Rec.2020 hull bisection and soft knee. Six empty curves skip the stage entirely, so an unedited image is unchanged. The GPU twin is `raw-gpu/src/color_curves.wgsl` (baked 256-sample tables, parity-gated within 1e-4 against `raw-core`, neutral bit-exact).

CPU and GPU hosts compile the same dependency-free 256-sample spline baker from `stages/color_curve_lut.rs`. Per-thread scratch and the GPU point-key cache reuse their storage when knots move, are inserted or are removed; larger imported curves retain their full point lists and warm their required capacity once. Changing-point allocation witnesses cover both periodic and clamped curves, including imported lists beyond the editor's authoring bound.

The editors' eyedropper does not read the screen: it asks `raw-core` (`stages/color_curve_sample.rs`, exposed as `maple_sample_color_curve_oriented` in `raw-ffi` and `sample_color_curve_from_bytes` in `raw-wasm`) for the 5×5 neighbourhood mean at the point `stages::color_curves` itself receives (after white balance, exposure, tone curves, vibrance, saturation and HSL, before AgX), returned as the curve-domain coordinates `(u_h, u_c, u_l)`. Display coordinates are mapped back to the sensor frame for the file's EXIF orientation, checked against the orientation matrix for all eight tags.

### Colour management

**DCP profiles.** `color/dcp.rs` builds a `DcpProfile` — a camera→XYZ `ColorMatrix` at the scene illuminant, an optional `ForwardMatrix` (white-balanced camera RGB → XYZ-D50 per the DNG SDK, _not_ XYZ→ProPhoto), the scene white point, and an optional HueSatMap. Dual-illuminant profiles interpolate CM, FM and HSM together by reciprocal CCT (`interpolated_profile`). Apply runs CM/FM chromatic adaptation plus HSM metameric correction in linear ProPhoto D50, then converts to Rec.2020. Adobe's aesthetic layers — `ProfileToneCurve` and `ProfileLookTable` — deliberately do **not** run: they were calibrated under Adobe's tone mapping and stacking them on AgX produced compound hue errors.

**HueSatMap interpolation (#4631).** The HSM lookup interpolates hue, saturation and value independently (trilinear, as the DNG SDK's `RefBaselineHueSatMap` does), including two-dimensional maps with a single value slice. The shared CPU prefix supplies it to full, sized, tile and GPU preparation.

**Dehaze transmission (#4654).** Positive dehaze keeps the dark-channel estimate's pointwise bound after guided refinement: `t >= clamp(1 - omega * min(I / max(A, floor)), 0, 1)` with the existing `omega = 0.95` and airlight floor, so refinement can no longer reconstruct negative radiance from positive observations. It constrains the transmission, never the scene RGB, which stays signed and unbounded; unit transmission returns the input bits unchanged. Negative dehaze keeps its forward haze model. CPU and WGSL share the constants through generated `color_matrices.wgsl`, with no extra pass or scratch buffer.

**Dehaze haze map (#3287).** Dehaze is measured once per frame, at one fixed resolution, and then applied anywhere. The frame-global half — atmospheric light `A`, the 15×15 dark channel, the dark-channel transmission, its radius-60 guided-filter refinement and the radius-8 sky mask — is computed on a proxy grid whose long edge is `HAZE_PROXY_LONG_EDGE = 2048` (`stages/dehaze_map.rs`): the frame is block-averaged onto it (a smaller frame is sampled nearest), and every window radius is in proxy texels. The result is a `HazeMap`: `A`, the guided filter's box-filtered coefficients `(mean_a, mean_b)` and the sky mask. Recovery is then a point operation: each rendered pixel samples the coefficients and the mask bilinearly at its place in the frame and rebuilds its transmission from its own luma, `t = a · (luma − luma(A)) + b` (He & Sun's fast guided filter, so edges stay at render resolution). Because the windows are a fixed fraction of the frame, a fit preview, a 100 MP export and a 100% tile see the same dehaze; 2048 is the resolution a fit preview on a Retina laptop or iPad already rendered dehaze at, which bounds the map at ~34 MB resident (a few hundred MB transient) on any sensor. The map depends only on the pixels dehaze receives, never on the amount. The guide is centred on `luma(A)` because hazy pixels sit near `A`, where an uncentred `mean(I²) − mean(I)²` cancels in f32 and `cov / eps` amplifies it; centring keeps the CPU and WGSL coefficients within 1e-5 of each other. Where the map comes from: a whole-frame render (sized preview, the per-tick chain, the GPU live chain) measures it from its own dehaze input; a native-density RAW develop (`develop/mod.rs`, export) and a native tile both measure it from the same Preview-density develop sized to the proxy grid (`develop_sized::haze_map_from_raw`, the #5049 pattern for the highlight prior), so export and tile agree bit for bit; and a native-detail window is handed the frame's map (`ChainOptions::haze_map`, `FrameHaze`), measured by running the chain up to dehaze on the host's whole decoded frame at the resolution the whole-image chain renders it (`scene_linear_chain_haze_map`) — tone curves, clarity and texture do not commute with a downsample, so only that buffer measures the displayed frame's maps. A sized preview's own map and the Preview-density one can differ by about a code where a 100% patch meets the base beneath it. The per-mask dehaze control (#3407) measures its own map from its layer's scratch the same way, and a window receives those per-layer maps alongside the global one. This was a one-time look change on existing dehaze edits, accepted with option A of #3287.

**Scene chroma continuity (#4664).** Saturation, vibrance, HSL and the local hue control return an uncompressed target only when the start of their soft knee (`c_target / 0.8`) is still inside the nonnegative Rec.2020 cone, and use that known-outside probe as the hull search's upper bracket, so chroma no longer steps when a target first leaves gamut. HSL and local hue, which have no input-chroma floor, also limit the knee span by the input chroma plus the edit's Oklab distance, so a tiny edit (or a mask-edge weight near zero) leaves a near-hull colour where it was. CPU, global WGSL and the masked kernels share the same math.

`profile_for_with_source` resolves in tiers, reported as a `ProfileSource`: `EmbeddedFull` (the DNG ships CM + FM + HSM — an internally consistent vendor triad, used whole), `BundleConfident` (a byte-exact `UniqueCameraModel` hit in Maple's bundled table), `EmbeddedCmOnly`, and `RawlerFallback` (no calibration for this body — synthesises an XYZ-D65→Rec.2020 matrix, which is visibly imperfect but bounded, and is logged once per model).

The bundle is `raw-core/src/color/profiles/profiles.bin`, embedded with `include_bytes!` and read by `color/profile_loader/`. Coverage is tracked in the sibling `COVERAGE.md`. The format has an inline v1 layout and a v3 split layout that dedups HueSatMap tables into a zlib-compressed pool with an offset directory (matrices alone are ~210 KB for ~1,459 profiles; with HSM inline the bundle balloons to tens of megabytes). `maple-cli transcode-dcp` repacks v1 → v3.

**White balance.** Temperature/tint are applied in camera-native linear RGB _upstream_ of DCP (`stages/wb_camera.rs`), matching ACR: the gain is `as_shot_neutral[c] / target_neutral_camera[c]`, a purely diagonal per-channel scale bounded by what the sensor can physically report. When user WB moves off as-shot, `retargeted_render_profile` re-interpolates only the ForwardMatrix at the target's CCT; the Bradford source stays at the true as-shot chromaticity. The slider _frame_ (`wb_camera::SliderFrame`) prefers the DNG's own embedded calibration when present, because that is the scale ACR's displayed numbers are defined in. Two paths fall back to the older post-DCP CAT16 matrix in scene-linear Rec.2020 (`stages/white_balance.rs`): LinearRaw sources and `RawlerFallback` bodies. `WbMethod` selects `Cat16` (default) or the legacy `DiagonalRec2020`. Sidecars carry a `WbScaleVersion` stamp so values authored under an older tint scale are converted on load rather than silently reinterpreted.

**Highlight recovery.** `HighlightRecoveryMode` defaults to `ChromaticAdaptation`, which runs pre-DCP in camera RGB where the per-channel ceiling after baseline exposure and WB pre-gain is `2^BaselineExposure / AsShotNeutral[c]` rather than 1.0. The clipping tolerance receives the same baseline-exposure gain as the pixels and ceilings; otherwise sufficiently negative exposure makes even black look clipped. `OklabChromaReduction` is an opt-in variant that instead runs post-DCP in scene-linear Rec.2020, scaling Oklab `a`/`b` by a common factor so hue is preserved by construction. `Blend` and `Luminance` are legacy XMP values silently upgraded to `ChromaticAdaptation`.

### Auto exposure, Auto Profile, Auto Adjustments

Three separate things share the word "auto":

- **Auto exposure** (`stages/auto_exposure/`) is a per-image scene anchor, on by default, inside the develop chain. It measures the geometric mean of luma over the middle 50 % percentile band plus the 95th percentile, takes the larger of `0.18/midgrey` and `0.85/p95` capped at 8× (+3 EV), and multiplies. Its purpose is to land every camera at the same point on the AgX sigmoid. User exposure stacks additively in EV downstream, and `papp:AutoExposure="Off"` makes the stage a bit-identical no-op.

- **Auto Profile** (`view/auto_profile/`) is a per-image _view_ tail selected by `papp:Profile="Auto"`: extract the camera's embedded JPEG preview and fit the structured tonescale + hue/chroma-field solver against it (`view/acr_fit/`, Auto 2.0 — the default since the #1740 M2 flip; `MAPLE_AUTO1=1` restores the Auto 1.0 curve + free residual LUT as a dev-only escape hatch), baked into the same (curve, residual-LUT) artifacts the CPU/GPU samplers consume. It layers on top of AgX rather than replacing it. When a fit is predicted to succeed, the render pins auto-exposure Off so the fitted curve owns the whole scene→JPEG brightness relationship. Hosts with an explicitly sized decode can request `fit_auto_profile_from_raw_at_cap` with `FitCap::Render(edge)` to obtain the native sized renderer's calibration, including its original embedded-JPEG target and `Render(size)` cache provenance (#4132). This is a one-shot fit using the default AE-off model, independent of live edits; it does not change the existing hosts' decode policy. Only a default-model sRGB render fits from its own buffer. Edited, film-look and Display P3 renders fit from a separate pinned sRGB develop, so a P3 export can't seed the cache an sRGB render or thumbnail of the same file reads, and a default-model P3 render applies that tail exactly as the sRGB render does (#4741, #4640). The standalone fit the GPU-live, LUT-bake and WASM hosts call (`fit_auto_profile_from_raw`) always develops a 1536 px proxy and downsamples the embedded JPEG to match (#3510): the ACR solver walks the (developed, JPEG) pair set several times single-threaded, and against a full 24–30 MP embedded JPEG that was 10–22 s per cold open — the pair set carries only the joint tone distribution, so the proxy is parity-neutral (per-fixture ΔE on #3510). Results are cached in a bounded LRU keyed on `(raw identity, mtime, quality, fit origin)` (mtime applies to path keys; fit origin distinguishes standalone, render-size and curve-only producers; the cache lives only for the process, so no fit-model version is needed, #5162); a post-LUT Oklab gamut guard runs after it so the terminal quantizer cannot hard-clip a pushed colour. M3 identifies the fit's white-balance component for shell surfacing: `acr_fit::wb::estimate_illuminant_gains` reads the JPEG's global cast from the same display pairs as green-normalised ±2-stop gains plus the ACR temperature/tint reading of that white (DNG Robertson path, schema-domain clamped), decaying to exact D65 identity whenever its count/spread/rail gates fail — shells display the offset only when `confident` is true, and the profile switch to Neutral remains the undo. The estimate is measurement-only (no render-path caller; `maple-cli fit-auto2` prints it as `wb_offset` JSON), so it cannot move pixels; the future pre-fit illuminant alignment (#1688, folded into M3) consumes these same gains before the tonescale/field fit, harness-gated.
- **Auto Adjustments** (`stages/auto_adjustments.rs`) is a one-shot recommendation for all eight tone/WB sliders, derived from one probe develop with auto-exposure off and WB pinned to D65. Its `exposure` output _replaces_ the anchor, so a caller writing it back must also set `papp:AutoExposure="Off"`. The white-balance half (`stages/auto_adjustments_awb.rs`, #2247) maps each probe pixel back to post-gain camera RGB through the inverse of the chain's own render matrix, drops anything at a sensor clip ceiling (`2^BaselineExposure · pre_gain · wb_gain` per channel), re-centres its chroma gate on the running estimate (seeded from where a neutral surface under the camera's as-shot reading lands in the probe — the as-shot gain on a calibrated body, plain neutral in the post-DCP tier), blends gray-world and white-patch as G-normalised chromaticities, and solves the result in the DNG slider frame — the same Robertson path `dcp::estimate_as_shot_cct_tint` uses — so a develop at the recommendation neutralises the population it was measured on. Its CI gate is the fixture-tier agreement with the as-shot reading plus idempotence on its own recommendation.

**Auto is the shipped default, by design (settled 2026-09-04, CLAUDE.md principle 8).** Neutral's flatness is AgX's headroom working as intended; Auto restores the colour and contrast the photographer expects by fitting the camera's embedded preview. Neutral is a selectable mode, not the default. Auto vs Neutral measures grand mean ΔE2000 5.98 across the fixture set, and the server's `thumb`/`preview` stages fit the same embedded JPEG, so the default keeps the grid thumbnail and the full view in agreement.

### The view transform and output

After develop, `pipeline/render/mod.rs` runs the display tail:

1. **AgX** (`view/agx.rs`) — inset matrix → ratio-preserving sigmoid below common diffuse white; when every inset RGB channel exceeds 1.0, a smooth common-highlight roll-off converges toward the neutral shoulder while preserving channel-difference ratios (#4635) → outset matrix → hue-preserving Oklab gamut compression into `[0,1]³`. The sigmoid is a baked 512-entry `f32` LUT (`view/agx_lut.bin`); the coefficients and matrices in `view/agx_coeffs.rs` are derived by `src/scripts/derive_agx_lut.py`. Output space is display-linear Rec.2020. `model.contrast` modulates the sigmoid slope about mid-grey. `model.whites` (`view/agx_whites.rs`, #3601) remaps the normalised log coordinate between the log encode and the contrast slope: positive applies an image-scaled bump displacement, while negative applies a rising compression weight that reaches midtones and preserves deep shadows — replacing the old scene-linear whites gain, which barely moved pixels because post-DCP scene-linear content sits mostly below the midpoint that gain measured against.
2. **`color_grade`** (`stages/color_grade.rs`) — three-zone (shadow/midtone/highlight) plus global hue+saturation and per-zone lightness offsets, in display-linear Oklab, with the zone axis being Oklab `L` and the balance slider warping that axis. The zone weights are three smoothstep windows whose four edges `[s0, s1, h0, h1]` come from `zone_edges(blending, shadow_edge, highlight_edge)` (#5040): `papp:ColorGradeBlending` (0–100, default 100) widens or narrows the ramps, and the shadow and highlight pivots (`papp:ColorGradeShadowEdge` 0.10–0.564622, `papp:ColorGradeHighlightEdge` 0.564622–0.90) move where each zone stops. At the defaults the edges are exactly `[0, 0.564622, 0.564622, 1]`, so an unedited image renders bit-identically. The strip each editor draws is checked against the same goldens as the stage (`color_grade_tests.rs`, `color-grading-panel.spec.ts`, `ColorGradeZoneWeightsTests.cs`).
3. **`film_look`** (`stages/film_look.rs`) — an optional baked `.mlut` film-print LUT, sampled tetrahedrally in the encoded-sRGB lattice domain and blended back by strength. The pack lives at `resources/film-luts/` and the 100-entry catalog is `raw-core/src/film_catalog.rs`; the codec is `raw-core/src/film.rs`. A host that cannot resolve the asset passes `None` and gets a bit-identical no-look render.
4. **`grain`** (`stages/grain.rs`) — display-linear, so its amplitude does not swing with exposure.
5. **`rec2020_to_display`** (`view/encode.rs`) — the primaries matrix, `TargetPrimaries::Srgb` (0) or `P3` (1), with Oklab soft gamut compression (`color/oklab_gamut.rs`) rather than a hard clip.
6. **`srgb_gamma_encode`** — IEC 61966-2-1 transfer function, identical for both primaries.
7. **Auto Profile curve + residual LUT + gamut guard**, when the profile is `Auto`.
8. **Quantize** — `encode::dither_and_quantize` (8-bit) or `view/quantize16.rs` (16-bit for TIFF masters, quantized straight off f32 rather than promoted from 8-bit). Both add ±0.5 LSB of deterministic 64×64 blue-noise jitter (`view/dither.rs`, void-and-cluster, zero DC bias) so smooth gradients read as fine noise instead of contour bands.
9. **Geometry tail** — `pipeline/render/finish.rs` applies EXIF orientation, then the manual-geometry homography, then the user crop, depth-generically, so the canvas render and the export master frame identically.

The manual-geometry stage (`stages/perspective`, #3410) composes Adobe's seven `crs:Perspective*` scalars — vertical and horizontal keystone, rotation, scale, area-preserving aspect stretch, and X/Y offset — into ONE 3×3 homography and applies it in ONE bilinear resample, sharing `stages::crop`'s sampler so the two geometry stages cannot disagree about the out-of-bounds fill or the narrowing round. It works in centred, half-extent-normalized coordinates (`[-1, 1]` with `y` down), which is what makes every slider resolution-independent and lets the same matrix serve the CPU tail and the WGSL present shader; only the rotation factor re-introduces the pixel aspect ratio, conjugated by `diag(ar, 1)` so it stays circular on a non-square frame. Composition order is `T · S · A · R · P` — keystone about the centre, then rotation, then the aspect stretch, then uniform scale, then the offset — and the three constants that pin what one slider unit buys (`KEYSTONE_MAX`, `ASPECT_MAX_RATIO`, `OFFSET_MAX`) live in `stages/perspective/matrix.rs`, because Adobe does not document its own mapping. Every field at its default composes to the exact identity matrix, which the stage short-circuits before any allocation, so an image with untouched geometry renders bit-identically to a build without the stage. Output dimensions are unchanged: pixels pulled from outside the source render black, as Adobe renders them, and the user frames them out with the crop that runs immediately after — auto-constrain is deliberately not part of this stage.

Orientation runs first because the sliders are authored against what the photographer sees, not against sensor framing; the crop runs last because the crop rect is how the surround gets framed out, so it has to be able to see it.

`render_display_scene` is the shared body; `render_display_from_raw` finishes at 8 bits and `pipeline/render/export.rs` finishes at `ExportDepth::Eight` or `Sixteen`. `raw-core/src/export.rs` encodes the result to JPEG/PNG/TIFF and tags every file with a real ICC profile written by `raw-core/src/icc.rs` — an untagged Display P3 file would be re-stretched as sRGB by every viewer, so tagging is what makes the P3 option mean anything.

The recipe byte dispatcher also accepts ordinary JPEG and TIFF sources (#3891). `pipeline/render/export/raster.rs` decodes without an 8-bit intermediate, transforms embedded RGB ICC profiles to linear Rec.2020 through the vendored `moxcms` engine (untagged inputs assume sRGB), and runs the existing non-RAW chain with `skip_agx`. It then shares the RAW export's terminal quantization, orientation/crop, encoders and output ICC tagging. CMYK, transparency, invalid input profiles and unsupported authored stages fail before output creation. In particular, nonzero Contrast/Whites require the AgX path and are rejected; RAW decode stages, imported lens profiles and repair/removal layers are also rejected rather than silently omitted. Windows uses the same oriented, color-managed base for JPEG/TIFF CPU and GPU editor rendering, with AgX and camera-profile fitting bypassed. The shared native thumbnail entry points also decode ordinary JPEG/TIFF sources for Browse/Preview and the filmstrip; RAW-in-TIFF retains camera-preview extraction. Unsupported raster settings fail shared validation, and the inspector disables RAW-only Contrast, Whites and capture-sharpening controls. Synthetic native tests cover previews, thumbnails, queue cancellation/resume and frozen export edits. Native raster detail, broader queue/share interaction, reference-color and performance qualification remain required before #3891 is complete.

### The per-tick chain

**Stage 27 carries two groups.** A local-adjustment layer's eleven POINT controls are per-pixel operators scaled by the mask weight, evaluated in one pass over the buffer. Its six SPATIAL controls (#3407 — texture, clarity, dehaze, sharpness, luminance noise, defringe) read a neighbourhood, so there is no weighted per-pixel form: `stages/local_adjustments/spatial.rs` runs the GLOBAL stage's own kernel over a scratch copy of that layer's output at the layer's slider value and lerps the result back by the mask weight (`out = base + w · (stage(base) − base)`). At `w = 1` that is bit-for-bit the global stage; at `w = 0` it is identity, and a layer that engages none of the six never allocates the scratch. `stages/defringe.rs` serves this group AND stage 26 above (#3411 added the global ACR controls): ONE kernel, whose parameters are a superset — the per-mask caller passes a single hue-agnostic amount, the global caller two hue-banded ones, and a pixel takes the strongest claim on it. With no band engaged the kernel never evaluates a hue, so the per-mask path is bit-identical to the single-amount stage it replaced. On the GPU the same structure is a per-layer split: when some layer engages the group, `raw-gpu`'s live chain emits one pass per layer instead of the fused single dispatch, and the engaged layer's pass drives the shipping clarity / texture / dehaze / sharpen / NLM / defringe kernels over scratch before blending by the weight `local_adjustments.wgsl` already writes into alpha for the vectorscope.

**Stage 27 and EXIF orientation.** Mask geometry is normalised over the upright, EXIF-oriented image, but the develop, sized-develop and tile chains run on SENSOR-framed buffers and orient only in the finish tail, so they remap every layer and raster into the sensor frame first (`pipeline/mask`, #4426). The GPU kernel instead reads each pixel's mask at its upright position, from `FullChainInputs::mask_orientation` (#4479). The Linux preview and the Web one-shot GPU render are sensor-framed and orient after the chain, so they pass the RAW's tag. Apple and Windows upload an already-oriented decode and pass 1. The Web live session passes the RAW tag and composes EXIF orientation with perspective at present time; the canvas shows the cropped upright frame, while masks and native dimensions stay on the uncropped upright frame.

`pipeline/scene_linear_chain.rs` is what the editor actually calls on a slider tick when the GPU path is unavailable. It takes an already-decoded fp16 or f32 RGBA scene-linear Rec.2020 buffer and re-applies only the model-dependent stages: `white_balance::apply_delta` → `scene_tone_controls` → `tone_curves` → `vibrance` → `saturation` → `hsl` → `clarity` → `texture` → `dehaze` → `defringe` → `local_adjustments` → `vignette` → `sharpen` → `nr_luminance` → `nr_color` → `agx` → `color_grade` → `grain` → display encode. White balance is applied as a _delta_ against the temperature/tint the buffer was decoded at (carried in `ChainOptions`), so opening a saved sidecar does not double-apply WB; when the decode exported a `SliderFrameExport`, the delta is derived in that same camera-calibration frame, which is what closes the live-vs-refine seam. On a ForwardMatrix profile with two HueSatMaps the develop also re-lerps the HueSatMap at the white-balance target (#4633), which no 3×3 can express, so the decode exports both tables too (`wb_camera::WbHsmRetarget`) and the delta becomes `R · H_T(M · H_A⁻¹(R⁻¹ · b))` in linear ProPhoto: undo the anchor's table by a four-step inverse solved in HSV, apply the camera-gain delta, apply the target's table, and soft-floor as the DCP exit does (#5099, `stages/wb_hsm_retarget.rs`). The decode's auto-exposure gain is divided out before the tables and restored after, because the develop applied them before auto exposure. Bodies whose table never moves keep the plain 3×3, and so does a profile carrying a LookTable, which this delta does not model. This delta serves only hosts still on the scene-linear decode (Android/Linux; see [the legacy live retarget](#the-legacy-live-retarget)); over the capture decode the chain runs the creative stage instead and none of it applies (#5377). `ChainOptions::skip_agx` turns off the whole display tail for non-RAW inputs (a JPEG/HEIF already carries a baked tone curve).

This chain is both the CPU oracle for the GPU live chain and its no-GPU fallback, which is why it runs `sharpen` and `nr_color` even though they are the expensive pair — the GPU path is the one held to the 16 ms tick budget.

### Sized and tile renders

`develop_sized` inserts `downsample_image_area` after baseline exposure, as-shot WB, highlight recovery, OpcodeList3 and DefaultCrop. Highlight recovery therefore sees sensor clipping before lens gain or interpolation changes it (#3633); user WB, DCP and later stages run on the viewport-sized buffer. Full-image and panorama preparation use the same ordering. These preparation stages are shared CPU code before the GPU live chain receives its decode product. Profile labels are prefixed `sized_` so traces do not collide with the full-res ones.

Despite its legacy name, `downsample_image_area` uses separable Mitchell-Netravali filtering (B=C=1/3), with scale-expanded support, normalized weights and clamped borders. It is not a box average. Noise-variance estimates based only on the output/input pixel-area ratio do not model this kernel; demosaic correlation must also be considered before using such estimates for production noise reduction.

`pipeline/tile/` linearizes only a padded crop region and runs a stripped develop chain on it, then trims the overlap and packs oriented fp16/f32 RGBA. Auto-exposure is never recomputed per tile (a tile's histogram is not the scene's) — the caller threads in the gain the full-image develop measured. `TILE_OVERLAP_PX` is pinned by a const-assert to clarity's guided-filter reach (`2 × CLARITY_GUIDED_RADIUS`); the pad grows per render to the stencils the model engages (see [zoom](zoom.md)), dehaze recovers from the frame's proxy haze map (#3287), and the stages with no tile form yet — deep denoise, unsupported opcode mappings — are rejected loudly at the entry rather than rendered wrong. `retouch` (#3409) is rejected per SPOT rather than per model: a repair spot reads a whole neighbourhood and its source can sit anywhere in the frame, so a tile holding a spot's destination but not its whole footprint refuses; a tile no spot reaches renders normally. See [zoom](zoom.md).

## The GPU path

`raw-gpu` is a headless wgpu 23 crate: a `GpuContext` (device, queue, lazily-compiled pipeline cache), a `GpuImage` uploaded **once**, and a `ChainRunner` that executes an ordered `Vec<Box<dyn Pass>>` by ping-ponging two scratch buffers with exactly one readback for the whole chain and cooperative cancellation. Every buffer is f32 RGBA; fp16 exists only at the FFI transport boundary (`pipeline/fp16.rs` packs and unpacks it, and `pipeline::finite_or_zero` scrubs NaN/Inf at the pack endcaps because sampling NaN in a GPU texture is implementation-defined).

Ported stages, each parity-gated directly against its `raw-core` function rather than a hand-copied oracle: capture sharpening, white balance (plus its retargeted-HueSatMap variant `white_balance_hsm.wgsl`, #5099: the two endpoint tables are a session-constant storage buffer and a tick only rewrites the uniform), scene tone controls, tone curves, vibrance, saturation, HSL, clarity, texture, dehaze, defringe, local adjustments, vignette, sharpen, NLM luma, NLM colour, colour grade, film LUT, grain, AgX, display encode, sRGB gamma, Auto Profile curve, residual LUT, and the terminal dither. Auto exposure stays on the CPU. Spatial stages (clarity/texture/dehaze/NLM/sharpen/capture sharpening) stay a single `Pass` each but orchestrate a small DAG or a dispatch loop over scratch planes via the shared `spatial.rs` primitives, because the WGSL downlevel baseline allows only four storage buffers per kernel. `local_adjustments` sits AT that same ceiling too (#3271): a `Mask::Bitmap` layer's raster pixels ride a fourth storage buffer (the concatenated "mask plane", alongside the src/dst/layer-stack buffers), leaving no headroom for a fifth.

Capture sharpening is the one ported stage in the live and full chains that does not run per tick on any shipping front end. It sits in develop's capture stage (9d), upstream of everything the live chain owns, so Apple, web and Windows all bake it into the DECODE PRODUCT and pass `capture_sharpening_enabled = 0` / `capture_sharpening: None` to the chain; moving either `captureSharpeningAmount` or `captureSharpeningSigma` invalidates that product and re-develops once, on gesture release. `CaptureSharpeningPass` is what runs when a caller does gate it on — it is the FIRST pass in both `full_chain.rs` and `live_chain.rs` (signature bit 0), so the same WGSL kernel serves a GPU-resident decode product without a double apply. Its Richardson–Lucy loop is encoded as a per-iteration dispatch loop over scratch planes, parity-gated at `< 1e-4` directly against `apply_capture_sharpening`. The staged Android port (#4623) adds a separate 512px GPU capture preview from a zero-capture upload; its final refinement still bakes canonical capture-before-AE CPU order and disables the GPU stage for that refined image. The fast phase is an interactive approximation, with physical frame-time qualification still tracked by the parent issue.

The capture-stage refine passes (#5217) run as the capture refine (#5381, see [The capture refine](#the-capture-refine-5381)); Apple is the first host. `ChromaPrefilterPass` and `DeepDenoisePass` (two-pass BM3D) are in no live chain; `PostDcpHighlightPass` (post-DCP Oklab recovery) runs in the creative stage below. All three are parity-gated against their `raw-core` stages, including signed and HDR input. BM3D luma and match distances split every multiply-add operand into 12-bit halves (`stages/bm3d/exact.rs`), so first-pass ranking is bit-exact on every backend; on the physical `test_0007` frame at 2560 and 1536 px the gate pins first-pass groups to the CPU, second-pass groups to the GPU's own first-pass guide (that estimate cannot be bit-exact across backends), and bounds the output at mean relative error ≤ 1e-6 and p99.9 ≤ 1e-4. BM3D filters its patch cache in tiles bounded by `GpuContext::set_bm3d_binding_cap` (default 128 MiB), gathers without float or fixed-point atomics, keeps a portable path beside the validated native subgroup variants, and checks its `CancelToken` before every tile. Its latency is qualified by the ignored `capture_refine_latency_gate` against its own refine budget, never the 50 ms slider limit.

**The creative stage (#5376).** When `FullChainInputs::creative` is set the uploaded buffer is a capture result (#5213), signed and in the fixed as-shot Rec.2020 basis, and the live builder replaces the white-balance pass with the GPU twin of `CreativeStage::render`: `CreativeDcpPass` (`creative_dcp.wgsl`), then `PostDcpHighlightPass` when the model opted into Oklab recovery, then `CreativeGainPass`. Capture sharpening is left to the capture stage, so a white-balance tick encodes no capture-stage pass (`live_chain/tests_creative_chain.rs` records the pushed passes). The dispatch computes, in this order and with the exposure gain applied last so the table lookups and the clip test never see it:

1. `pro = T_to_pro · capture`, where `T_to_pro = M_target · diag(g_wb) · M_fixed⁻¹` is derived per tick on the CPU (`CreativeStage::gpu_plan`) from the target ForwardMatrix, the camera white-balance gain and the inverse as-shot basis, with no exposure gain;
2. the target HueSatMap (trilinear; at a retargeted white balance the two endpoint tables are blended per cell at the reciprocal-CCT weight, as `hsm::lerp_tables` does) and then the LookTable (tetrahedral), both in linear ProPhoto D50;
3. `pro → Rec.2020` and the soft floor, folded with step 1 into a single 3×3 when the profile has no table;
4. Oklab recovery at the unchanged pre-exposure ceiling `1 + CEILING_EPSILON`;
5. `post = ae_gain · W_post`, where `W_post` is the post-DCP white-balance matrix the uncalibrated tiers (LinearRaw, `RawlerFallback`) still use and is the identity otherwise.

Every table of the profile rides one storage buffer, built once per profile by `CreativeStage::gpu_wire` and held in a pooled data buffer whose retained snapshot skips the upload when the bytes are unchanged: `[endpoint cold | endpoint warm | LookTable]` for a dual-illuminant profile, whose as-shot HueSatMap is the two endpoints blended at the as-shot CCT exactly as `dcp::profile_for` lerps it, and `[HueSatMap | LookTable]` for a single-table one, so the wire depends on the profile and not on the photo. A dual-illuminant profile whose stored table is not that blend keeps it after the endpoints (`[cold | warm | HueSatMap | LookTable]`), so a white-balance tick rewrites the uniform and uploads no table (`live_session/tests_creative.rs` asserts zero pool allocations and zero uploads over a drag). The pass binds three storage buffers, inside the four-buffer baseline. Bits 24–26 of `active_mask` (`CREATIVE_DCP`, `POST_DCP_HIGHLIGHT`, `CREATIVE_GAIN`) follow the builder's own gates, and the wire length is folded into `chain_signature`. The creative operations are pointwise, so an oriented upload needs no orientation logic: the gate renders all eight EXIF orientations and checks both CPU parity and equivariance. The CPU oracle is `CreativeStage::render_basis`; the gate (`live_chain/tests_creative.rs`) covers signed, out-of-gamut and HDR input over every table shape (none, one table, dual linear, dual sRGB, dual plus LookTable, uncalibrated tier) and five white balances at ≤ 1e-4 relative to max(|v|, 1), and the ignored `live_chain/tests_creative_physical.rs` runs the same comparison with `test_0007`'s own profile. Hue-delta tables whose neighbouring cells differ by about 180° make the unwrap flip at a lattice line, where a pixel with a zero channel sits within one rounding of either side, so the synthetic fixture steps the hue seam by 200°. Apple (#5377), Windows (#5378) and Web (#5379) drive it through the capture decode; Android/Linux is described under [the legacy live retarget](#the-legacy-live-retarget).

`DehazePass` measures the haze map on the same 2048-texel proxy grid as the CPU stage (`dehaze_downsample.wgsl` block-averages the pre-dehaze buffer onto it; the dark channel, airlight, transmission, guided coefficients and sky mask then run at proxy size) and recovers in `dehaze_recover.wgsl`, which samples the proxy planes bilinearly with raw-core's exact f32 tap expression. In the live session (`AirlightSource::Resident`) the map stays resident across ticks: it is keyed by the frame pool's FNV digest of every pipeline, uniform and data lease encoded before dehaze (`FramePool::frame_digest`), so a dehaze-slider tick — whose prefix is byte-identical — skips the map and runs only the recovery dispatch; any upstream edit or a new source image re-measures. Measuring pools its resources in a detached frame-pool bucket per slot and proxy size, owned by the session (`FramePool::enter_detached`), outside the frame's own, so skipping it leaves every later stage on its cached bind groups and the frame digest unchanged, and a downstream stage crossing its gate (a new chain signature) keeps the map. A measured map only becomes reusable once its frame is submitted; a render cancelled after measuring, or the exposure-preparation frame that is encoded and dropped, forgets it, since its copies into the resident planes never ran. Each engaged local layer's dehaze keeps its own resident map in its own slot (slot 0 is global, slot 1+i is layer i), keyed the same way; the layer's point pass uploads its parameters with the spatial controls zeroed, so dragging that layer's dehaze amount leaves its map's digest unchanged (its texture and clarity run before its dehaze, so they re-measure). The on-GPU airlight reduction sums its selected samples in blocks of 64, because a flat sky can select ~10⁴ samples per thread on the proxy grid.

`full_chain.rs` composes the canonical chain unconditionally; `live_chain.rs` is the caller that _gates_ pass inclusion from the live `AdjustmentModel` using the same thresholds raw-core's `apply` functions early-return on, so a neutral model omits every no-op pass. The view tail always runs. `live_session.rs` holds the resident state across ticks so a slider move allocates no new GPU buffers and recompiles no pipelines. Present paths are per-platform and `#[cfg]`-gated: `CAMetalLayer` on Apple, `SwapChainPanel` on Windows, a WebGPU `OffscreenCanvas` on the web, all sharing `present_chain.wgsl` and `present_chain_pipeline.rs`.

The present shader also carries the manual-geometry warp (#3410): when a `PresentGeometry` is armed it resamples the chain buffer through the destination→source homography instead of loading a pixel straight, reproducing raw-core's _hybrid_ out-of-bounds rule exactly — a footprint fully outside the source is opaque black, one still straddling the border clamps its individual taps — because plain clamp-to-edge would leave a one-pixel bright fringe around every warped frame. The matrix is built by raw-core and carried into `raw-gpu` as three `vec4` rows plus an active flag, since the crate dependency runs the other way and a second copy of the math is exactly what would drift. It is deliberately NOT part of the `PresentDispatchCache` key — a slider drag changes it every tick, and keying on it would turn every tick into a cache miss — so the uniform is rewritten per present instead, which allocates nothing. A user crop is folded into that one homography, except an off-axis crop over active perspective: the CPU tail resamples twice there, so `PresentGeometry::from_stages` carries a second affine stage and the shader evaluates the warp at the four display pixels its footprint touches (`present_texture_tests` gates it against the CPU within 1 LSB). A zeroed flag takes the untouched pre-#3410 load paths byte for byte, and `present_chain/tests.rs` gates all three: the warp against raw-core's own f32 warp at ≤ 1 LSB, the identity case as byte-identical, and the surround as black rather than smeared.

The vectorscope scope pass (#3272, spec §4/§5.4) is a side channel off the live chain, not a `Pass`: `scope_vectorscope.wgsl` reads the chain's FINAL buffer (after the view tail, before dither) and bins it into a 128×128 Rec.709 Cb/Cr histogram with integer atomics, weighted per pixel by the alpha lane — `local_adjustments.wgsl` writes one layer's mask×range weight there instead of the untouched upload alpha when `ScopeRequest.layer` names a target, so the histogram can show "just this mask's colours" without a second render. `LiveSession` owns a pair of `MAP_READ` staging buffers and alternates between them every tick (`live_session/scope.rs`): each render REQUESTS an async map of its own sample and reports whichever OTHER slot's map has already completed — always the PREVIOUS tick's, one tick late, and `take_scope_stats` only polls, never blocks, so a still-in-flight map costs nothing and is retried on the next call. A dithered-and-requantized u8 frame is deliberately not treated as a valid oracle for cross-checking the histogram in tests — see `live_session/tests_scope.rs`'s module doc for why quantization alone can move a large fraction of total bin weight with no individual pixel being wrong; only a full-precision f32 readback is a valid comparison.

Constants the kernels bake in are generated, not hand-typed: `src/generated/color_matrices.wgsl` (Rec.2020↔sRGB/P3 and the Oklab pair) and `src/generated/agx_coeffs.wgsl` (inset/outset matrices and the log-encode scalars). The Rust pipeline accessors prepend those modules before compiling a kernel — WGSL has no `#include` — and `src/scripts/check_wgsl.sh` reproduces that concatenation to run naga's front-end and validator on CPU, so shader breakage is caught on a runner with no GPU.

### Ordered local mask groups (#3408)

One correction may contain ordered Add, Subtract and Intersect components, independent component/group inversion, and final opacity. CPU and WGSL evaluate the same union/product coverage formulas described in `xmp-canonical-format.md`; local controls and scope selection address logical layers, not the group's physical component records. The flat wire retains its 40-float stride: kind 4 is a group header carrying component count, opacity and group inversion, followed by control-free leaf records whose encoded kind carries shape, combine operation and inversion. Layout constants are generated for Rust, WGSL, Swift, TypeScript and C#. Shape changes update the live-chain signature; geometry/opacity changes only update parameters. GPU components share the existing chain and bitmap bindings, without intermediate component planes or new per-tick GPU buffers. Missing any group bitmap makes the entire group inert, even if inverted.

## The FFI surface

The GPU-enabled `maple_gpu_fit_auto_profile_at_render_size` entry returns the same separate curve/residual buffers as `maple_gpu_fit_auto_profile`, with an explicit nonzero maximum long edge matching the native sized renderer (#4136). It delegates to shared-core `FitCap::Render(edge)` and retains that size-specific cache origin; live edits do not affect the fit model. The existing entry preserves standalone-proxy calibration. Windows render-size fitting adoption is tracked separately under #4120; retained-artifact composition is described below. This ABI addition alone does not change host defaults or qualify color/performance.

`maple_compose_auto_profile_lut` bakes retained curve/residual artifacts into the CPU display cube using the same shared-core curve-then-residual math (#4138). It performs no file I/O or fitting. Either stage can be omitted; absent tails and malformed buffers leave the destination untouched. Windows uses it to compose the CPU cube from the retained GPU fit artifacts (#4146), retaining that cube across slider ticks. Render-size fitting adoption and integrated color/performance qualification remain tracked by #4120.

### The capture decode (#5377)

The one interface a host uses to drive the capture-first live chain. A capture decode returns the capture result — the RAW developed through stages 1–9d into the fixed as-shot Rec.2020 basis, EXIF-oriented f32 RGBA, with no white balance, camera profile, Oklab recovery or exposure gain applied — together with the creative stage that renders it. The host keeps both and, every tick, hands the creative stage back with the absolute slider pair; the chain runs `CreativeStage::render`'s GPU twin (or, on the CPU fallback, the stage itself), so the live frame and a fresh develop of the same model agree by construction.

| Entry                                                                         | Output                                                                                                                                                  |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maple_render_file_capture_f32`, `maple_render_bytes_capture_f32`             | full-resolution capture into `MapleCaptureBufferF32`                                                                                                    |
| `maple_render_file_capture_sized_f32`, `maple_render_bytes_capture_sized_f32` | the same, downsampled to `max_long_edge` before the capture stages                                                                                      |
| `maple_render_handle_capture_tile_f32`                                        | a tile of a handle's capture result into `MapleSceneLinearBufferF32`, for a native-detail patch; render it with the whole-frame decode's creative stage |
| `maple_free_capture_buffer_f32`                                               | frees the pixels; the creative tables stay valid                                                                                                        |

Arguments and return codes match the scene-linear f32 entries they sit beside. `MapleCaptureBufferF32` is `{ scene: MapleSceneLinearBufferF32, creative: MapleCaptureCreative }`: `scene` carries the pixels, the slider frame's as-shot pair (`wb_frame_scene_cct`, `wb_frame_as_shot_tint`) for seeding the sliders, the Whites anchor, the sampling density, the noise profile, ISO and the lens-correction flags as before, with `wb_hsm_data` always null and `ae_gain` equal to the creative stage's gain (the pixels do not carry it).

`MapleCaptureCreative` is raw-core's `CreativeHeader` laid out flat (`raw-ffi/src/capture_creative.rs`): `present` (1 for a capture decode, 0 when zeroed), the Oklab-recovery flag, the exposure gain measured on the as-shot render, the as-shot neutral, the render profile's linear core (illuminant, ColorMatrix, optional ForwardMatrix, scene CCT and white, the pre-gain flag, the optional dual calibration with its optional ForwardMatrices), the optional slider frame (endpoints, as-shot CM, as-shot CCT and tint, render CM), the as-shot table kind (none, a stored table, or the endpoints lerped at the scene CCT) and four `MapleCreativeTable { offset, dims[3], srgb }` spans (`hsm`, `cold`, `warm`, `look`; all-zero `dims` is absent) into `tables`/`tables_len`. The tables are interned per profile for the life of the process (`wb_frame_flat::intern_table_wire`), so a host copies the struct by value and needs no owner for the pointer.

Per tick the host points `MapleGpuLiveParams::creative_ptr` (GPU) or `MapleAdjustmentParams::creative_ptr` (every CPU chain entry: plain, fused, scoped, windowed, haze map and key) at its copy, valid for the call, and passes the slider pair in `temperature`/`tint` as the absolute values in the decode's slider frame; `decoded_*`, `wb_frame_*` and `wb_hsm_*` are then not read. A null `creative_ptr` keeps the scene-linear decode's white-balance delta. A struct that is not a capture decode's, or whose spans do not fit its tables, is refused rather than rendered: rc -1 from the GPU entries and the CPU scope entry, 8 from the other CPU chain entries, and a zero window reach. Deriving a GPU tick's plan (`CreativeHeader::gpu_plan`) allocates nothing and borrows the interned tables, which the GPU pools by content, so a white-balance drag allocates no GPU resource and uploads no table after its first tick.

Raw-core's side is `pipeline::render_capture_from_raw_f32` / `render_capture_sized_from_raw_f32` (`CaptureRender`), `render_capture_tile_cancellable_f32`, `CreativeStage::transport` and `CreativeHeader::{gpu_plan, stage, tick}`, which Apple (#5377) and Windows (#5378) use through raw-ffi. Web (#5379) drives `raw_gpu::LiveSession` itself, so it uses raw-core's side directly: `gpu_host::capture::develop_capture_prefix_rgba` runs `render_capture_sized_sensor_framed_f32` (the sized decode left in sensor framing, since its chain orients at present) and interns the tables (`intern_creative_tables`, the set raw-ffi uses), and `LiveCreative::apply` sets a tick's `FullChainInputs::creative` from `CreativeHeader::tick` (the model's pair in the slider frame, imported scales converted) with no allocation. Its gate is listed in [testing](testing.md#capture-first-gates-5213). Android/Linux adopts it next (#5380). The capture stages and the exposure anchor run once, at decode: the anchor is the as-shot render's, measured on the capture result before it moves into the basis (see [the exposure anchor](#the-exposure-anchor)), so the decode's gain is the one a full develop of the same model applies. The gates are listed in [testing](testing.md#capture-first-gates-5213).

### The capture refine (#5381)

A chroma pre-filter, deep denoise or capture-sharpening change does not need the RAW re-developed: those three stages are the last capture stages, so a host that kept their input can re-run only them, on the GPU. That input is the **refine base** — the as-shot basis after retouch, in the sensor frame (before EXIF orientation, so the BM3D patch grid and every stencil see the same pixels the CPU stages see). `render_capture_with_base_from_raw_f32` returns it beside the capture decode (`CaptureBase`), running the CPU stages on the base so the decode's pixels are unchanged.

1. `maple_render_{file,bytes}_capture_base_f32` decode exactly like the sized capture entries (a zero `max_long_edge` means full resolution) and also hand the host an opaque `MapleCaptureBase`, freed with `maple_free_capture_base`.
2. On a capture-stage edit the host calls `maple_gpu_capture_refine(base, xmp_path, budget, cancel, out)`. raw-ffi loads the model and checks it against the base's: anything beyond the three stages changing (retouch, profile, exposure mode, highlight recovery, any other decode-baked field) returns rc 10 and the host re-develops. Retouch therefore stays on the CPU capture path. A base whose long edge is over `budget.max_long_edge` also returns 10; `budget.bm3d_binding_cap_bytes` sets the BM3D binding cap (`GpuContext::set_bm3d_binding_cap`).
3. `raw_gpu::capture_refine` runs `ChromaPrefilterPass → DeepDenoisePass → CaptureSharpeningPass` (only the engaged ones) over the uploaded base in a transient pool bucket that is released when it returns, so the live sessions' warm buckets are untouched. `raw_core::pipeline::finish_capture_refine` then re-measures the as-shot exposure anchor on the refined capture, applies the orientation and packs it as the decode packs its own result, outside the GPU lock. The output is a `MapleCaptureBufferF32` the host treats as a fresh decode. BM3D dispatches its patch cache indirectly, so on a device without `DownlevelFlags::INDIRECT_EXECUTION` (the iOS Simulator's Metal device) a refine that engages deep denoise returns rc 8 and the host re-develops; chroma prefilter and capture sharpening still refine there.
4. Cancellation is the host's decode generation: a newer edit flips `cancel`, BM3D stops at its next tile, and the refine returns rc 4 with nothing written. There are no partial results: the refine reads back whole or not at all.
5. The host publishes the refine atomically with `maple_gpu_live_update_image` (`LiveSession::update_image`): one queue write of the new pixels into the open session, which keeps its buffers, pool and Auto Profile fit.

The shared Rust half is `raw_core::gpu_host::capture::refine::refine_capture_rgba[_async]` plus `finish_capture_refine`, beside the Web live prefix in `gpu_host::capture`. Only Apple calls it so far; Windows (#5378) and Web (#5379) run the capture decode but still re-develop on a capture-stage edit, and Android/Linux follow #5380. On Apple, `RenderActor` keeps the base beside its decoded slot (`decodedCaptureBase`, keyed on asset, sidecar, profile, exposure mode, quality and decode edge); a sized decode request matching that key refines under the decode's own cancel flag and write gate, and `GpuLiveDriver` replaces a same-size, same-crop upload in place. The per-device budget is `CaptureRefineBudget`: macOS refines bases up to 2560 px with a 128 MiB BM3D cap (a 4096 px refine measured about 1.1 GiB of GPU scratch, so larger decodes keep re-developing); iOS and tvOS up to 1536 px with 32 MiB, and an iPhone clamps its RAW decode to 1536 px while a refinable stage is engaged (#5213 decision 7). A decode over the budget keeps no base, so it costs no extra memory and its edits re-develop on the CPU as before; that is every iPad fit-mode decode today. The base answers one decode request, so a refine fires when the same request repeats (fit mode, and every iPhone decode under the clamp); zoomed in, the fast and refine phases decode at different sizes and still re-develop. The driver replaces in place only when the new decode's dims, crop, noise profile, ISO, Whites anchor and sampling density match the open session's, and it claims the session revision as a reopen does, so an older replace or open still reading back cannot land after it (#3360). Gates: `capture_first/tests_base.rs` (a decode with its base equals the capture decode; a refine from the base equals a fresh decode, including EXIF orientation 6); raw-ffi's `gpu_live_capture_refine_tests` (S0 GPU/CPU gate per stage, refusals, cancellation, `update_image`) and the fixture-gated `gpu_live_capture_refine_physical_tests` (the S0 gate — mean relative error ≤ 1e-6, p99.9 ≤ 1e-4, max ≤ 1e-2 — on `test_0007`, `test_0005` and `test_0013` at 2560 and 1536 px for each stage and all three chained, plus the ignored latency and footprint measurement).

`raw-ffi` is thin marshalling over `raw-core`: type shims, pointer helpers, error codes, and a `LAST_ERROR` thread-local read back through `maple_last_error`. The generated header is `RawPipeline.h`, produced by cbindgen (config in `raw-ffi/cbindgen.toml`) as part of `src/apple/scripts/build-xcframework.sh`, not by `tools/codegen.sh`. The **handle model** (`raw-ffi/src/handle.rs`) is what makes deep zoom viable: `maple_open_raw_handle` decodes the RAW and parses the XMP once and keeps both alive behind an opaque pointer, so a 100 MP decode runs once per asset open instead of once per tile. Re-rendering with a different model means closing and reopening — the handle never mutates its stored model. Callers must free it; failing to do so leaks tens to hundreds of megabytes.

The Apple xcframework is built by `src/apple/scripts/build-xcframework.sh` for `aarch64-apple-ios`, `aarch64-apple-ios-sim`, `aarch64-apple-darwin` and `x86_64-apple-darwin`, always with `--features gpu` plus `pano` (macOS) or `pano-ios` (iOS). The server's dylib is built by `src/api/scripts/build-raw-ffi.sh` into `src/api/native/`. See [apple](apple.md) and [api](api.md).

## The WASM surface

`raw-wasm` exports, via `wasm-bindgen`: `render_bytes` / `render_bytes_sized` / `render_bytes_with_film` (8-bit sRGB), `render_bytes_scene_linear[_sized]` (fp16 RGBA), `develop_non_raw` (an already-decoded scene-linear f32 RGBA buffer through the per-tick chain with AgX skipped), `export_bytes[_with_film]`, `extract_embedded_preview`, `compute_auto_tone`, `compute_auto_adjustments_from_bytes`, `compute_profile_lut`, `render_filename_template` / `validate_filename`, the streaming `FallbackIdHasher`, and — under the `gpu` feature — `render_bytes_gpu` (one-shot) and the persistent `WebLiveSession` (open → render(xmp)\* → drop, presenting straight to a transferred `OffscreenCanvas` with no CPU readback).

Build it with `src/raw-pipeline/raw-wasm/build.sh`, never a bare `wasm-pack build`:

```bash
cd src/raw-pipeline/raw-wasm && bash build.sh
cd ../../web && bash scripts/sync-raw-wasm.sh
```

The script runs `wasm-pack build --target web --release --features gpu,parallel -Z build-std=panic_abort,std`. The `-Z build-std` is not optional: `raw-wasm/.cargo/config.toml` sets `-C target-feature=+atomics,+bulk-memory,+mutable-globals` for `wasm32-unknown-unknown`, and the standard library has to be rebuilt with the same features for atomics to link. Those features only become _usable_ when the page is cross-origin isolated (COOP `same-origin` + COEP `require-corp`); JS checks `crossOriginIsolated` before calling `initThreadPool`, and the single-threaded path works everywhere else. The same config passes `--max-memory=4294967296` — 4 GiB is the wasm32 hard ceiling, and it still does not fit a full-resolution develop of a large sensor, which is why `raw-wasm/src/cpu_budget.rs` clamps every CPU render entry. One bundle ships both features; the worker picks the GPU entry when `'gpu' in navigator` and falls back to threaded CPU otherwise. See [web](web.md).

## Pipeline output version

`PIPELINE_OUTPUT_VERSION` was retired in #5007. The counter (introduced by #1926, last value 30) existed to invalidate derived artifacts when the develop pipeline's pixels changed for the same (RAW, sidecar) input, but shared derivatives were decoupled from it in #4793 and its evidence-record coupling only bought re-recording and PR serialisation. There is no replacement counter and nothing to bump: pixel changes are gated by the Auto-to-embedded-JPEG colour harness, evidence records are gated only on their corpus (see [testing](testing.md)), and a change that alters what an already-stored sidecar value _means_ must instead ship a per-field load-time converter in the same PR, following the `WbScaleVersion` pattern — see [xmp-canonical-format](xmp-canonical-format.md). The v1–v30 lineage below is kept as history; it is the audit trail for reinterpretations that may still owe a converter.

It reached the platforms through codegen (`AdjustmentModel.pipelineOutputVersion` in Swift, `PIPELINE_OUTPUT_VERSION` in TypeScript, `AdjustmentFields.pipelineOutputVersion` in Kotlin); all of those mirrors were deleted with the counter, and `codegen-drift` coverage of every other constant and schema is unchanged. `WbScaleVersion` remains the richer per-field tool, and is now the only one. See [caching](caching.md) and [xmp-canonical-format](xmp-canonical-format.md).

## Diagnostics and profiling

`MAPLE_PROFILE` still exists. `pipeline::stage()` wraps every stage with an `Instant::now()` and, when the variable is **set to anything at all** (existence, not value — `MAPLE_PROFILE=0` enables it; only `unset` disables it), prints `[raw-core] <stage_name>  <elapsed>` to stderr. It is compiled into release builds because the cost when unset is one `Instant::now()` and one `getenv`. On `wasm32` there is no `std::time::Instant`, so the wrapper is a pass-through.

Other environment switches: `MAPLE_STAGE_DUMP` (with `--features stage-dump`) writes one OpenEXR per stage into the named directory for `src/scripts/stage_diff.py`; `MAPLE_DISABLE_AUTO_PROFILE`, `MAPLE_DISABLE_AUTO_LUT` and `MAPLE_AUTO_LUT_STRENGTH` gate the Auto Profile tail; `MAPLE_DISABLE_BUNDLED_PROFILES` forces the embedded/fallback DCP paths; `MAPLE_BE_OVERRIDE` is a dev-only absolute `BaselineExposure` override. These are development and harness affordances, not product configuration.

Diagnostic examples under `raw-core/examples/` include `dump_pixel` and `dump_scene_linear` (per-stage values at one pixel), `inspect-camera`, `probe-crop`, `wb_camera_probe`, `wb_gamut_probe`, `mem-probe`, and the `nlm_bench` / `clarity-bench` / `downsample-bench` / `tick-tail-bench` micro-benchmarks. Run them with `cargo run --release -p raw-core --example <name> -- <args>`.

### Windows ARM64 NLM qualification (#4273)

Pipeline epoch 9 includes the five-tap constant-strength tiled CPU NLM path,
fixed 256-row reseed boundaries in the general path, and a canonical binary32
exponential table. The table is generated with 80-digit decimal precision by
`tools/generate_nlm_exp_table.py` and included by both CPU and GPU hosts. This
removes platform `expf` variation; fixed boundaries remove thread-pool-dependent
rounding. The tiled path preserves shift order but changes patch reduction
rounding, so epoch 8 previews must be invalidated rather than claiming bit identity.

The WGSL kernel already uses local separable patch sums and receives the same
canonical table. Its arithmetic contract remains the existing maximum absolute
error below 1e-4, not CPU/GPU bit identity. The profile-free parity test includes
257×65 and 513×67 planes to enter the CPU tiled dispatch; a separate profiled test
covers the general path. CPU tests additionally require bit-identical outputs
across 1, 2, 4 and 7 threads and compare ARM64 vector accumulation exactly with
the scalar operations. Scratch allocation is bounded to six buffers per worker
per call, reused across all that worker's tiles; no per-tile allocations remain.

The presentation blue-noise storage change preserves the original 4096 values;
it changes the Adreno shader resource representation, not the dither sequence.
The repeated-frame test checks initial upload and subsequent buffer reuse, and
requires every frame to pass.
