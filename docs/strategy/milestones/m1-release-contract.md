# M1 — Release Contract & Qualification

This is the design spec for GitHub Milestone 13, "Release Contract & Qualification" (due 2026-09-11), tracked by the epic issue #2443 and its sub-issues (#2430–#2433, #2288, #2315, #2335, #2336, #2366, plus #2674, a bug the work surfaced). Several sub-issues cite this file as their design spec but it never existed, so each carried its own Outcome / Design / Acceptance criteria / Non-goals with no shared account of the current state or how the pieces fit together. This document is that account, written from a read of the tickets, the CI configuration, the branch-protection ruleset, and the relevant code as of 2026-09-02.

## Outcome, and why it matters

CLAUDE.md's product bar is "color quality that a working photographer will trust" on a non-destructive pipeline where "the sidecar is the contract." Trust here is not a feeling — it is a claim a photographer can act on: edit a photo, close the app, come back next week or on a different device, and get back exactly what they left, with the original file untouched. Milestone 13 exists because that claim currently rests on evidence quality that varies wildly by surface. Some of it is excellent (the color harness's CIEDE2000 budgets, gated as a one-way ratchet). Some of it is a test that has never once executed (#2366). Some of it was, until this week, a CI check that segfaulted at a rate that trained people to re-run it rather than read it (#2336, now fixed — see below). And as of this week, the mechanism that made any of these checks mandatory before merge was quietly emptied (see below) — so today, nothing stops a change from landing on `main` even if every one of these gates is red.

The milestone's job is to close that gap in two ways: make the evidence for "this capability works" impossible to fake or silently skip (#2433 — done; #2430 — open), and make the thing every capability actually depends on — a committed edit surviving reload, undo, and export — a single well-defined transaction instead of an assortment of ad hoc call sites (#2432). The rest of the milestone is the unglamorous work of making the gates that back those claims actually run: sidecar round-trips across every real storage backend (#2431, done), the Apple visual-regression harness (#2366, #2288), and GPU parity on the backends Maple ships on, not just the one lavapipe emulates (#2315, #2336).

## Current state

### Branch protection has regressed since this milestone's own qualification work landed

`gh api repos/zubair-io/Maple/rules/branches/main`, read live on 2026-09-02, returns exactly four rules on the repository's one ruleset ("Main", id 22041068): `deletion`, `non_fast_forward`, `pull_request` (0 required approvals, rebase-only merges, Copilot review required), and `copilot_code_review`. There is no `required_status_checks` rule at all. That means no CI job — not `api-tests`, not `jules/review`, not the color harness, nothing — is a server-side precondition for merging to `main` right now.

This is a regression, not the starting state this milestone found. #2433's closing comment (2026-09-01) records that the ruleset carried a `required_status_checks` rule naming `jules/review` and `api-tests` as required, with strict-up-to-date enforcement, and explicitly notes the rest (`raw-gpu`, `file-budget`, `codegen-drift`, `color-pipeline`, web/windows builds) were still advisory pending #2336. The ruleset's own `updated_at` timestamp (2026-09-01T23:38:57-04:00) is consistent with the requirement being removed a few hours after that comment. `docs/testing.md` still describes branch protection as "not configured," which was wrong on 2026-09-01 and, by coincidence, is accurate again today. Whoever owns this milestone should decide whether that was a deliberate rollback (and if so, why) or an accidental ruleset edit — see Open decisions.

### CI as configured today

Ten workflows exist under `.github/workflows/`; `docs/testing.md` catalogs all of them accurately. The two relevant to this milestone:

- **`apple.yml`** runs exactly one job, `swift-build`, which compiles the `MapleCore` Swift package against a cbindgen-generated header and a fabricated empty stub `libraw_ffi.a` (see the workflow's own comment block for why a stub suffices for a compile-only gate). It does not build the `Maple Exposure` app target, `Maple TV`, `MapleBackupAgent`, `MapleFileProvider`, `MapleWidget`, or any extension. It does not run `MapleTests` or `MapleUITests`. `docs/testing.md` § Apple states this plainly: "No cloud CI runs Apple tests." Every Apple-side gate this milestone touches (#2366, #2288, the slider matrix) only ever runs locally or via Xcode Cloud (configured in App Store Connect, outside this repo), and Xcode Cloud does not build or run UI tests either — `src/apple/ci_scripts/ci_post_clone.sh` only bootstraps the Rust toolchain and the xcframework for an archive build.
- **`raw-pipeline.yml`**'s `raw-gpu` job installs Mesa lavapipe (a software Vulkan implementation) on a stock Ubuntu runner and runs `cargo test -p raw-gpu` (about 180 tests) plus `cargo test -p raw-wasm --features gpu` against it. This is the CPU-core-vs-WGSL-kernel parity gate #1973 made real; before that, a green tick only meant the shaders parsed. It proves raw-core and the WGSL kernels agree under naga's SPIR-V output. It says nothing about naga's MSL output (what every Apple build actually runs) or a browser's native WebGPU compiler — that gap is #2315.

### The raw-gpu SIGSEGV (#2336) is now fixed

As of #3206 (merged 2026-09-02), `raw-pipeline.yml`'s `raw-gpu` job runs `cargo test -p raw-gpu -- --test-threads=1`. The root cause: each of the crate's ~200 tests builds its own `GpuContext` from scratch, and under `cargo test`'s default per-CPU-core parallelism, many of those were alive and churning concurrently against lavapipe's software rasterizer — which isn't validated for concurrent multi-context creation/teardown from independent OS threads. The three crashing tests (`present_chain::tests::offscreen_present_matches_cpu_render_within_1_lsb`, `offscreen_present_row_alignment_misaligned_width`, `present_paints_the_image_not_the_clear_color`) were the only ones in the crate that create a `wgpu::Texture` and read it back, so they were consistently the ones still mid-flight when a sibling thread's context churn corrupted shared rasterizer state — a control (identical binary hash across a crashing run and a clean `main` build) had already ruled out the diff under test. Serializing removes the concurrency dimension the crash needed, with no test skipped and no coverage lost — unlike the ticket's alternative of skipping the three offscreen tests under lavapipe. `docs/testing.md`'s GPU-parity section documents this fix and its reference command; this doc's own "Already resolved" section below reflects it too.

### The Apple canvas visual-regression gate (#2366): partially fixed, still open

Both root causes #2366 identified have working fixes in the tree on `main` today, but the acceptance criterion isn't fully met and the ticket is still open:

- **Cause 1 (env vars never reached the runner).** `Maple Exposure.xcscheme`'s `TestAction` now sets `shouldUseLaunchSchemeArgsEnv = "NO"` and declares `TEST_RUNNER_MAPLE_UITEST_FIXTURE_ROOT` / `TEST_RUNNER_MAPLE_UITEST_GOLDENS_ROOT` directly in its own `<EnvironmentVariables>` block, each with an inline comment citing #2366 and explaining the `TEST_RUNNER_` prefix mechanism. This is fixed.
- **Cause 2 (sandboxed app can't read a repo path).** `MapleAppDriver.launch(fixture:)` (`src/apple/MapleUITests/Helpers/MapleAppDriver.swift`) now copies the located fixture into a fresh temp directory before launch and points `MAPLE_UITEST_FIXTURE_ROOT` at the staged copy, with a comment explaining that `Maple.entitlements`' sandbox grant (`files.user-selected.read-write`, no arbitrary-path grant) is why a direct repo path silently produced a blank canvas. This mirrors what `SliderMatrixUITests` already did. This is fixed.

What's still open is the acceptance criterion itself: `testCanvasMatchesGolden` calls `XCTSkip` unconditionally whenever the fixture is missing, with no distinction between "fixture genuinely absent" (fine, matches the repo's skip-pass convention) and "an operator explicitly set `MAPLE_UITEST_FIXTURE_ROOT` and it still didn't resolve" (should fail loudly — a silent skip is exactly what let this gate go unexercised for as long as it did). The ticket names this decision explicitly and it hasn't been made in code. CLAUDE.md's UITest section also still documents the CLI form `xcodebuild test ... MAPLE_UITEST_FIXTURE_ROOT="$PWD/test-fixtures/raws"`, which — per the issue's own diagnosis — sets an Xcode build setting, not a process environment variable, and never reaches the runner; the scheme fix above makes that invocation redundant (the scheme now hardcodes the path) but the doc has not been corrected to say so.

Separately, and outside this milestone's ticket list but directly blocking verification of both #2366 and #2288 locally: #2525 (open, milestone 13) reports that XCUITest cannot complete its automation-mode handshake on the reporter's development machine at all — every class, including long-standing ones, times out during launch, independent of load or the known biometry/lock-screen blockers CLAUDE.md documents. Until that's resolved on a given machine, "run the harness and confirm" for anything under `MapleUITests` needs either a different Mac or an interactive Xcode run to re-authorize the TCC grant.

### The slider-matrix aspect-mismatch bug (#2288) is fixed on `main`, but the ticket is still open

`src/apple/MapleUITests/Helpers/CanvasCapture.swift`'s `imagePNG(_:containerFrame:imageRectMarker:)` now crops to an accessibility-published image rect rather than the whole canvas container, with five follow-up "review round" commits (`2f300e2f3`, `482baff0f`, `584525964`, `6b668d045`, `3defd327c`) tightening the scaling and rounding. `git merge-base --is-ancestor` confirms the final commit is on `main`. This is done. Its ticket being open is a bookkeeping gap the owner should close, not a work item — flagged in Open decisions only because it's the second sub-issue in this milestone (after #2288's sibling below) where the code and the tracker disagree.

### What's already landed in this milestone

Four of the milestone's sub-issues are closed with real merged work, and it's worth knowing what they did because later items build on it:

- **#2431** (cross-adapter sidecar transaction contract suite) drove one versioned test vector — the canonical-format golden model plus a real Lightroom-authored passthrough document — through all four adapters declared for release (`FilesystemSource`, `SMBSource`, `PhotoKitSource`, `CloudSource`; see `docs/architecture.md`'s sidecar-location table) and the API's storage layer, without mocking the sidecar layer, per commit `3e8d04b9c`. It found and fixed a real bug in the process (`PhotoKitSidecarStore` silently dropped unknown XML content on every write) and documented a second, larger one via `XCTExpectFailure` rather than fixing it out of scope: SMB-sourced edits were never persisted at all, because `EditSession` had no code path that wired an `SMBSidecarStore` for that provenance. That became #2674, which is also now closed — `EditSession`, `BrowseViewModel`, and `AppShell+FolderActions.ensureSession` were updated to tag and route SMB assets the same way PhotoKit assets already were.
- **#2433** (non-vacuous qualification jobs) is the ticket that put the now-vanished `required_status_checks` rule in place, among other things.
- **#2335** (budget-ratchet re-baseline path) landed the `RE-BASELINE: <fixture>/<case>.<metric>: <justification>` marker mechanism in `tools/check_budget_ratchet.py` (wired into `.github/workflows/cross.yml`), so a legitimate, audited ceiling raise is possible without disabling the gate.
- **#2238** and **#2256** were both documentation/tooling drift fixes (a dead doc pointer, a stale committed WASM package) unrelated to the qualification-evidence thread but scoped into this milestone.

### The action model this milestone's transaction work (#2432) has to unify

Apple's undo/redo today (`src/apple/Packages/MapleCore/Sources/MapleCore/EditSession+UndoRedo.swift`) is a 32-entry FIFO ring of whole `AdjustmentModel` snapshots: `beginEdit()` pushes the current model, `undo()`/`redo()` pop and swap it wholesale. There is no per-action identifier, no semantic before/after diff, and no shared object that also drives sidecar persistence, render invalidation, and accessibility announcement — each of those is its own call site scattered through `EditSession` and its extensions. The web editor (`editor-state.service.ts`, `editor-shell-undo.ts`) follows the same snapshot-stack shape. #2432 is not proposing a net-new mechanism so much as replacing N independent snapshot/notify call sites with one transaction object that all of them consume.

### The feature-status gap this milestone's registry work (#2430) closes

`docs/features.md` § 8 carries a per-platform matrix of what ships where, but nothing in the codebase currently classifies a capability as `Core`, `Integrated`, or `Released`, and nothing ties that classification to whether its qualification evidence actually exists and is non-vacuous. The existing single-sourcing precedent #2430 would extend is the `codegen` crate (`src/raw-pipeline/codegen/src/`: `adjustment.rs`, `adjustment_tables.rs`, `color_matrices.rs`, `ui_tokens.rs`, `ui_tokens_xaml.rs`, `film_catalog.rs`), which already generates Swift, TypeScript, SCSS, and WGSL consumers from one Rust source, driven by `tools/codegen.sh` and checked for drift by the `codegen-drift` job in `cross.yml`. A capability registry is the same pattern applied to a new kind of fact.

## Per-ticket design

### #2430 — Capability registry and evidence-backed release state

**Scope.** One schema, one Rust source of truth, generated consumers for Swift and TypeScript (and, given `codegen`'s existing scope, plausibly C# for Windows, though the ticket doesn't name it — see Open decisions). Each capability record carries a stable identifier, an owner, its declared surface(s), storage adapter(s), asset class(es), preview and export path, and the state (`Core` / `Integrated` / `Released`) computed — not asserted — from the qualification evidence #2433 already made non-vacuous: pipeline version, schema version, corpus hash, backend, expected case count, and executed case count.

**Design.** This slots into the existing codegen pipeline as a new module (e.g. `capability_registry.rs`) alongside `adjustment.rs` and `color_matrices.rs`. The schema itself should live as plain Rust data (structs/consts, the same shape `adjustment_tables.rs` uses), because that gives the "cannot manually override" property almost for free — the registry a human edits is Rust source under normal PR review, not a JSON file a doc or a script could silently diverge from. Promotion to `Released` needs a build step that reads the actual qualification outputs (the color-harness summary, the qualification-job JSON #2433 established, the sidecar contract suite's pass/fail) and mechanically checks the capability's declared evidence sources against them — this is the piece with no existing analog in the codebase and is the bulk of the implementation work. "Evidence loss demotes a capability in the next build" means the check has to run every time the registry is regenerated (i.e., every `tools/codegen.sh` run gated by `codegen-drift`), not just once at authoring time.

**Sequencing.** The registry's promotion logic is only as trustworthy as the CI jobs it reads evidence from. Building the schema and the Rust/Swift/TS generators can start immediately and in parallel with everything else in this milestone — that part has no dependency. Wiring live evidence-promotion for the Apple canvas gate specifically should wait until #2366's remaining acceptance gap (fail-loud vs. skip) is settled, or the registry will promote a capability on the strength of a test that silently skips. Wiring evidence-promotion for GPU-backed capabilities should wait on #2315 (#2336, the lavapipe SIGSEGV, is now fixed — see below), or "evidence" for anything routed through the GPU path means "the lavapipe-only gate happened to be green that day."

**Acceptance tests.** A registry unit/integration suite (Rust, mirroring `codegen`'s own test conventions) that: constructs a capability whose declared evidence source reports zero executed cases and asserts the build cannot classify it `Released`; constructs one whose evidence is present and complete and asserts it can; and a codegen-drift-style check that the generated Swift/TS files match a fresh generation. A machine-readable release summary (JSON) is itself a build artifact this suite should validate against a fixed schema.

**Non-goals.** No new editing operator. No manual status spreadsheet — if the registry needs a fact no build artifact currently expresses, the fix is to make that build artifact express it, not to hand-author the fact. No inference from product age, issue count, or code presence alone — a capability with code and no green evidence stays `Core` (or unclassified), not `Integrated`.

### #2432 — Unify committed actions across undo, sidecar diff, and render invalidation

**Scope.** Every committed editor action — global adjustments, Auto, crop/rotation, copy/paste, masks (once they ship — see `docs/features.md` § "Local adjustments and masks — not surfaced"), repair, variant operations — goes through one transaction contract: a stable transaction ID, semantic before/after state, a deterministic sidecar diff, an invalidation scope, and a user-visible description for accessibility. Preview-only slider drags stay cancellable and don't enter history until committed, which is already true in spirit (the two-phase render's fast/refine split exists for exactly this reason) but isn't expressed as a first-class "this is a commit, not a preview" signal today.

**Design.** The natural home on Apple is a replacement for (or a wrapper around) `EditSession+UndoRedo.swift`'s snapshot ring: instead of pushing whole `AdjustmentModel` copies, `beginEdit()`'s call sites construct a transaction object carrying the semantic diff between old and new model state, and that one object is what the undo stack stores, what gets serialized to the sidecar, what marks render tiles/caches invalid, and what accessibility announces. Web's `EditorStateService` / `editor-shell-undo.ts` need the equivalent shape, since #2432's acceptance criteria (`docs/testing.md`'s parity principle) apply cross-platform. This is exactly the kind of schema the `codegen` crate was built to single-source, but transaction _shape_ (not values) is a code-structure decision more than a data-table one, so it's plausible this stays hand-mirrored in Swift and TypeScript rather than generated — worth deciding early since it sets the pattern (see Open decisions).

**Sequencing.** Independent of the CI-facing tickets (#2315, #2336, #2366) — this is app architecture, not test infrastructure — so it can run in parallel with all of them. It does depend conceptually on #2431's sidecar contract suite (done), since that suite is what defines "a valid semantic round-trip" for the diff a transaction produces; #2432 should reuse that suite's fixtures rather than inventing new ones. Given the size (`effort:L`, six platform-crossing action classes), the practical sequencing is per-action-class: land the contract for global adjustments first (highest-traffic, already well-covered by the color harness for correctness), then extend to Auto, crop/rotation, copy/paste, and the rest, rather than attempting one PR that touches all six at once — consistent with CLAUDE.md's guidance that independent sub-slices of an epic are candidates for incremental, even parallel, delivery.

**Acceptance tests.** Per the ticket: every committed action produces exactly one undo entry and a valid redo path (a property test driving action → undo → redo → compare model, per action class); reloaded semantic state matches committed state (round-trip through a real sidecar file, no mocks, per CONTRIBUTING.md's sidecar-testing rule); a stale async render result arriving after a newer transaction has committed cannot clobber it (a race test constructing that ordering deliberately); accessibility announces a committed change (an XCUITest or equivalent assertion on the announcement, not just that code path execution occurred).

**Non-goals.** No render-internal events entering user-visible history — a cache invalidation or a re-render triggered by, say, a display profile change is not a user action and must not create an undo entry. No per-platform action semantics — the same transaction shape and diff format on Apple and Web, even if the concrete UI gesture differs.

### #2315 — Bring Metal/MSL and browser-WebGPU parity into CI

**Scope.** The lavapipe-based `raw-gpu` job proves raw-core agrees with naga's SPIR-V output. It does not exercise naga's MSL output (what ships to every Apple user) or a real browser's own WebGPU compiler (what ships to every Web user). Today those two surfaces are covered only by `cargo test -p raw-gpu` run locally on real Metal hardware and by the Apple `MapleUITests` visual harness — both dependent on a human remembering to run them, and currently also blocked from running in CI at all per the "Apple app targets are not CI-compiled" finding above.

**Design.** The ticket itself recommends scoping the macOS-runner option first: GitHub-hosted `macos-*` runners expose a real Metal adapter to headless `wgpu`, so the same `cargo test -p raw-gpu` suite that runs against lavapipe on Ubuntu could run unmodified against Metal on a `macos-15` runner (the same image `apple.yml`'s `swift-build` already uses) — cheapest to add because it reuses the existing test suite verbatim, just against a different adapter, and it covers the platform with the most users. The browser-WebGPU side is a separate, larger effort: a Playwright-driven harness that opens `maple-syrup` or a minimal WASM test page in a real Chromium/WebKit build with WebGPU enabled and runs the parity comparison client-side, closer in shape to the `web.yml` Playwright artifact suite already described in `docs/testing.md` than to anything in `raw-pipeline.yml`.

**Sequencing.** #2336 has now stabilized the existing lavapipe job (#3206), which was the precondition for adding a second GPU-adapter job without compounding the "which gate do I distrust today" problem the ticket is trying to avoid — #2315 can proceed. The macOS-runner and browser-WebGPU halves are independent of each other and can be built in parallel once someone owns each.

**Acceptance tests.** A new CI job (or a matrix addition to `raw-gpu`) that fails when the Metal-adapter run and the raw-core reference disagree beyond the existing parity tolerance, using the same `cargo test -p raw-gpu` / `cargo test -p raw-wasm --features gpu` entry points lavapipe already exercises — the acceptance bar is "the same tests, a different real backend," not new test content. For the browser side, at minimum one case through `render_bytes_gpu` in a real WebGPU context compared against the WASM-CPU reference already validated by `raw-wasm`'s existing suite.

**Non-goals.** Not a rewrite of the parity test content itself — reuses what #1973 built. Not a requirement to cover every browser engine in the initial pass; Chromium-via-Playwright is the pragmatic first target given `web.yml` already runs a Playwright suite.

### #2336 — raw-gpu parity job intermittently SIGSEGVs on lavapipe (resolved)

Closed by #3206 (merged 2026-09-02): `cargo test -p raw-gpu` now runs with `--test-threads=1`. Root cause and fix are described under "The raw-gpu SIGSEGV (#2336) is now fixed" in Current state above, and in the `raw-gpu` job's own comment block in `raw-pipeline.yml` plus `docs/testing.md`'s GPU-parity section. No further design work remains here; kept as a heading only so this doc's ticket list and the epic's checklist agree on where #2336 was addressed.

### #2366 — remaining work: the skip-vs-fail decision and the CLAUDE.md correction

Both root causes are already fixed (see Current state above); what's left is small but load-bearing. `MapleAppDriver.launch(fixture:)` should distinguish "no `MAPLE_UITEST_FIXTURE_ROOT` was set and the default repo path has no fixture" (keep skip-passing — this is the correct behavior on a clean clone with no `test-fixtures/raws/`, matching `test_color_pipeline.sh`'s convention) from "an operator explicitly set `MAPLE_UITEST_FIXTURE_ROOT` (or its `TEST_RUNNER_`-prefixed form was read from the scheme) and the fixture still wasn't found at that path" (fail with `XCTFail`, not `XCTSkip` — an explicit root that doesn't resolve is misconfiguration, not "fixtures not provisioned"). CLAUDE.md's "UITest visual harness" section needs its example invocation corrected to stop suggesting `MAPLE_UITEST_FIXTURE_ROOT=...` as an `xcodebuild` command-line argument, since the scheme fix means that argument is now inert (the scheme hardcodes the path via `TEST_RUNNER_` env vars) and, per the issue, was never doing what the doc implied in the first place.

**Acceptance test.** The ticket states it precisely: "a deliberate perturbation of the golden should fail it." Concretely — run with a fixture present and a corrupted/mismatched golden PNG substituted, confirm `XCTFail` with a real ΔE number in the output, then run with `MAPLE_UITEST_FIXTURE_ROOT` pointed at an empty directory and confirm the new fail-loud path triggers rather than a skip.

## Open decisions for the owner

**Was removing `required_status_checks` from the Main ruleset intentional?** Recommended default: no — restore a `required_status_checks` rule naming at minimum `jules/review` and `api-tests` (the same pair #2433 established) with strict-up-to-date enforcement, immediately and independent of the rest of this milestone. Every day this stays unset, every other gate in this document — including ones this milestone is actively hardening — is advisory in practice, no matter how non-vacuous its evidence is.

**Should `raw-gpu` join the required-checks list, and when?** #2336's root-cause fix (#3206, serializing the binary) has landed, so the ~1-in-3 crash rate that made "required" mean "occasionally blocks an unrelated PR for reasons nobody can act on" no longer applies in principle. Recommended default: promote it once a handful of real post-fix CI runs on `main` confirm the serialized job stays green — the fix itself wasn't validated against this doc's earlier 20–50-run soak-test bar (lavapipe can't be reproduced locally on macOS, so #3206's own verification was "watch it stay green on CI"), so a short confirming window is still worth spending before making it a merge gate.

**macOS-runner Metal parity or browser-WebGPU harness first for #2315?** Recommended default: macOS runner, per the ticket's own reasoning — it reuses the existing `raw-gpu` test suite unmodified and covers the pipeline shipping to the most users, versus a net-new Playwright-based harness for the browser side.

**Should the capability registry's Rust-source schema (#2430) also generate a C# consumer for Windows?** The ticket only names Rust/Swift/TypeScript, but `codegen`'s existing scope already reaches Windows via `ui_tokens_xaml.rs`, and `docs/architecture.md` counts Windows among the shipped platforms. Recommended default: yes, scope it in from the start — adding a fourth codegen target later, after the schema and promotion logic are settled, is strictly more expensive than including it in the initial design.

**Should the #2432 transaction shape be generated (Rust source → Swift/TS) like the adjustment model, or hand-mirrored per platform like the undo stacks are today?** Recommended default: hand-mirrored initially. The transaction's _values_ (the semantic diff) are already generated via `adjustment.rs`; the transaction _object_ wrapping them is control-flow and platform-specific persistence/invalidation hooks, which is a poor fit for the codegen crate's current "emit constants and tables" shape. Revisit only if a third platform's implementation drifts in a way generation would have prevented.

## Implementation order

**Do first, no dependencies, small:** restore the ruleset's required-checks rule. This is a GitHub settings change, not a code change, and every day it's deferred widens the gap between "this milestone's gates exist" and "this milestone's gates matter."

**Track A — GPU CI trust:** #2336 is done (#3206 fixed the lavapipe SIGSEGV by serializing the job). What remains is #2315 (macOS-runner Metal parity and, separately, the browser-WebGPU harness — those two halves of #2315 can run in parallel with each other now that #2336 is settled).

**Track B — Apple visual-regression completion (small, independent of Track A):** the #2366 fail-loud/skip decision plus the CLAUDE.md correction, and closing #2288's ticket against its already-landed fix. Verifying either locally needs a machine where #2525's XCUITest automation-mode issue doesn't reproduce.

**Track C — action-model unification (independent of A and B, can start immediately):** #2432, sequenced internally by action class as described above — global adjustments first, then Auto/crop/copy-paste/masks/repair/variants.

**Track D — capability registry (schema work can start immediately; evidence-promotion wiring depends on A and B):** #2430's Rust schema and Swift/TypeScript (and, per the open decision above, C#) generators have no dependency on anything else in this milestone and can be built in parallel with Tracks A–C. Wiring live evidence-promotion for GPU-backed and Apple-canvas-backed capabilities specifically should land after Track A and Track B respectively land, so the registry's `Released` state means what it claims to mean rather than reading a gate that itself can't be trusted yet.

Tracks A, B, C, and D have no cross-dependencies at the track level and are natural candidates for parallel ownership; the dependencies that exist are all _within_ a track (or, for Track D's evidence-promotion half, pointing at the output of Tracks A and B) rather than between them.
