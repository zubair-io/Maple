## Three next implementation lanes

### #2435 — deterministic lens resolution and geometry

The [issue](https://github.com/zubair-io/Maple/issues/2435) is broader than distribution. The [M2 lens design](../strategy/milestones/m2-global-workflow.md) separates embedded opcodes, external profile resolution, and interactive manual geometry. No direct implementation PR was observed; the merged #3204 is the design spec. Related #3182/#3189 branches address the existing opcode signals.

Current source has the embedded correction sink in [lens_correction.rs](../../src/raw-pipeline/raw-core/src/types/adjustment/lens_correction.rs) and crop geometry in [geometry.rs](../../src/raw-pipeline/raw-core/src/pipeline/develop/geometry.rs), but no shared LCP resolver or the proposed perspective/aspect/scale model was found. The ongoing lens lane verified real Adobe LCPs in installed Camera Raw/Lightroom resources. Lack of parser input is therefore **not** a blocker on this machine.

Concrete implementation: deterministic exact identity matching and source/confidence metadata, profile parsing/interpolation into the existing correction sink, and independently the CPU/GPU manual geometry transform with matching crop/mask coordinate handling. Synthetic interpolation and coordinate tests can be built immediately.

Remaining release evidence: approved external distribution source/version/checksums, resolution against the declared physical camera/lens set, CPU/GPU geometry parity and latency/memory measurements. Local installed profiles do not establish permission or a mechanism to distribute a production catalog. Do not claim 95% coverage from synthetic profiles or include installed proprietary profile files in the repository.

### #2437 — variants, snapshots and semantic history

The [issue](https://github.com/zubair-io/Maple/issues/2437) and merged [M2 variant design](../strategy/milestones/m2-global-workflow.md) decide sidecar-first storage, stable variant identity, the legacy primary sidecar, sibling variant sidecars, nested snapshots, and bounded semantic history. No observed feature PR/branch exists; a dedicated implementation lane is now assigned.

Source still exposes one adjustment model and one ordinary sidecar per asset. [XmpStoreService](../../src/web/projects/maple-common/src/lib/xmp/xmp-store.service.ts) computes a single replacement-extension filename; [Windows SidecarStore](../../src/windows/Maple.WinUI/Services/Xmp/SidecarStore.cs) likewise owns ordinary sidecar loading/writing. No `VariantId`, `VariantName`, `variant_id`, or persistent variant/snapshot schema was found in the checked shared core, Web, API, or Windows sources. UI design-system history widgets are not a persisted product model.

Concrete implementation: one versioned shared schema and parser; deterministic sibling discovery that verifies headers and original association; atomic variant persistence preserving unknown XMP; API/Web/Windows selection and switching against the same original bytes; snapshot restore as one committed action; bounded durable history and recovery after reopen. Existing primary sidecars remain readable by older clients. A missing chosen variant must be an explicit missing-state error, never a silent switch to the primary edit.

There is **no external fixture, model, service, or product-decision blocker** to this non-Apple slice. Real temporary XMP files and deterministic original bytes can test discovery, rename/delete recovery, unknown-field preservation, and compaction. Full four-platform acceptance remains open while Apple UI/runtime work is excluded. Export can consume the active adjustment model without waiting for a new queue.

### #2438 — recipes and resilient export queue

The [issue](https://github.com/zubair-io/Maple/issues/2438) and [M2 export design](../strategy/milestones/m2-global-workflow.md) explicitly allow the versioned recipe schema and capability table to start independently. No recipe implementation PR was observed. The #3311 lane is assigned to continue with this work after publishing batch-sync changes.

The [Web export service](../../src/web/projects/maple-common/src/lib/export/image-export.service.ts) already exports the current model through the real pipeline. In contrast, the [API batch handler](../../src/api/src/job-runner/handlers/batch-jpeg-export.ts) still calls `renderThumbnailPreviewJpegToFile` and reports only in-process success/failure lists. A developed export ABI already exists in [export_file.rs](../../src/raw-pipeline/raw-ffi/src/export_file.rs); the API pool has not adopted it for this handler. No shared `ExportRecipe` model was found.

Concrete implementation: generated recipe schema with explicit per-encoder validation, reusable recipe UI, export from captured semantic adjustment state, per-item persistent queue state, cancellation, retry-only-failed and restart recovery. Reuse the #3311 ledger/status contracts and existing API claim/lease loop. Unsupported recipe fields must produce capability errors instead of silently disappearing.

The remaining shared orchestration dependency is active code coordination, not an unavailable external prerequisite. Output ICC/metadata golden files and cancellation/collision/error tests can use synthetic inputs. Final 100MP memory/latency qualification needs the real corpus and reference hardware; that does not block schema, persistence, UI or queue implementation.
