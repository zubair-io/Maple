# M2 — Complete Global Editing Workflow

Design spec for GitHub milestone **"14 · Complete Global Editing Workflow"**, epic #2444. Unlike the rest of `docs/`, this file describes work that has not landed yet — it is the shared design the five core sub-issues (#2434–#2438) implement against, so the four platforms don't independently invent incompatible answers to the same question. Once a piece lands, its lasting documentation belongs in `features.md`, `pipeline.md`, `xmp-canonical-format.md`, etc., the way every other shipped feature is documented; this file should be read as a proposal, not as a description of current behavior, except where a section is explicitly marked "today."

## 1. Outcome and why

A working photographer can take a multi-thousand-image assignment through Maple end to end: cull, correct white balance and lens geometry globally, synchronize those corrections across the shoot, keep alternate treatments without duplicating files, and export deliverables — without leaving the app, and without the process silently losing images, edits, or original bytes along the way.

Maple already has a capable single-image editor and a real copy/paste mechanism (#2239/#944). What it does not have is the layer that makes that editor scale to a shoot: white balance that is more than "As Shot or type a Kelvin number," a lens-correction path that only covers two fixtures in the whole test corpus, a synchronize operation that is a synchronous foreach with no progress bar, no branching or history model beyond a 32-entry RAM ring that a relaunch erases, and an export path that is single-asset on every front end and, where a batch path does exist server-side, renders through the thumbnailer rather than the real develop pipeline. Each of #2434–#2438 closes one of those gaps. This document is where their interactions — shared schema fields, shared batch-orchestration shape, shared sequencing — are worked out once instead of five times.

## 2. Current state

### White balance (`temperature`, `tint`)

`AdjustmentModel` carries `temperature` (2000–12000 K, default 6500) and `tint` (−150…150, default 0) plus `wbMethod` (`Cat16` | `DiagonalRec2020`) and the parse-state flags `temperature_seen`/`tint_seen` (`src/raw-pipeline/raw-core/src/types/adjustment/mod.rs`). A `whiteBalancePreset` marker already exists as a **web/sidecar-only** field outside the generated schema (`src/web/projects/maple-common/src/lib/models/adjustment-model.ts`) with the full ACR vocabulary — As Shot, Auto, Daylight, Cloudy, Shade, Tungsten, Fluorescent, Flash, Custom — but no front end offers a picker for it, so no UI-driven authoring path ever produces anything but `As Shot` or `Custom` today (`docs/features.md` § White balance) — the web XMP serializer (`xmp-serializer.service.ts`) will write and round-trip any named preset the field is set to (e.g. `Tungsten`), it's just that nothing in the UI ever sets one.

The only sampling UI is the web WB pad's eyedropper (`wb-pad.component.ts`, `wb-pad-math.ts`). It samples the **single center pixel** of whatever the canvas currently has decoded (no click-to-pick, no region average, no clipped-pixel guard) and runs it through `rgbToWb`, a hand-derived log-ratio heuristic the file's own comment calls out as "NOT the Robertson CCT method." The result is written straight to `temperature`/`tint` with no record of where it came from, what pixel was sampled, or what version of the estimator produced it — there is no provenance to show, because none is stored. Apple has no eyedropper at all.

AUTO (`editor-state.service.ts`, `EditorState+AutoReset.swift`) analyses the RAW and applies **exposure only**; the underlying `compute_auto_adjustments` also returns a white-balance estimate, and the apply path deliberately discards it, because `compute_awb` has three documented defects (#2247: a highlight-clipping guard that doesn't fire until 0.9 luma while the sensor clips at 0.786 on the flagged fixture, an un-normalized 0.6/0.4 blend where the bright term ends up voting 71%, and a neutrality gate that selects for the dominant subject color instead of neutral surfaces) that rail tint on real fixtures. AUTO white balance is not a "not built yet" gap — it is built, wired to real per-fixture regressions, and turned off.

### Lens corrections and manual geometry

The only lens-correction path today (#376, #2231) reads a DNG's own embedded `OpcodeList3` (`WarpRectilinear`, `FixVignetteRadial`, `GainMap`) and scales it with three fields — `lens_correction_distortion`/`_ca`/`_vignetting` (0–100, default 100) plus the `lens_profile_enable` master switch (`raw-core/src/types/adjustment/mod.rs`, tail of the struct, deliberately append-only per its own comment). These are **decode-product** parameters — resampled into the demosaiced buffer before DCP, upstream of every per-tick GPU stage — with no WGSL/Metal mirror, the same cache-key family as `chroma_prefilter` and `deep_denoise`. Across the whole fixture tree exactly two files carry an `OpcodeList3` at all (`test_0000.DNG`, DJI L3D-100c; `test_0015.dng`, Pixel 6 Pro), both with a single `WarpRectilinear` coefficient set (no lateral-CA data). Every CR2/RAF/ARW/NEF fixture renders with **no distortion, CA, or vignette correction at all**, where ACR applies a bundled profile (#2230).

`RawImage::has_lens_corrections()` and `RawImage::lens_correction_ca_inert()` (`raw-core/src/image.rs`) are the only decode-derived signals threaded to a UI today, and only on Apple (`EditSession`/`RenderActor.DecodedSnapshot` → `LensCorrectionsSection.swift`); web's `LensCorrectionsPanelComponent` has no such wiring yet (#3182), and neither platform has a third signal for "no `WarpRectilinear` at all, so the Distortion slider is also inert" (#3189). There is **no manual geometry control** beyond `crop`'s `{top, left, bottom, right, angle}` — no perspective (H/V), no independent rotation, no aspect/scale correction (`docs/features.md` § Geometry; confirmed against `AdjustmentModel` — no such fields exist).

### Batch synchronization

Copy/Paste/Sync (#2239/#944) already ships the piece #2436 is meant to build on: a single-sourced group table — White Balance, Tone, Color, Detail, Effects, Geometry — generated from `raw-core`'s schema (`raw-core/src/types/adjustment/schema/groups/`) into `adjustment-tables.generated.ts` and `AdjustmentModel+Generated.swift`, with a codegen-drift CI gate and a completeness test that fails the build if a new field lands in neither a group nor `NON_COPYABLE_FIELDS`. `AdjustmentClipboardService` (web) and `AdjustmentClipboard.swift` (Apple) hold one in-memory, session-only copied model each.

What it does **not** have is anywhere in #2436's acceptance list: `browse-shell.component.ts`'s `onSyncSettings`/`_pasteToSelection` is a synchronous `for (const id of this.state.selectedAssetIds())` loop that calls `updateAdjustment` per asset with no progress signal, no cancellation, no retry, and no per-asset failure reporting. `updateAdjustment` (`library-state.service.ts`) itself doesn't throw per-asset in that loop — it mutates the in-memory model via `store.setAdjustment` and schedules a debounced sidecar write (`scheduleSidecarWrite`) plus a debounced preview persist, both off the call stack — so a failure for one asset, if it happens at all, would surface later at debounce time with no link back to which loop iteration caused it, not as an exception that halts the remaining assets. Either way there's no progress bar, no cancellation, no retry-only-failed, and no final per-asset summary — the loop just fires 2,000 writes and returns immediately. Every group patch is **absolute** — `buildGroupPatch` (`adjustment-groups.ts`) copies each selected field at the source's literal value; there is no concept of a relative or asset-relative transfer anywhere in the codebase today.

### Variants, snapshots, history

There is no variant or snapshot concept anywhere in Maple's own model. Undo is `EditSession`'s (`EditSession+UndoRedo.swift`) and `EditorStateService`'s (`editor-state.service.ts`) matching 32-entry, push-on-gesture, FIFO-drop **in-memory** ring of full `AdjustmentModel` snapshots — it does not touch the sidecar and does not survive an app relaunch or a page reload. Maple already promises to preserve a **foreign** Lightroom sidecar's own variants, snapshots, and history byte-for-byte as opaque passthrough XML (`docs/xmp-canonical-format.md` § "A Maple writer must not destroy anything it does not understand") — so the precedent for order-preserving, byte-faithful round-trip of this class of data exists, just not a Maple-authored version of it.

### Export

`raw-core/src/export.rs` (`export_from_raw`/`export_from_raw_with_film`) is the one real export path — full develop chain, highest-quality demosaic, an ICC profile tagging the actual primaries — and every export today is **single-asset**, on every front end, driven by a coupled `format` enum that bundles color profile into the format itself (Apple's `ExportFileFormat`: `jpegSRGB`, `jpegP3`, `heicP3`, `tiff16`, `png` — `MapleExporter.swift`). Apple's own `ExportOptions` has a `maxSidePixels` field with no UI control wired to it. There is no naming template, no destination picker beyond a directory, no watermark, no metadata policy, and no overwrite policy anywhere in any export dialog.

The only batch path is server-side and JPEG-only: `batch_jpeg_export` (`src/api/src/job-runner/handlers/batch-jpeg-export.ts`) — note the real path is `src/api/src/job-runner/`, not `workers/job-runner/`; treat this doc's own citation, not `CLAUDE.md`'s, as stale if they disagree. Critically, it calls `ffiPool().renderThumbnailPreviewJpegToFile`, the **thumbnailer** shared with the 1280px describe/OCR preview tier — not `export_from_raw`. It produces a JPEG at up to 4096px with the asset's _baked-in preview render_, not necessarily the user's current adjustment state, and no UI creates one (`docs/features.md` § Export). The job-runner substrate underneath it — `src/api/src/job-runner/runner.ts`, a claim/lease/poll loop with `reportProgress`, `shouldCancel`, per-asset try/catch and a `{successCount, failedCount, failures[]}` result shape — is exactly the recovery/progress shape #2436 and #2438 need, and is worth reusing rather than re-inventing, but it exists **only** for Web Self Hosted; Apple and the browser-only `maple-syrup` deployment have no server to run it on.

## 3. Sub-issue designs

### #2434 — Sampled and preset white balance with provenance

**Scope.** As Shot / Auto / eight named-illuminant presets / temperature-tint / neutral sampler, all producing an explicit, undoable, inspectable result, with the sampler and Auto each landing as one committed action rather than a live-drag stream.

**Design.**

- _Presets_: the vocabulary and the `whiteBalancePreset` field already exist — as a sidecar/XMP field surfaced by the web `AdjustmentModel` (`src/web/projects/maple-common/src/lib/models/adjustment-model.ts`), read and written by the web XMP parser/serializer; there are no `whiteBalancePreset` references anywhere in `src/api/src`, so it is not yet a server-side schema field. The work is UI (a preset picker on both front ends) plus a resolver that maps a chosen preset name to a `(temperature, tint)` pair using each camera's own calibration illuminants where available (the DCP already carries `ColorMatrix1`/`ColorMatrix2` calibration illuminant tags — see `docs/xmp-canonical-format.md` § DCP), falling back to the standard CIE values (D65, D55, tungsten ≈2850 K, etc.) when the DCP doesn't name a matching pair.
- _Sampler_: replace `rgbToWb`'s log-ratio heuristic with a real CCT/Duv estimator (Robertson's method, or McCamy's polynomial approximation of it — either is a closed-form, well-understood computation, not a fit) implemented **once in `raw-core`** and exposed through FFI/WASM, not re-derived per platform — this is exactly the kind of color math principle 3 reserves for the shared core. `dcp::estimate_as_shot_cct_tint` already does CCT/tint estimation from a DCP-calibrated white point in `raw-core`; the sampler needs the same shape applied to a user-picked pixel region rather than the as-shot neutral.
- _Sampling UX_: click-to-pick a screen point (not a fixed center pixel), average a small neighborhood (e.g. 5×5) in the still-linear decode buffer before the view transform, and reject the sample with an actionable message when the region's max channel is within the sensor's own clip margin (the same class of clipping-awareness #2247 identifies as missing from `compute_awb`) or when the resulting CCT falls outside the declared 2000–12000 K domain.
- _Provenance_: new `AdjustmentModel` fields — `wb_source` (`Enum`: `AsShot | Auto | Preset | Sampled | Manual`), `wb_sample_x`/`wb_sample_y` (`F32`, normalized `[0,1]` image-relative coordinates, only meaningful when `wb_source == Sampled`), and reuse `wb_scale_version`'s existing versioning pattern for an `wb_algorithm_version` string/int so a re-derivation of the CCT math doesn't silently reinterpret an old sidecar's stored provenance. All three fit `FieldKind::F32`/`Enum` with no new codegen machinery. XMP keys live in the `papp:` namespace (Maple-authored, no ACR equivalent) alongside `temperature_seen`/`tint_seen`; omit-on-default the same way those two do.
- _Multi-image transfer_: absolute (copy the literal temperature/tint) is what #2239's paste already does. The "optional relative correction" mode this ticket owns is the first real relative-transfer case and should be built as the reference implementation for the transfer-mode framework #2436 introduces (§ below) — apply the _delta_ between the source's current and as-shot temperature/tint to each target's own as-shot reading, rather than overwriting the target's absolute values.

**Where it lives.** Sampler math and provenance fields: `raw-core` + codegen. Sampling UX: `wb-pad.component.ts` (web, replace `rgbToWb` call) and a new Apple eyedropper (none exists today) sharing the FFI-exposed estimator. Preset picker: new UI on both front ends reading the existing `whiteBalancePreset` vocabulary.

**Sequencing.** Independent of lens/batch/export work; depends on nothing else in this milestone. #2247 (the AWB bug fix) is a **soft dependency**: shipping an "Auto" WB mode that calls the currently-documented-broken `compute_awb` reproduces the same railed-tint regression this milestone would otherwise be fixing. Land #2247 first, or gate Auto WB's UI exposure behind it.

**Acceptance tests.** Golden-fixture CCT/Duv values for the new sampler against known neutral patches (reuse the `test-fixtures/references` neutral regions #2247 already characterized for `test_0017`/`test_0006`); round-trip tests for the three new sidecar fields across raw-core/Swift/TS; a parity vector (GPU live vs CPU reference) proving the provenance fields don't change rendered pixels (they're metadata, not inputs to `white_balance.rs`).

**Non-goals.** No auto white-balance-per-region (local WB) — that needs the mask infrastructure #2239 explicitly left uncopyable and unsurfaced. No batch WB transfer UI beyond what #2436's framework provides generically.

### #2435 — Deterministic lens resolver and geometry workflow (incl. #2230, #2231 follow-ups #3189/#3182)

**Scope.** Three correction sources in a deterministic priority order — embedded `OpcodeList3` (already shipped), an externally-resolved Adobe LCP profile (#2230, new), or explicit manual controls (new: perspective H/V, rotation, aspect, scale) — plus the two open threading gaps left by #2231 (#3189 distortion-inert signal, #3182 web decode-metadata export).

**Design.**

- _Resolution order_: `OpcodeList3` present → use it (existing path, unchanged). Otherwise, resolve an LCP profile by `(camera body, lens model, focal length, aperture)` read from EXIF — interpolating between the nearest focal/aperture-sampled entries in the matched profile — and evaluate its distortion/CA/vignette model into the **same pixel-domain application** the opcode path already uses, so this is a second _source_ for the same sink, not a second code path (the ticket's own framing: no lens-profile abstraction existed before this because #376 deliberately built none — this ticket is where it's finally justified by a second real caller, consistent with CLAUDE.md's YAGNI rule). Otherwise, expose the three manual scale sliders with no automatic correction — i.e. `lens_profile_enable` stays meaningful but scales nothing. Every resolution outcome (which source matched, at what confidence/interpolation distance) is surfaced to the UI, per the ticket's explicit "never silently apply an approximate match."
- _LCP distribution_ (#2230): Adobe ships on the order of 1,000 profiles; bundling them in the app is out of scope per #376's own prior ruling. Fetch-on-demand + a local cache, keyed by the same `(body, lens)` pair, mirroring the precedent already in the codebase for large, optional, fetchable assets — the Cloudflare R2 thumbnail-mirror cache (`docs/caching.md`) and the film-LUT catalog's `.mlut` files under `resources/film-luts/` are both "shipped or fetched, then cached locally, never re-fetched for an unmodified key" shapes worth following rather than inventing a fourth caching pattern.
- _Manual geometry_ (new fields: `geo_perspective_h`, `geo_perspective_v`, `geo_rotation`, `geo_aspect`, `geo_scale` — names indicative, final naming is an implementation call): unlike the LCP/opcode scales, these are **interactive** the way `crop`'s straighten angle is — a user drags a slider and expects a live preview — so they belong on the GPU per-tick path alongside `crop`, not the decode-product path the lens-profile scales use. This is a real architectural fork inside one ticket: same "Geometry" copy/paste group, two different pipeline tiers.
- _Third decode signal_ (#3189): `RawImage::lens_correction_distortion_inert()` (or equivalently `has_warp_rectilinear()`), threaded exactly like `lens_correction_ca_inert` — raw-core method → `raw-ffi` field on `MapleSceneLinearBufferF32` (all 5 call sites) → Apple's `PipelineRenderer` → `SceneLinearDecodeResult` → `DecodedSnapshot` → `EditSession`, greying the Distortion slider on vignette-only DNGs the same way CA is greyed today.
- _Web threading_ (#3182): the same three booleans (`has_lens_corrections`, `lens_correction_ca_inert`, and the new distortion-inert signal) need a `raw-wasm` getter on whichever struct actually feeds the Angular editor's live decode buffer — confirm this is the render worker's live-session entry point, not `MapleRender` (which may only back the legacy 8-bit thumbnail path) — threaded through the render worker's message protocol into `LibraryStateService` as a per-asset signal, and bound to `[disabled]` on `LensCorrectionsPanelComponent`.

**Where it lives.** LCP parsing + the shared correction-source abstraction + manual-geometry math: `raw-core` (CPU reference) and `raw-gpu` (WGSL, for the manual-geometry per-tick path only — the LCP/opcode scales stay decode-product with no GPU mirror, matching the existing three fields). FFI surface: `raw-ffi` (new fields, xcframework rebuild required). Fetch/cache: platform-specific (Apple `URLSession` + local cache dir, web `fetch` + IndexedDB, mirroring the film-LUT/R2 precedent each already has). UI: `LensCorrectionsSection.swift` / `LensCorrectionsPanelComponent` for the resolver source + confidence display and the two inert-slider gates; a new geometry panel (both platforms) for the manual sliders.

**Sequencing.** #3189 and #3182 are small, already-scoped, non-blocking follow-ups that can land independently and in parallel with the LCP work — they close gaps in the _existing_ opcode path and don't depend on LCP landing first. The manual-geometry sliders have no dependency on LCP either and can be built in parallel. LCP resolution is the long pole (new parsing, new fetch/cache infra, new resolver logic) and is the one piece that should be sequenced deliberately rather than parallelized against itself.

**Acceptance tests.** The 95%-of-fixture-set resolution-path acceptance criterion needs the CR2/RAF/ARW/NEF fixtures currently rendering with zero correction to gain either an opcode or an LCP match; extend `test-fixtures/references/manifest.json` accordingly. Resolution-order and interpolation determinism: unit tests pinning tie-break behavior for a focal/aperture pair that falls between two profile samples. GPU-vs-CPU parity for the manual-geometry sliders (new WGSL, needs the harness). Crop/mask coordinate stability through a geometry change: a regression test asserting a normalized crop rect re-projects correctly when perspective/rotation change the effective frame.

**Non-goals.** No profile _creation_ (camera calibration workflow) — only consumption of Adobe's published LCP set. No per-lens manual profile editing UI.

### #2436 — Semantic batch synchronization with progress and recovery

**Scope.** Turn #2239's synchronous, all-or-nothing `_pasteToSelection`/`onSyncSettings` loop into an operation with progress, cancellation, retry-only-failed, and a final per-asset summary, at a declared 2,000-image throughput/memory budget — plus the transfer-mode framework #2434 needs a home for.

**Design.**

- _Transfer-mode declaration_: extend the existing group table (`raw-core/src/types/adjustment/schema/groups/`) — the same place #2239 already declares group membership and copy exclusions — with a per-field transfer mode: `Absolute` (today's only behavior — copy the literal value), `Relative` (apply the source's delta from _its own_ baseline, e.g. white balance's as-shot-relative correction from #2434), `AssetRelative` (re-normalize against the target's own dimensions/state — crop's `{top,left,bottom,right}` fractions are already asset-relative by construction since they're normalized 0–1, so this mode mostly formalizes existing behavior rather than changing it), or `Unsupported` (the field is in a group but paste/sync should skip it — e.g. `auto_exposure`'s anchor role makes an unqualified relative transfer ill-defined). This is additive to the generated tables, so `codegen-drift` catches any Swift/TS mirror gap the same way it already does for group membership.
- _Orchestration_: because a 2,000-image sync has to survive being started, partially completing, and either being cancelled or the app/tab closing, it needs a persisted, resumable operation record — not the current in-memory `for` loop. Given Apple, Web Self Hosted, and the browser-only `maple-syrup` deployment have three different execution environments (native process with local file access; a server with Mongo and the existing `job-runner`; a browser tab with no server at all), this should **not** be forced through the one substrate that only one of the three has. See § 4 open decision on orchestration shape.
- _Preview before apply_: the ticket's "users select semantic groups and preview the affected settings" acceptance point extends the existing paste-settings dialog (`paste-settings-dialog.component.ts`, `AdjustmentGroupPickerSheet.swift`) — already group-scoped — to show a value diff per group, not just a checkbox list.

**Where it lives.** Transfer-mode table: `raw-core` schema + codegen (Swift/TS mirrors, same mechanism #2239 used). Orchestration: platform-specific batch runner behind a shared progress/cancel/retry/summary contract (§ 4). UI: extends `browse-shell.component.ts`'s existing sync/paste handlers and `AppShell.swift`'s equivalent, replacing the direct loop with a call into the new orchestrator.

**Sequencing.** Depends on #2434 only for the _reference_ relative-transfer case (white balance) — the framework itself can land first with `Absolute` as the only populated mode and `Relative` wired in once #2434's delta semantics exist. Independent of #2435, #2437, #2438.

**Acceptance tests.** A synthetic 2,000-asset selection (or the largest available fixture library) exercising the full progress/cancel/retry-only-failed/summary lifecycle, asserting a mid-batch failure never rolls back completed assets (already true of the current loop by construction, since each `updateAdjustment` call is independent — the new requirement is that a failure is _recorded and surfaced_, not swallowed) and that cancellation mid-batch leaves exactly the assets processed so far modified. Relative/asset-relative semantics: paired-fixture tests transferring white balance and crop across assets with different as-shot values/dimensions and asserting the _rendered_ result, not just the copied number, matches intent.

**Non-goals.** No mask/local-adjustment transfer (unsurfaced on both platforms, per #2239's own scoping). No cross-library sync.

### #2437 — Non-destructive variants, snapshots, and semantic history

**Scope.** A variant (independent sidecar-branch identity sharing one RAW's bytes), a snapshot (named checkpoint within a variant), and history (a bounded, semantic, reopen-durable action log) — replacing today's 32-entry in-memory-only undo ring with something that survives a relaunch, without introducing a second copy of any original file.

**Design.**

- _Storage level_: the epic's own non-goal — "No catalog-only dependency for variants or history" — already settles the headline open question here: variants and history must be reconstructible from the sidecar alone, the same way every other edit is. A catalog/DB row is allowed as an index or a fast-enumeration cache (Self Hosted already indexes everything server-side; there is no reason to _not_ have a `variants` collection for listing), but it can never be the only place a variant's edit state lives — losing the DB and re-scanning the filesystem must recover it, matching principle 1 ("the sidecar is the contract").
- _File layout_: today one `.xmp` sidecar exists per stem (`docs/xmp-canonical-format.md` §"Sidecar path"; images swap the extension, videos append it). The **default/primary variant continues to be that same file**, unchanged, so an existing library, a foreign tool, or an old Maple build reads a variant-naive photo exactly as it does today. Additional variants are new sibling files discovered by a glob next to the base sidecar — e.g. `IMG_1234.v2.xmp`, `IMG_1234.v3.xmp` — each carrying a small `papp:VariantId`/`papp:VariantName` header. This needs `SidecarPath.swift` and `xmp.ts`'s discovery logic extended to _enumerate_, not just compute, a sidecar path — a real but bounded change, isolated to the sidecar I/O layer on each platform (raw-core reader, Swift, TS, and eventually C#).
- _Snapshots_: local to one variant, so they live **inside** that variant's own sidecar as a new nested element list (mirroring the `rdf:Seq`/`rdf:li` machinery #365's tone-curve walkers already established, and structurally similar to what Lightroom's own snapshot passthrough already looks like) — `{name, timestamp, full AdjustmentModel}` per entry. A snapshot restore is one undoable action: it becomes a normal `beginEdit()`/model-replace, not a special code path.
- _History_: a bounded, append-only, semantic log **inside the sidecar** — discrete user-visible actions (applied preset X, pasted from asset Y, restored snapshot Z, reset), not a diff-per-slider-tick log. Render internals (a debounced refine pass, a cache invalidation) must never produce an entry — this is explicit in the epic's acceptance criteria and matches how `beginEdit()` already only pushes on gesture _start_, not per frame. Boundedness comes from periodic full-model checkpoints plus a rolling window of recent semantic entries, the same shape the existing 32-entry ring already uses, just persisted and periodically compacted instead of purely FIFO-dropped.
- _Switching variants "instant from cached preview state when available"_: reuses the existing `RenderedPreviewCache`/`TileKey` pattern, which already keys on `sidecar_mtime` (`docs/caching.md`) — a variant's sidecar is a distinct file with its own mtime, so the existing cache-key shape naturally gives each variant its own cache slot with no new invalidation logic, only a new key input (variant id) alongside the ones already there.

**Where it lives.** Sidecar discovery + snapshot/history element I/O: raw-core reader, `SidecarPath.swift`/new Swift writer code, `xmp.ts`, eventually the C# sidecar layer. Variant switching + snapshot/history UI: new panels on both front ends; `EditSession` and `EditorStateService` both need a variant-aware wrapper around the model they already hold (today there is exactly one model per open asset; a variant switch needs to swap which sidecar backs that model without re-opening the whole session).

**Sequencing.** The most structurally invasive of the five — touches sidecar discovery on every platform, which nothing else in this milestone depends on, so it can be built in parallel with #2434–#2436. #2438 (export) should be able to target "the currently active variant" trivially once this lands, but does not need to block on it — export today already exports whatever model is loaded, and a variant is just a different model-loading source.

**Acceptance tests.** Round-trip a multi-variant, multi-snapshot sidecar set through raw-core → Swift → TS → raw-core and assert byte-identical re-serialization (the existing golden-document discipline `xmp-canonical-format.md` already holds Swift/TS to). A missing-sidecar-for-a-known-variant-id scenario resolving deterministically (surfaced as an error state, not a silent fallback to the primary variant, which would silently discard the user's alternate treatment). A bounded-compaction test proving history surviving many sessions' worth of entries doesn't grow the sidecar unboundedly and doesn't lose the entries a compaction pass folds into a checkpoint.

**Non-goals.** No local-mask history (masks aren't surfaced at all yet). No cross-device variant sync beyond the existing sidecar-follows-the-file model — a variant is exactly as portable as any other sidecar edit, no more, no less.

### #2438 — Versioned export recipes and a resilient batch queue

**Scope.** A reusable, named export configuration — format, quality/bit depth, dimensions, output profile, rendering intent, metadata policy, naming template, destination, watermark, overwrite policy — in one platform-neutral model, plus a batch queue with cancel/retry/restart recovery, replacing both the single-asset-only dialogs on every front end and the thumbnailer-backed `batch_jpeg_export`.

**Design.**

- _Recipe model_: today's Apple `ExportFileFormat` couples format and color profile into one enum (`jpegSRGB`, `jpegP3`, …); the recipe model should **decouple** them — `format` (JPEG/TIFF/PNG/HEIC), `outputProfile` (sRGB/Display P3/…), `renderingIntent`, `qualityOrBitDepth`, `dimensions` (full or a long-edge cap; export never upscales, matching today's behavior) — because a naming template or a watermark policy is meaningless coupled to a specific format/profile pair, and because the "encoders declare supported subsets through the capability registry" design (a small static per-encoder table — e.g. HEIC only exists on Apple's encoder, PNG has no quality knob, TIFF has no watermark-compositing path today) needs orthogonal axes to declare support _against_. This is new: no capability-registry pattern exists anywhere in the codebase today, so keep it to the minimum table the five encoders (JPEG/TIFF/PNG/HEIC × the platforms that support each) actually need — YAGNI applies directly here.
- _Where the model lives_: `raw-core`, codegen-emitted to Swift/TS/C# the same way `AdjustmentModel` is — this is exactly the kind of cross-language, versioned schema principle 3 and the codegen pipeline exist for, and "recipes round-trip across declared surfaces without silent field loss" is precisely what the codegen-drift gate already guarantees for `AdjustmentModel`. A recipe is not part of `AdjustmentModel` itself (it doesn't describe a develop state) and should be its own generated type with its own schema version, independently bumpable from the adjustment schema version.
- _Batch execution_: extend the job-runner substrate (`src/api/src/job-runner/`) with a new handler that calls `export_from_raw`/`export_from_raw_with_film` against the recipe model — **not** the thumbnailer `batch_jpeg_export` currently uses — for Web Self Hosted, where the existing claim/lease/progress/cancel machinery already matches the acceptance criteria almost exactly (`reportProgress`, `shouldCancel`, per-item try/catch with a failures array is the same shape "retry-only-failed" needs, just re-queuing the failed subset). Apple and the browser-only `maple-syrup` build have no such server and need a local equivalent — see § 4.
- _Preview/export equivalence_: "preview and export use the same semantic adjustment state and declared terminal color conversion" is already close to true — `export.rs` reuses the same develop chain the canvas does — but needs an explicit test asserting it stays true as the recipe model's color-conversion knobs (rendering intent, specifically) are added, since that's a new axis the live-preview path doesn't currently vary.

**Where it lives.** Recipe schema + codegen: `raw-core`/`codegen`. Encoder capability table: one per platform, sourced from the same generated recipe fields. Batch queue: `src/api/src/job-runner/handlers/` (new handler, Self Hosted) plus new platform-local orchestrators (Apple, `maple-syrup`) sharing the transfer's progress/cancel/retry contract with #2436's batch sync (§ 4 — these two should share one orchestration shape, not invent two).

**Sequencing.** The recipe schema and capability registry have no dependency on the rest of the milestone and can start immediately. The batch-queue half benefits from #2436 landing first only in the sense that it's worth building the shared orchestration contract once — see § 5 for the recommended order.

**Acceptance tests.** Recipe round-trip (raw-core → Swift → TS → raw-core, byte/field-identical) mirroring the existing `AdjustmentModel` codegen-drift discipline. Golden fixtures for output metadata and ICC-profile policy per format (the ticket's own acceptance criterion). Disk-full/collision/permission/encoder-error injection tests against the new batch handler, asserting each produces an actionable per-item failure rather than aborting the whole batch. A memory-ceiling test for a large-file (100MP) batch export, given `docs/performance` budgets already gate cold-open memory and this is the same class of concern at N-times scale.

**Non-goals.** No cloud-delivery integrations (upload-to-service). No print-layout export. No collaborative/shared export-recipe library across users in this milestone — a recipe is local/per-user.

## 5. Implementation order

Sequencing is driven by two real dependencies — #2247 gates #2434's Auto-WB surface, and #2434's relative-WB transfer wants #2436's transfer-mode framework to exist first — plus the shared-orchestration-contract decision above, which should be settled once rather than drifting between #2436 and #2438. Everything else in this list is independent and can run in parallel.

1. **#2247** (AWB fix) — unblocks Auto WB in #2434; small, already fully diagnosed, no design work left, just the fix + the regression gate the ticket already specifies.
2. **In parallel:**
   - **#2434** (WB provenance + presets + sampler), sequenced internally so the CCT/Duv estimator and provenance schema land before the Auto-WB UI surface is exposed (waiting on #1 above only for that last piece).
   - **#2435** (lens resolver + manual geometry), with #3189/#3182 (the two small opcode-signal follow-ups) picked off first since they're independently scoped and unblock nothing else, then the LCP resolver and manual-geometry sliders in parallel with each other (different pipeline tiers, no shared files).
   - **#2437** (variants/snapshots/history) — fully independent of the WB/lens/batch work; the sidecar-discovery change is the long pole and worth starting early given it touches every platform's sidecar layer.
3. **Shared batch-orchestration contract** (the DTO/interface from open decision #4) — design and land once, before either #2436 or #2438 builds its platform-native orchestrator against it, so the two don't converge on incompatible shapes independently.
4. **In parallel, after #3:**
   - **#2436** (batch sync), whose transfer-mode framework should land before #2434's relative-WB transfer ships (or the two can be co-designed and landed together, since #2434 is the framework's reference case).
   - **#2438** (export recipes + batch queue) — the recipe schema and capability registry can start immediately (no dependency on #3), but the batch-queue half waits on the shared contract.
5. **Loose ends already tracked under milestone 14** but outside the five core sub-issues — #2232 (post-AgX tone curves), #3152 (wiring #2320's parametric split points into the curve builder + GPU-live params), #3186 (TS finite-value guard) — have no dependency on, and are not depended on by, any of #2434–#2438, and can land whenever their own PRs are ready without affecting this sequencing.
