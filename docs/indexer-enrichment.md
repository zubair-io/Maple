# Indexer, Workers and Search

Everything Maple knows about a photo beyond its bytes is produced by a background pipeline that lives in the API server's worker tier. A **discover sweep** walks each registered library folder one directory at a time and keeps the `assets` table in step with the filesystem — inserting new files, deduplicating identical content, repointing renames, tagging vanished files. Every asset then flows through a set of **stages** (EXIF, thumbnail, preview, vision captioning, geocoding, faces, transcription, search indexing), each of which is a small handler plus a target version number; a generic runner claims assets whose recorded version is below target, runs the handler, and writes the result back. Bumping a stage's `targetVersion` re-queues the whole library through that stage. Alongside the stages sit interval-driven **maintenance workers** (trash purge, missing-file reaper, one-shot migrations, deduplication, mirror replication, derivative audit) and **jobs** for user-triggered one-off work like a batch export or a panorama stitch, plus the operator's one-shots (mirror reconcile, face clustering, folder scans) on a lane of their own. Operators see and control all of it on Settings → Workers.

The whole tier runs in a separate, `nice`d child process spawned by the HTTP server, so indexing load can never starve or crash the API. The database holds what work exists; [Temporal](temporal.md) decides when each piece runs, and that page covers the lanes, outages and crash recovery common to all of them.

## AI provider connections and worker assignments

Settings → AI is the single editor for named provider connections (Ollama servers,
OpenAI, Anthropic, Gemini accounts), connection testing/model discovery, and worker
assignments. `GET/PUT /api/ai/connections/` reads/saves the connection list and
assignments together in `app_settings.enrichment.config.ai_connections`. API keys
are write-only; omitting a key preserves it only for the same connection ID and
provider. `POST /api/ai/connections/probe` tests/discovers using that connection's
saved key or the unsaved key supplied by the owner. All three routes require owner access.

Describe and Video Describe can mix Ollama and cloud connections, each with its
own model. Requests rotate round-robin through healthy connections with capacity.
Connection concurrency caps each worker's pool; Describe's stage
concurrency is derived from its assigned pool. Generated search chooses its own
text-generation connection/model: an Ollama server (grammar-constrained `/api/generate`)
or an OpenAI-compatible server (`<base URL>/chat/completions` with a `json_schema`
response format and the connection's bearer key). Its setting no longer follows
Describe after the first unified save.

Semantic search has no assignment: the `embed` stage computes document vectors with the
bundled bge-m3 on the server's CPU, in the same search child that embeds queries (see
[Search](#search)). Settings → AI shows it as a
read-only "Semantic search" section with the engine's status. Migration 0037 dropped the
former `embedder_url`/`embedder_model` settings and any saved `semantic-search` assignment,
and a save from an older client that still sends one ignores it.

An OpenAI connection has an optional base URL. Blank means `https://api.openai.com/v1`;
any other value points the same protocol and bearer key at an OpenAI-compatible server
(vLLM, llama.cpp, Strata, …), which model discovery lists unfiltered and the describe
workers record at `cost_usd` 0. Changing the base URL discards the saved key, so a key
is never sent to a host it was not entered for. A connection with a base URL may have no
key, for a self-hosted server without authentication: model discovery and Generated search
then send no bearer header, while Describe and Video Describe still require a key. Whisper
and face-model controls remain on their worker cards.

Before that first save, the API imports the effective legacy configuration for
review, preserving all Describe servers, capacity, worker model overrides, and the
generated-search model override. Reading does not rewrite existing settings. Saving
snapshots independent assignments atomically. Legacy AI/enrichment writes that
would compete with the registry return 409 after migration. Worker processes pick
up connection, credential and assignment changes through the existing two-second
config refresh. Assignments do not bump stage versions or reprocess existing assets
automatically.

## Where it runs

`src/api/src/index.ts` spawns `src/api/src/workers/worker-main.ts` as a child process (`ChildProcessWorker`, niced) and auto-respawns it on death with exponential backoff (1 s → 30 s, reset once a worker has lived 60 s). Setting `MAPLE_INDEXER_AUTOSTART=0` suppresses the spawn entirely — useful for running an API-only replica, which then runs no background work at all (see [Temporal](temporal.md#when-temporal-is-unreachable)).

`worker-main.ts` opens its own connection pool onto the same database file, initialises OpenTelemetry, loads the mirror registry, and calls `startWorkers()` in `src/api/src/workers/start-workers.ts`, which brings up:

- the stage orchestrator (`workers/orchestrator.ts`)
- the discover registration (the sweep itself runs on the Temporal host, below) plus a one-shot cache-GC pass per library
- the FFI decode pool (`ffi/ffi-pool-bootstrap.ts`)
- enrichment bootstraps (Nominatim health check, face-model preload, describe config)
- enrichment config refresh (`workers/enrichment-config-refresh.ts`)
- the Temporal host, which runs user jobs, folder imports, the pipeline stages, the discover sweep and the scheduled maintenance tasks
- the in-process side of maintenance (`workers/maintenance/support.ts`): the Settings → Workers entries for the reaper, migration and deduplicate workers, and the minute-by-minute mirror-registry refresh

It also publishes a status snapshot into the `worker_status` table every 2 s. That is how the API process — which has an empty in-process registry — can answer `GET /api/workers/status`.

RAW and bitmap thumbnail/preview decode and ONNX face inference run in dedicated child processes, so a decoder crash on those paths kills a child. `src/api/scripts/check-worker-isolation.sh` checks `onnxruntime-node` and `heic-convert` imports in selected worker-main directories, thumbnail/preview pool routing, and the face child's presence. It does not check Maple native imports or establish crash isolation for other Maple callers, including describe and video frame extraction (#3629).

## Discovery: keeping the catalog in step with disk

There is no filesystem watcher. `workers/discover/sweeper.ts` runs a breadth-first reconciliation sweep, one directory per tick, paced by `sweepDirIntervalMs` (default 250 ms) read from the `discover` row in `worker_config` on every tick — so pausing or re-pacing the sweep takes effect without a restart.

Each directory visit (`visitDirectory`):

1. Lists the directory. A directory holding a `.mapleignore` marker stops here and is excluded instead (see [Excluding a folder](#excluding-a-folder-mapleignore)). Otherwise, subdirectories are pushed onto a database-backed frontier queue (`workers/discover/frontier.repo.ts`), skipping dotdirs (notably `.maple/`, our own derivative cache — indexing it would create a self-feeding `.maple/.maple/…` loop) and the `_duplicates/` quarantine.
2. Does **one** indexed read for the assets already recorded in that directory, and diffs it against what is on disk. Files on disk with no row are "new candidates"; recorded entries absent from the listing are "missing candidates".
3. Re-stats every missing candidate before believing it. A `readdir` on an SMB share can succeed and return an incomplete listing; only a genuine ENOENT counts, and if the library root itself is unavailable the whole visit confirms nothing rather than mass-tagging present files.
4. Runs rename reconciliation, then emits ordinary `created` / `removed` events for whatever is left.
5. Reconciles the folder-level `.hidden` marker (`workers/discover/folder-hidden.ts`), and the folder's RAW+JPEG pairings (`assets.stack_primary_id`, `db/repos/assets.raw-jpeg-stacks.ts`, #5849): a JPEG beside exactly one same-stem RAW points at it, so search and the timeline can fold the pair. Only changed rows are written. See [api.md](api.md) § RAW+JPEG stacks.
6. Settles the private names a crashed relocation left in the folder (`fs/crash-left-temps.ts`, #5136, #5786), once untouched for a day (the later of modification and change time, so a rename or link counts) and not owned by this process. A verifying copy (`<name>.tmp.<pid>-<hex>.copy`) is removed. A displaced file (`.keep`: a Replace's kept occupant, a sidecar moved aside) is removed when its bytes live under another name (its link count is above one, or a byte-identical file still sits beside it); otherwise it may be the only copy of something and the filesystem cannot say whether the crash fell before or after the move committed, so it is published exclusively under a visible name beside where it was (`<name> (replaced).<ext>`, then `(replaced 2)`…; a sidecar becomes the `(conflict from move)` copy) and its private name is removed only after that. The next visit indexes the photo like any other, so the user sees it and deletes or keeps it; Trash is not used because its rows live in the database and a bare file under `.maple/trash` would be invisible there. A long name's short hidden form keeps its extension (`Recovered file (replaced).<ext>`). Any other private sibling is removed only when it is a hard link of the file beside it; unmarked names from earlier builds are otherwise left.

When the frontier for a generation drains, `advanceSweep` records a checkpoint (`indexer/checkpoint.ts`) and reseeds the root at the next generation, so the sweep loops forever and a restart resumes the in-progress generation rather than re-walking from scratch.

### The sweep on Temporal

The sweep runs on the same Temporal host as jobs and imports, on a task queue of its own, `maple-discover` (`workers/discover/discover-lane.ts`). Each library root has one long-lived workflow, `discover-<library id>` (`discover-workflow.ts`), which runs the `sweepRoot` activity over and over. One activity is one **slice** of the sweep (`sweep-slice.ts`): it claims, visits and paces directories exactly as described above, advancing to the next generation whenever one drains, and ends after about ten minutes. So a root costs Temporal about one activity per ten minutes however large or small the library is (a one-photo library walks dozens of generations inside that one activity), and the workflow continues as new every hundred slices, about seventeen hours, or sooner when Temporal suggests it.

- **Adding a folder.** Every ten seconds the host's connection check reads the library list and starts a workflow for any root that has none, so a folder registered while the server runs starts sweeping within about ten seconds, without a restart.
- **Removing a folder.** A slice checks that its root is still registered before every directory; once it is gone the slice reports so and the workflow completes.
- **Pausing.** Still the `discover` switch on Settings → Workers. A paused slice visits nothing and keeps heartbeating until it is resumed or its ten minutes are up.
- **Stopping in Temporal.** A workflow someone cancels or terminates in Temporal is started again at the next connection check; the slice it was running stops at the next directory boundary. To stop the sweep, pause it instead.
- **Shutdown, crashes and outages.** Stopping the worker tier ends every slice before its next file event, so a stop waits for one event at most, not for the rest of the directory in hand; a directory left half visited keeps its frontier lease and is visited again from the start once the lease (five minutes) expires. A slice heartbeats every 15 s whatever it is doing, so a worker killed mid-slice (a deploy, a crash) loses its root for about a minute: after one minute without a heartbeat Temporal delivers the slice again, to whichever worker is up. A redelivery for a root whose slice is still running in this process joins that slice instead of starting a second one (`discover-activity.ts`). Without a reachable Temporal server nothing is swept; the frontier and checkpoint stay in the database and the sweep resumes where it stopped once the server answers.
- **Many roots.** The lane runs up to 64 slices at once. A server with more roots than that sweeps them in turns, since each slice frees its slot within ten minutes.

The supported extension set lives in `workers/discover/types.ts`: RAW formats decoded through libraw, bitmap formats through sharp, PSD/PSB and Radiance HDR, video containers (metadata-only), audio, and a handful of metadata-only stubs (`.eip`, `.braw`, `.afphoto`, `.ai`) that are indexed for filename/size/date and never decoded.

### Per-event handling and content dedup

`workers/discover/handle-event.ts` is the chokepoint every producer funnels into — the sweep, imports, browse indexing, the pano handler.

- **created / modified** — hash the first 64 KB (`indexer/id.ts`), look up an existing row by `maple_id`, falling back to `sha1_head`. A hit **appends a location row** to the existing asset rather than inserting a duplicate; a miss inserts a fresh asset plus one `stage_state` row per registered stage at version 0. A unique-constraint collision with a concurrent insert falls back to the append path. Before either, a "modified in place to new content" guard compares the stored `sha1_head` for that exact `(library, path, filename)`; a mismatch marks the old entry `deleted_at` + `missing_since: 'content-changed'` so the stale row stops claiming the location.
- **removed** — re-confirm the file really is absent and the library root really is mounted, then stamp `missing_since` on **that one location**, never the whole asset. A photo that also exists elsewhere stays visible and claimable on its surviving entries.
- **renamed** — rewrite the matching `fileinfo` entry in place (the array length does not change) and re-arm the `embed` stage, because `filename` is the first line of the text it embeds.

Reserved trees (`.maple/`, `_duplicates/`) are refused for every event kind by `workers/discover/reserved-trees.ts`, whatever the producer.

### Rename reconciliation

`workers/discover/rename-reconcile.ts` handles the common case where a file is renamed **outside** Maple between two sweeps. Without it the sweep would see an unrelated removed+created pair, orphaning the `.xmp` sidecar and every edit in it.

The match signal is a cheap fingerprint — file size + EXIF capture time + camera serial — rather than a full checksum, because a pure rename never touches bytes and the sweep already pays for the EXIF read. The false-positive guard is structural: candidates on both sides are grouped into fingerprint buckets, and a pairing is only ever yielded from a bucket pair where **both** buckets have exactly one member. An ambiguous bucket declines outright and falls through to ordinary created/removed handling. A reconciled rename repoints the `fileinfo` entry, re-arms `embed`, and resets the `thumb` and `preview` stages (their cache keys are path-derived, so the derivatives must be regenerated at the new location — the cache files themselves are never physically moved).

### Missing files, damaged files, and the reaper

Three tags govern an asset's participation in the pipeline, and all three are enforced in one place — the stage claim in `db/repos/stage-claim.ts`:

| Signal                    | Set by                                                                                                | Effect                                                                                                     |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| per-entry `missing_since` | discover `removed`, a file-reading stage's ENOENT, the content-changed guard, a `.mapleignore` marker | that location is non-live; an asset with no live location drops out of reads and every stage's claim query |
| per-entry `deleted_at`    | content replaced in place                                                                             | same — the entry is dead, and is never re-stat'd (a different file may sit at that path)                   |
| root `damaged.since`      | a file-reading stage that exhausts retries, or a handler returning `{ damaged }`                      | the asset parks out of **every** stage and appears in the Workers "Damaged" list                           |

Tagging is the only automatic step. `workers/missing-reaper.ts` then reconciles, every 60 s (its maintenance schedule) in batches of 200:

- **Recover** — the file reappeared: clear the tag, and re-arm any file-reading stage that had died on it. Never age-gated.
- **Prune** — the location is confirmed gone and has been missing longer than `prune_window_hours` (default 12 h): `$pull` the entry.
- **Soft-delete** — that prune emptied the row: set `deleted_at` + `deleted_reason: 'reaped'` and emit a `delete` change event. The record keeps its fileinfo and derived data; trash-GC purges it after the trash retention window, and a content re-discover revives it in the meantime.

Safety properties, all load-bearing: the reaper boots **paused** and its paused state persists in `worker_config`; an install with no stored row counts as paused, and `/api/workers/status` reports it so, until an owner resumes it. Pausing pausing suspends only the record soft-delete — recovery and sibling-prune keep running. An unregistered library, an absent mount point, or an unstattable path skips the row entirely. Before a soft-delete, the parent directory is listed and a case/Unicode near-match vetoes the delete (a stored-path bug, not a deleted file). A pass that soft-deletes more than 25 rows _and_ more than half of what it scanned surfaces a persistent worker error as a systemic-misdetection tripwire.

A file that is still on disk but sits under a `.mapleignore` folder is not recovered: the reaper treats it as gone, so it ages through the same prune and soft-delete as a vanished file. It also skips the near-match veto, because the file is deliberately still there under its recorded name. If the marker check itself fails (a permission or I/O error), the row is skipped for that pass.

The prune window resolves DB row → `MAPLE_REAPER_PRUNE_HOURS` → 12 h default, clamped to 1 h–1 year, and is editable at `PATCH /api/workers/missing-reaper/prune-window`.

### Excluding a folder: `.mapleignore`

An empty `.mapleignore` file in a library directory excludes that directory and its whole subtree (#5398). It is an operator signal: Maple never writes, moves or deletes it, nor any file it covers.

1. **The sweep stops at the marker.** `visitDirectory` sees the marker in the listing and calls `excludeIgnoredDirectory` (`workers/discover/folder-ignore.ts`) instead of reconciling the directory. Nothing below it is enqueued or ingested.
2. **Indexed files leave the way deleted files do.** Every live location still recorded in the directory or its subtree is tagged `missing_since` with `missing_reason: 'mapleignore'`, and a `delete` (last live location) or `update` (a deduplicated copy survives elsewhere) change event is published. The missing-reaper takes over from there, unchanged: the asset leaves reads at once and is pruned or soft-deleted (`deleted_reason: 'reaped'`) after the prune window. Thumbnails, search and cloud-backup bookkeeping follow the reaper's existing rules. In the steady state, once everything is tagged, the visit matches nothing and writes nothing.
3. **Every other producer is refused at the chokepoint.** `handleEvent` checks the marker chain (the library root and every ancestor of the file's directory, `fs/mapleignore.ts`) before any created/modified/renamed event. That covers the import hand-off, browse indexing, the pano on-demand path and the folder rescan walk; the rescan walk also skips marked directories outright. The sweep checks the chain once per directory, before any other work in the visit (rename reconciliation moves sidecars, so it must never run under a marker), skips a directory under a marked ancestor or whose chain cannot be checked, and flags its own events (`markerChainChecked`) so the chokepoint does not repeat the check per file. An upload into an ignored folder, or one whose marker cannot be checked, is stored on disk but not catalogued. The library folder listing (`library/folder-listing.ts`) omits a marked folder from its parent's listing. Nothing moves an original under a marker, in two layers. By tag: trash and relocate never act on an excluded location (`missing_reason: 'mapleignore'`), not by default and not when a caller names the location explicitly (recursive folder trash, geo-relocate); the exclusion pass also relabels locations already tagged missing for another reason (keeping their `missing_since`, so the prune window does not restart), since their file may have come back under the marker. On disk: trash, relocate (and so rename, batch rename and geo-relocate), organize-by-location (source and destination), the DeDuplicate move and the backup-refile migrations (source and destination) each re-check the marker chain right before acting and refuse when it is ignored or cannot be checked, whatever the tag says (`refusesMoveUnderMarker` in `fs/mapleignore-guard.ts`); relocate also refuses a destination under a marker. Writers that hold only a path — every sidecar write or delete through `authorizeSidecarWrite`, the `<photo>.hidden` sibling markers, the canonical-sidecar migration, and the Trash purges (automatic and permanent delete) — use `refusesFileUnderMarker` from the same module, which walks every ancestor up to the filesystem root and exempts only Maple's own `.maple/` tree. Both guards check the path as given and its real path through symlinks, so a link from outside a marked folder cannot reach into one. An upload over an excluded original takes the normal replace path: the old bytes go to Trash with their asset, which retires that asset's claim on the path, and the new file stays uncatalogued until the folder is unignored and it is ingested as a new asset. `/api/fs/dir`, which the File Provider reads, still lists their files as plain un-indexed files and does not start indexing for them.
4. **Removing the marker** needs no special path. The next sweep descends again, the reaper recovers locations still in their window, and content-dedup revives assets it already soft-deleted.

Safety: only a regular file of that exact name counts (an `lstat`, so a directory or a symlink does not; case matching follows the volume, the same in every caller). A stat error is "unknown", never "ignored", and each caller resolves it safely (the chokepoint drops the event until the next sweep; the reaper skips the row; an upload is not catalogued). The library-root availability guard runs before anything is tagged, so an unmounted volume cannot look ignored. A marker at the library root excludes the whole library and is logged as a warning on every sweep. A large exclusion also trips the reaper's circuit breaker, which shows as a worker error on Settings → Workers.

## The stage machinery

A stage is one object built with `defineStage()` (`workers/stage-config.ts`) and handed to `runStage()` (`workers/run-stage.ts`). There are no child processes and no IPC: every stage runs in the worker process, and Temporal decides when (see [Scheduling](#scheduling-stages-on-temporal)).

### What a stage declares

| Field                     | Meaning                                                                           |
| ------------------------- | --------------------------------------------------------------------------------- |
| `name`                    | key in `worker_config` and in the asset's `stage_state` row for this stage        |
| `targetVersion`           | bumping it re-queues every asset below that version, and resets dead rows on boot |
| `dependsOn`               | upstream stages, as `'exif'` (≥ v1) or `{ name, minVersion }`                     |
| `defaults`                | `concurrency`, `maxAttempts`, `paused`, `pausedOnFirstBoot`                       |
| `claimResidual`           | optional extra SQL predicate `AND`-ed into the claim query                        |
| `tagsMissingOnEnoent`     | ENOENT means the original vanished — tag for the reaper                           |
| `tagsDamagedOnDeadLetter` | exhausting retries means the bytes are unreadable — tag `damaged`                 |
| `onProgress`              | optional per-batch and idle hook; `face-embed` (clustering) and `embed` use it    |
| `handler`                 | `(image, ctx) => Promise<StageResult>`                                            |

`pausedOnFirstBoot` is the mechanism for a stage that cannot work until an operator configures something external — a Nominatim URL, an Ollama endpoint, Cloudflare credentials, a whisper model. It seeds `paused: true` on the very first boot only; from then on the saved value wins. Without it, a version-gated stage would mark every asset permanently handled before its configuration existed.

### The claim query

The claim (`db/repos/stage-claim.ts`) scans one index over `stage_state` for rows of this stage whose version is below target, that are not `dead`, and whose retry backoff has elapsed, then checks each candidate: at least one location live, the asset not tagged `damaged`, and every `dependsOn` stage at its minimum version. That index does not grow with the stage list, which is the point of keeping stage bookkeeping in its own table rather than on the asset.

Taking a candidate is a compare-and-swap rather than a read-then-write: the claim is an `UPDATE` that re-asks every gate the scan asked, and whichever caller's write actually changes a row is the one that got it. The winner stamps a lease 15 minutes ahead into `next_attempt_at` — the same column the retry backoff uses, so a claim and a backoff share one gate — and every subsequent write to that row is fenced on the lease it was granted, so a handler that finishes after its claim was taken over updates nothing. A slow handler like `transcribe`, which runs the length of a video, renews instead.

A stage's optional `claimResidual` is `AND`-ed onto the claim, so it can only narrow. `transcribe` and `video-describe` use it to select on `stage_state.media_kind`, carried by a partial index over the video and audio rows, so they never sweep the photo library stamping "not media" skips — before that narrowing existed, each poll tick walked 323,000 rows to find nothing and burned 418 ms of CPU per second (#3795).

### Scheduling: stages on Temporal

`stage_state` stays the record of what every asset still needs and `worker_config` of whether a stage may run; Temporal only decides when a stage runs. Work goes to Temporal in batches, never one activity per asset.

1. **The lane asks.** The stage lane (`workers/stage-lane.ts`, task queue `maple-stages`) runs in the worker tier's Temporal host. About once a second, for every booted stage that is not paused and not already running a slice, it asks whether a claim would find anything — the claim's own candidate scan with a limit of one, which writes nothing (`stageHasWork` in `db/repos/stage-claim.ts`).
2. **Work starts a workflow.** If there is work, the lane makes sure the stage's workflow, `stage-<name>`, is running. Starting one that already runs is a no-op that adds nothing to its history.
3. **The workflow runs slices.** `stageWorkflow` (`workers/stage-workflow.ts`) calls one activity, `runStageSlice`, until a slice reports the stage drained, then completes. A slice polls for about ten seconds: it claims up to `5 × concurrency` rows (`deriveBatchSize`), dispatches them through a bounded pool (`workers/dispatch-pool.ts`) and writes them back. A full batch claims again at once; a short one waits about a second before claiming again, and an empty one also runs the stage's idle hook first. A batch is never cut short. A slice reports drained only if it claimed nothing at all, or the stage is paused, so a workflow stays open while work keeps arriving and completes 10 to 20 seconds after the last of it (the rest of the slice that found it, then one slice that finds nothing). That is about one activity every ten seconds per active stage, however many assets it moves. After 500 slices (about 83 minutes of continuous work), or when Temporal suggests it, the workflow continues as new so a backlog of millions never grows one history without bound.
4. **No work means idle.** While no workflow runs and there is nothing to claim, the lane calls the stage's idle hook instead (`onProgress(0, true)`), about once a second, which is what `embed`'s foreign-vector sweep and `face-embed`'s cluster-on-drain wait for. Inside a running slice the same hook runs on every empty claim.

Each stage runs at most one slice at a time, even if Temporal delivers an attempt twice; a stage's own `concurrency` lives inside its slice. A slice heartbeats every 15 s with a one-minute heartbeat timeout, so if the worker process dies mid-slice Temporal retries the slice elsewhere about a minute later, without ever timing out a healthy long batch. A slice that throws (a claim or writeback the database refused) is recorded on `/status` and retried by Temporal from 1 s, doubling to 30 s, without limit; a handler that throws is the stage's own per-asset retry below, not Temporal's. A slice ignores a cancel or terminate made in Temporal: its batch always finishes its writeback, and if work remains the lane starts the workflow again. Only shutdown aborts handlers: the worker tier stops every stage first, each waiting at most 30 s for its batch, and only then stops the Temporal host, whose own drain waits for running activities.

`worker_config` is re-read before every batch, at most every 2 s, and on every idle call (a paused stage still gets idle calls for exactly this), which is how a pause or resume written by the API process reaches the stage with no IPC. A pause ends the running slice before its next batch, within about 2 s plus the batch already in hand, and the workflow completes. If the lane's has-work check itself fails, the error shows on that stage's row in `/status` (Temporal stays "connected") and clears on the next successful check or slice.

While Temporal is unreachable, stages do not advance; the rows wait in `stage_state` (see [Temporal](temporal.md#when-temporal-is-unreachable)).

### Result shapes

A handler returns one of five things (`StageResult`):

- `{ patch }` — field values written atomically together with the stage's own success state. Handlers may not write `stages.*` keys themselves; the runner rejects that. An optional `invalidates: ['search-blob']` marks downstream stages stale in the _same_ write, so a crash can never land new fields without also re-arming the consumer. `describe`, `geocode` and `sidecar-metadata-index` all use this to force a search re-index.
- `{ wrote: true }` — the handler persisted its own output (e.g. `transcribe`), just record the stage state.
- `{ skip: reason }` — nothing to do and nothing retryable: no GPS, not a media file, a stub format with no decode path. Recorded as `last_error: "skip: <reason>"` with `attempts` reset, and the version **is** advanced, so the asset counts as handled.
- `{ rearm: { stage, reason } }` — an upstream artefact is missing even though that stage claims done (a moved cache directory, an interrupted write). The runner re-arms the named upstream stage, keeps this stage below target with its attempt spent, and the `dependsOn` gate parks the asset until the upstream completes. A pair that never converges dead-letters at `maxAttempts` instead of ping-ponging. The named stage must be one of this stage's dependencies.
- `{ damaged: reason }` — the handler already knows retries are futile (a 0-byte file). Marks the stage dead after one attempt and tags the asset. Only allowed on stages that set `tagsDamagedOnDeadLetter`.

### Retry, backoff, and dead-letter

The attempt counter is persisted **before** the handler runs, so an uncatchable native crash (SIGSEGV/SIGABRT in libraw or ONNX) still counts against the budget. A clean success or a skip resets it to zero.

A failure records `last_error`, `failed_at`, and `next_attempt_at`. The per-asset retry ladder (`workers/loop-policy.ts`) is 30 s → 2 min → 5 min → 15 min with ±20 % jitter — minutes rather than seconds, because the failures worth surviving are provider restarts and model loads, and jitter because provider outages fail every in-flight asset within the same second. An error carrying `retryable: false` short-circuits the budget. Reaching `maxAttempts` sets `dead: true`, which removes the asset from the claim query.

Operators triage dead assets at `GET /api/workers/:name/dead` and reset them with `POST /api/workers/:name/retry-dead`. Damaged assets are listed at `GET /api/workers/damaged` and cleared with `POST /api/workers/damaged/clear`, which also resets the damage-tagging stages' bookkeeping so the file is genuinely retried.

(The `enrichment` subdocument in `db/schema.ts` and the `enrichment/dead-letter.repo.ts` triage helpers predate this design. Nothing writes that subdocument today except a `$setOnInsert` default, and the routes built on it are not mounted; `stages.<name>.dead` is the live dead-letter surface.)

### Registering a stage

Three additions, all mechanical: `workers/stages/<name>.ts`, exporting the definition and a `start<Name>Stage()` that calls `runStage`; the name in `ALL_STAGE_NAMES` (`workers/stages/stage-names.ts`), which is what makes existing assets retroactively eligible and what the status counters key off; and a `{ definition, start }` entry in `stageRegistrations` (`workers/stages/manifest.ts`), which the orchestrator boots and the stage lane then schedules on Temporal (`stageManifest` is derived from it, and the type check refuses a name without an entry). A fourth, optional, gives the UI a real label instead of the generic fallback: a `STAGE_META` entry in `src/web/projects/maple/src/app/settings/workers/workers-stage-meta.ts`.

Boot is best-effort and retried: a stage whose starter throws (a missing ONNX model, say) is retried with the same 1 s → 30 s ladder while every other stage comes up, and it is pre-registered so `/status` reports it as an error row rather than silently omitting it.

**Describe configuration.** `/settings/ai` assigns an Ollama, OpenAI, Anthropic, or Gemini provider and model independently to `describe` and `video-describe` (#3635). Worker polling invalidates cached providers/prompts when assignments or instructions change, and enrichment polling invalidates credentials and server configuration. Existing in-flight work may finish with its prior settings.

Description and OCR remain derived database fields; no XMP sidecars are written. Because the preview is AVIF and provider inputs are JPEG, handlers re-encode in memory.

An image answer that fails the stage parser (an off-list enum such as `lighting: "indoor"`, malformed JSON, a missing field) is re-asked inside the same attempt, up to two more calls, logged at info (`describe: model output failed validation, re-asking`). Sampling varies between calls, so a repeat almost always parses, and the asset never touches the stage's attempt ladder or dead-letter. Only when all three answers are invalid does the last parse error propagate to the normal retry path. Each re-ask is a full model call, so a paid provider bills it and its charge joins `cost_usd` like any other. These re-asks are not server faults, so they never count against a server's circuit breaker, and timeouts or connection failures are never re-asked here: failover and the breaker own those.

Describe and video-describe accumulate reported provider charges in their respective metadata's `cost_usd`, including billed truncations, empty responses, and responses rejected by the stage parser. Failed attempts persist charges with the failure writeback even without a description; retries and later successful descriptions add to the recorded total without marking failed work successful. Calls without reported usage cannot be accounted for, and previously discarded charges cannot be recovered.

**`search-blob` depends only on the always-on stages,** so keyword search is available early. Every producer of the blob's text — describe, geocode, transcribe, video-describe, people renames — re-arms it when its output changes, and re-arms `embed` too, since the embedded text reads the same sources.

### maple_id derivation rules and version

The server and every client that mints a maple_id (Apple Filesystem, SMB and PhotoKit backup sources, the browser's Hosted mode) must date a file identically, because the primary form hashes the capture time. The rules that choose that date are versioned by `raw_core::id::MAPLE_ID_DERIVATION_VERSION`, which `tools/codegen.sh` emits as `MapleIdDerivationVersion.current` (Swift) and `MAPLE_ID_DERIVATION_VERSION` (API and web TypeScript). Device id caches (`.maple/id-cache-apple.json`, the browser's `maple-id-cache` IndexedDB store) stamp every row with the version and treat a row from another version as a miss, so ids derived by older rules re-derive once (#5106). Bump the constant in the same change that alters which date a client reads for any file type. The hash forms themselves are unversioned.

Which date a client reads, by file type:

- **Video** (`VIDEO_EXTS`, `SidecarPath.videoExtensions`, the web's `VIDEO_EXTENSIONS`): the QuickTime `moov` atom's `com.apple.quicktime.creationdate` key, else `mvhd` creation time, never EXIF (`indexer/video-metadata.ts`, `VideoCaptureDate.swift`, `video-capture-date.ts`). A file with no `moov` has no date and takes the fallback form (#5079, version 2).

- **Stills**: `asIsoDate(DateTimeOriginal) ?? asIsoDate(CreateDate)` over the raw ExifIFD tag 0x9003 / 0x9004 strings (`ExifCaptureDate.swift`, `captured-at.ts`, #5082). Those strings come from the tag bytes themselves — IFD0 to ExifIFD by ranged reads, ASCII only, trailing NULs then whitespace trimmed, first duplicate wins — in the shared `exif-capture-dates.ts` (the API's `readExif` and the browser) and `RawExifDates.swift` (Apple), for JPEG, TIFF-family (every RAW), PNG `eXIf`, WebP `EXIF` and HEIF. ImageIO is not used: it repairs `2024:6:1 12:34:56`, drops `2024:06:01T12:34:56`, and finds dates exifr's chunked reader misses, and exifr's chunked reader misses the ExifIFD of a 100 MP DNG that keeps it at the end of the file (#5090, version 3).

`test-fixtures/ids/derivation.json` lists files with the capture date and id the server derives; the API (`maple-id-contract.test.ts`), raw-core (`maple_id_derivation_corpus.rs`), MapleCore (`MapleIdDerivationContractTests`) and web (`maple-id-derivation-contract.spec.ts`) suites all pin it, so a client that dates a file differently fails its own suite. Its `optional` cases name gitignored RAWs under `test-fixtures/raws` (including the DJI and Hasselblad DNGs whose ExifIFD sits at the end of the file) and are skipped when absent.

Known divergence, not fixed here: an original date that JavaScript's `new Date(...)` accepts but that is not the EXIF `YYYY:MM:DD HH:MM:SS` form (`2015-11-14T14:26:58` from a Hasselblad `.fff`, `2024-06-01 12:34:56`, `2024/06/01 12:34:56`, a bare `2024:06:01`) is read by the server through `new Date(...)` in the indexer host's timezone, which no client can reproduce; the device falls through to `CreateDate` instead.

### Merging duplicate rows

When the exif stage upgrades an asset to a primary `maple_id` that another row already holds, `mergeIntoSurvivor` (`db/repos/assets.merge.ts`) folds the two into one in a single transaction. The survivor is the row with the earlier `indexed_at` (ties: lower id), not necessarily the row being processed. What it keeps:

- **Locations and backup history** of both rows, re-numbered above the survivor's. Rating, flag and colour label are copied only while the survivor still holds defaults, and the EXIF and screenshot flag only when the survivor has none.
- **Apple Photos links** move to the survivor; a link both rows hold (same device and local id) keeps the survivor's copy.
- **Derived data** (`db/repos/assets.merge-derived.ts`) is filled group by group where the survivor has none, and the survivor's own value always wins: description/OCR/vision with their provenance (`describe`), transcript and video description, place (`geocode`), faces with their embeddings and the person segmentation. Both rows holding the same kind of data keeps the survivor's and drops the other's.
- **Stage state follows the data.** A group the survivor inherits takes the condemned row's stage state when it is further along, so the survivor is not re-queued for work already done; a group it did not inherit is untouched, so its own stage run still fills it. Any inheritance re-arms `search-blob`, which composes the blob from that text. `embed` is re-armed by the `maple_id` change itself, and the stale vector is dropped.

Everything else keyed to the condemned row (its search blob, derivative-audit marks, stage bookkeeping) is removed with it by cascade.

### On-demand previews

A cold-cache `GET /api/preview/:slug/*` renders the preview in the API process, ahead of the `preview` stage's backlog (#5433, `indexer/ondemand-preview.ts`):

1. Concurrent requests for the same preview share one render. If the stage is already rendering that file, the request waits for the stage's render instead of starting a second one.
2. On-demand renders have their own cap: as many as the API process's FFI pool can run at once, so no render waits inside the pool where a disconnect can no longer skip it. It is not a setting, and the stage's concurrency does not affect it. A client fetching many previews at once is served that many at a time.
3. While any on-demand render is pending, the API tells the worker child over IPC, and the stage stops admitting new renders (`workers/background-preview-gate.ts`). Renders already running finish, so a viewer waits for at most about one render before theirs gets the CPU. The gate also admits no more stage renders than the worker's FFI pool has RAW workers, so extra work waits in the gate rather than in the pool's queue, where it could not be held back. The stage pauses for at most 10 s per run of continuous on-demand activity; after that it runs at full speed until on-demand activity stops, so heavy browsing cannot stall the backlog.
4. If every requester has disconnected by the time a render slot is free, the render is skipped. A render that has already started always finishes and writes its file, because the stage needs it anyway.

## Maintenance workers

These are not per-asset version-claim stages. Each is a task in `workers/maintenance/tasks.ts`, and each task is a [Temporal](https://temporal.io) Schedule, `maintenance-<task>`, that starts a `maintenanceWorkflow` run on the `maple-maintenance` task queue; the run's one activity calls the task's single-pass function in the worker child.

- **The database decides; Temporal keeps time.** Every task reads its interval and whether it is paused from its own settings. About every ten seconds the worker tier makes each schedule match — creating it, changing its interval, pausing or resuming it — and deletes `maintenance-` schedules for tasks that no longer exist, so a schedule edited or deleted in the Temporal UI is put back. Pause/resume and config routes on Settings → Workers write the same rows as before; the schedule follows within about ten seconds.
- **Paused means the pass would do nothing.** A schedule is paused exactly when configuration makes a pass a no-op: deduplicate paused, change-log-gc or derivative-audit disabled, migration paused or with no enabled unfinished migration, the mirror tasks while no library has a mirror, db-backup while automatic backups are off. A worker whose paused pass still does work keeps a running schedule and its own gate: the reaper still recovers re-found files while paused, generated-search still prunes.
- **One pass at a time, no backlog.** A run that comes due while the previous one is still going is skipped. After an outage or a restart, at most one missed run per task is made up: a run missed by less than the task's interval (at least a minute) still runs, older ones are dropped. A schedule that starts running — new, or resumed — runs its first pass at once. Because schedules live in Temporal, a restart of the server no longer sets off a boot-time pass of every worker.
- **A failed pass is a failed run.** Each run makes one attempt; the next scheduled run is the retry. Every pass stops between items or batches when the worker shuts down or the run is cancelled in Temporal, and the next run picks up where it stopped. The longest wait is one item: a single file copy for mirror-copy, one chunk of R2 lookups for derivative-audit, one library's model call for generated-search, and the snapshot step of a database backup.
- **Run now.** The API holds no Temporal client, so a run-now is a request in the `maintenance` settings document (`workers/maintenance/run-now.repo.ts`); the worker tier starts a `maintenance-<task>-run-now` run for it, even while the schedule is paused, and then clears the request. A run-now that finds the task's pass already running waits for it and then runs, so a forced pass is never lost to a scheduled one. The derivative-audit and generated-search "Run now" buttons are forced requests of this kind: the pass runs even while the audit is disabled or generated search is paused, and the route answers `already-running` while a request is pending or a pass is under way.
- **Without the worker tier or Temporal** no pass runs, and nothing piles up meanwhile (see [Temporal](temporal.md#when-temporal-is-unreachable)). Expired sign-in rows still stop working without the clean-up, because every read refuses them.

The reaper, migration and deduplicate workers also register into the in-process registry (`workers/pause-control.ts`), so the standard `/api/workers/<name>/{status,pause,resume}` surface shows and controls them.

## Jobs

`src/api/src/job-runner/` is the sibling subsystem for **user-triggered, bounded** work. A job is a row in the `jobs` table, and it runs on [Temporal](https://temporal.io):

1. A route inserts the row as `queued`, in one statement with its admission fence. That row is what every client reads from then on.
2. The worker tier relays the oldest queued row to Temporal once nothing else is running (the row relay in [Temporal](temporal.md#lanes), which imports share): one workflow per job, with the workflow id `job-<id>`.
3. The workflow runs one activity, which claims that row and hands it to the handler for its kind (`execute-job.ts`). Handlers report progress and must consult `ctx.shouldCancel()` between steps so an in-flight job can be aborted.
4. The activity records the outcome on the row, and the workflow ends the same way: completed, or failed with the handler's message.

**One at a time, in creation order.** Temporal is only ever handed one job. Several workflows waiting on one task queue start in no particular order, so the queue stays in SQLite, where `created_at` decides.

**A worker that dies.** Temporal notices when the heartbeat stops (five minutes) and delivers the job again; the new attempt takes the row over and resumes from the checkpoint the handler saved. A handler that throws fails the job, and that is not retried.

**Losing contact with Temporal.** A queued job waits and is relayed when the server returns. A running job keeps running: its handler does not stop because Temporal gave up on the attempt, it finishes and records the result, and the redelivery that follows finds the job finished and only reports how.

**Cancelling.** Through the API, or by cancelling the workflow in Temporal. Terminating the workflow cancels the job too.

**A workflow that is gone.** A job whose workflow was cancelled or terminated is cancelled; one whose workflow is missing or closed without settling the row (an emptied or different Temporal server, an upgrade from the release whose runner claimed rows itself) is submitted again. Each Maple server needs its own namespace; see [Temporal](temporal.md#one-namespace-per-maple-server).

Six user job kinds exist (`JobKind` in `db/schema.ts`, registry in `job-runner/handlers/index.ts`):

- `batch_jpeg_export` and `batch_recipe_export` — render the selected assets into an output directory via the shared FFI pool. See [export recipes](export-recipes.md).
- `batch_adjustment_sync` — applies one edit to a selection of photos, with a per-photo ledger.
- `pano_stitch` and `pano_preview` — spawn `maple-cli pano` over the selected assets and, for a stitch, import the result as a new asset. Admission allows one stitch at a time. A stitch holds the whole decode memory budget while it runs and passes it to the CLI as a memory limit, so a panorama too large for the server fails with the reason instead of being killed (#5835). See [pano](pano.md).
- `cloud_backup_restore` — restores from a cloud-backup destination.

### Operations

The operator's one-shots are job rows too, on a second lane, the `maple-operations` task queue (`job-runner/operation-queue.ts`). They use the same workflow, activity, workflow id, adoption, cancellation and redelivery rules as jobs; the jobs lane never relays them and the operations lane relays nothing else, so an operation never waits behind an export or a stitch, and a user job's order and pano admission are unchanged. Up to four run at once.

- `mirror_reconcile` — "Reconcile now": one scan of every mirrored library, then copy passes until the queue drains. Its progress is saved on the row about once a second, and `GET /api/mirror/status` reads the latest reconcile row. A reconcile whose worker died is run again from the start; the scan and copy are idempotent.
- `people_cluster` — `POST /api/people/cluster`. The pass goes through the worker tier's cluster coordinator, so it never runs beside an automatic one.
- `folder_scan` — the walk of a registered folder into the discover producer, after which the folder's `last_scan` is stamped. Registering a folder queues one; rescan and scan queue one and wait for it.

The database allows one queued or running reconcile, and one scan per folder: the insert carries the check, so two requests cannot both get in. A second "Reconcile now" or scan of the same folder joins the operation already going. Clustering is the exception: a pass already running may have read the database before the request arrived, so the request gets a row of its own, which the lane hands to Temporal once the running pass has finished. Its answer therefore always comes from a pass that started after the request, and the pass happens with the request's own threshold even if the caller has stopped waiting. A request joins another only when that one has the same threshold and has not started yet. Cancelling an operation that has not started yet ends it at once and frees its slot, and a new request never joins one whose cancel is pending. Routes that answer with a result (cluster, rescan, scan) wait up to 90 seconds, under the roughly 100-second limit of a Cloudflare tunnel; past that they answer 504 saying the work will finish in the background, and they stop waiting when the client disconnects. `/api/jobs` never lists operations, and only the owner can read or cancel one by id.

**Which to reach for.** Anything whose job is "eventually, every eligible asset gets property X" is a stage, not a job — a stage gets pause/resume, concurrency, retry/backoff, dead-letter, and a live progress row on Settings → Workers for free from the generic machinery, and it becomes retroactively eligible for the existing library the moment it is added to the manifest. A job is for a specific, user-selected request with no ongoing backlog behind it: export _these_ photos, stitch _this_ panorama.

## Imports

`src/api/src/imports/` copies a server-local folder into a library. `scan.ts` walks the source (following symlinks, with realpath cycle detection and a re-jail check against `MAPLE_ROOTS`), classifies files, pairs `.xmp` sidecars to their parent image, and groups everything into `YEAR/MM` buckets keyed on **capture** time — EXIF `DateTimeOriginal`/`CreateDate`, falling back to file mtime — so the folder a photo lands in matches the date it is shown under everywhere else. The user reviews and edits the buckets, and the create route freezes the per-file destination list onto the import document.

Imports run on Temporal exactly the way jobs do, through the same relay (`temporal/row-queue.ts`) on a task queue of their own, `maple-imports`: the create route inserts a `pending` row, the worker tier hands the oldest one to an `import-<id>` workflow once no other import is held, and that workflow's activity claims the row and runs `imports/worker.ts` for it. Imports go one at a time in creation order, and an import never waits for a job or a job for an import. The rules in [Jobs](#jobs) carry over unchanged — a redelivery for a finished import only reports how it ended, a cancel made in Temporal ends the import like one made through the API, terminating the workflow cancels the import, a lost workflow is submitted again, and a retried import runs again under the same workflow id. An import has no checkpoint of its own: the attempt that takes one over continues from the file outcomes already recorded in `import_files`, and the attempt it replaced writes nothing more (`ImportTakenOver`). An import left `running` by the release whose runner polled the table is adopted at connect.

Per image it copies the image first, then its sidecars under the name the image landed at, then hands the image to `handleEvent` for indexing. Dedup is decided at the image (`maple_id`, then `sha1_head`); a duplicate image _and_ its sidecars are skipped, because an orphan sidecar would be meaningless. Name collisions resolve to a free sibling (the sidecars follow the image's new name), an image or movie whose exact bytes are already at its destination is skipped together with its sidecars, and cancellation is observed between files with already-copied files left in place.

An attempt can stop partway through one group (an image or movie plus its sidecars): after copying a file and before recording it, or after recording some of the group's files and before the rest. The attempt that takes over a running import (`taken_over` on the claim) therefore finishes that group rather than judging it afresh (`imports/resume.ts`). Files are recorded group by group and in order, so it takes the first group that still has a `pending` file to be the one. In that one group, a pending image, movie or sidecar found at its own destination with the same bytes counts as copied, even when the sweep has catalogued the image in the meantime; the sidecars still missing are copied beside it; and the image is handed to the indexer with its sidecar-metadata index re-armed. A different sidecar already beside the image is kept, no renamed copy is made, and the import reports that sidecar as skipped. Nothing recorded says whether the earlier attempt had reached that group at all (it may have been paused between two groups, or stopped while still comparing files), so a file that was already in the library there is counted as copied too and gains any sidecar it was missing. Every other group, and every group on an import's first attempt, follows the rules above unchanged. An Auto Import taken over before its scan finished has copied nothing, so no group is treated this way. Three stops are not recognised: one after a group's last file was recorded and before the indexer hand-off (the sweep catalogues that image), one where the image had landed under a new name after a collision, and one where the import failed and was retried instead of being taken over.

## Search

Search has two layers, and the database layer is always there.

**Maple's own full-text index is the floor.** The `search-blob` stage writes `search_blob` — a lowercased, whitespace-split, deduplicated, alphabetically sorted token bag composed by `enrichment/search-blob.ts` from place metadata, the LLM caption, OCR text, the transcript, the structured vision fields (subjects, setting, activity, notable objects, tags), and named people. These sources land on different schedules, so a single recomputed field is what keeps them coherent. Auto-generated `Person N` cluster names are excluded — folding them in would pollute the index with the token "person". The blob lands in `asset_search`, and `assets_fts` is the full-text index over it, stemmed for English and folded for accent and case. A request with no free text (filters only, a bare date) never leaves this layer, and neither does any text request the engine below cannot answer.

What a person types is not forwarded to that index verbatim. `db/repos/search.fts.ts` re-emits every term as a quoted literal, because several characters people actually type — `*`, `:`, `^`, brackets, a leading `-`, the bare words `AND`/`OR`/`NOT`/`NEAR` — are operators to the index, and a query like `C++ (2019)` would otherwise be a syntax error rather than a search. A query that leaves no usable term behind matches nothing, which is deliberately not the same as having typed nothing at all: only a blank query means "no text filter".

**The in-process engine ranks text queries above it.** A `search` child process (see [api](api.md#in-process-search-4463)) holds the bge-m3 query model, every stored vector from the `embed` stage and a Tantivy keyword index, and answers a fused ranking in tens of milliseconds. `embed` renders each asset's text with `enrichment/embedder-document.ts` — the single source of truth for the document template and its byte ceiling — and stores the vector in `asset_vectors`; the child indexes the same rendered text for its keyword leg, so the two legs describe one document, and beside it the asset's `search_blob` as a second, half-weighted field, so vision tags the template leaves out still match by keyword (#4512). `EMBEDDER_TEMPLATE_SHAPE_VERSION` is the `embed` stage's `targetVersion` and the version of the child's on-disk index: a template change re-queues every asset and rebuilds the index. Template field order is load-bearing, because the rendered text is truncated before embedding, so the highest-value fields (filename, media type, people, place) come first.

**Documents are embedded by the same model, in the same child (#5445).** The `embed` stage runs in the worker tier, but the bundled bge-m3 lives in the API's search child, so a document batch travels worker → API → child over the IPC channels that already exist (`search/remote-embed.ts`, `workers/embed/bundled-embedder.ts`) and never runs on either event loop. The stage gathers up to 8 documents and sends them in runs whose size times longest text stays within 6,000 bytes (the tokenizer pads a run to its longest text, so a long transcript goes alone), one run at a time; the child serves waiting searches before the next run. A search whose 2 s budget runs out while it waits falls back to the database without restarting the child: only a request still running at its own deadline (2 s for a query, 120 s for a run) counts as wedged. A run that crashes or wedges the child fails its documents, so they dead-letter after three attempts; runs that were only queued behind it wait. On an M5 Max a typical document takes about 45 ms of CPU and a 5,000-byte one (a long transcript) about 650 ms. While the child is not running, still loading the model (a first boot downloads ~2.2 GB) or failed to start, a claim is deferred for 30 s without spending a retry, with the reason shown on Settings → Workers. The model's token window is bge-m3's full 8,192, as Ollama served it, so a long document is not cut at 512 tokens; a query is cut to its first 2,000 characters, about the 512 tokens it had before. Measured against the Ollama bge-m3 vectors recorded in `search/__fixtures__/bge-m3-ollama-reference.json`, cosine is above 0.99997 (the test requires 0.9999).

**A bge-m3 vector stays current whoever wrote it.** Rows Ollama wrote are tagged `bge-m3:latest` with the Ollama URL as their endpoint; rows the bundled model writes are tagged `bge-m3` with endpoint `bundled`. Neither the search child nor the stage's once-a-minute sweep compares endpoints, and both accept either spelling of the model, so switching a library from Ollama to the bundled model re-embeds nothing. The sweep re-queues only rows another model wrote (an old `nomic-embed-text` library, say). The first sweep after the switch also revives dead-lettered `embed` rows once, as `worker_config.ai_model` changes to `bge-m3 (bundled)`.

When the child is loading, restarting, failed, slower than 2 s, or `empty`, the request is answered from the database layer instead. A search never fails because the engine is unavailable. The engine's ranking is paginated by offset, as relevance is not a stored value a seek cursor could record; the database layer paginates the same way for a text query and by seek cursor for the default capture-time sorts.

## People and face clustering

`face-detect` and `face-embed` produce the raw material; `src/api/src/people/` turns it into people.

`clustering-job.ts` runs online clustering: for each face without a `person_id`, find the nearest person centroid under cosine similarity and assign it if the score clears the threshold (default 0.5), else create a new auto-named "Person N" seeded with that embedding. Centroids are stored as the L2-normalised mean of assigned embeddings, so cosine similarity collapses to a dot product. The pass is incremental and idempotent — re-running touches only unassigned faces.

`cluster-coordinator.ts` fires it automatically, from two triggers: the work→drained edge of the `face-embed` stage (via its `onProgress` hook), and every N faces embedded (default 500, `MAPLE_AUTOCLUSTER_FACE_THRESHOLD`) so people populate progressively during a long run rather than only at the end. Both triggers, and the manual `POST /api/people/cluster` (a `people_cluster` operation the worker tier runs, see [Operations](#operations)), share one single-flight guard that coalesces overlapping requests into exactly one follow-up pass — two concurrent passes would race on the same `person_id` writes.

The pure clustering core is isolated in `people/cluster-embeddings.ts` so it can be gated without a database. `src/scripts/test_face_clustering.sh` runs it over a committed JSONL fixture set and ratchets purity / NMI / V-measure / ARI / recall@1 against `test-fixtures/face-clustering/budgets.json`; `.github/workflows/face-clustering.yml` runs that on any change under `src/api/src/people/`. Both skip-pass when the fixture is absent. See [testing](testing.md).

## Operator surface

`GET /api/workers/status` (`workers/routes-status.ts`) — and the WS `workers-status` frame the Settings → Workers page actually consumes — reports, per worker:

| Field                                           | Source                                                                                     |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `status`, `inFlight`, `throughput`, `lastError` | the live registry snapshot, read from the `worker_status` row the worker process publishes |
| `pending`                                       | assets below target version, not dead, with a live location                                |
| `ready`                                         | the subset the claim query would actually pick up right now                                |
| `blocked`                                       | derived as `pending − ready` — everything waiting on an upstream stage                     |
| `dead`                                          | assets at `dead: true` for this stage                                                      |
| `config`, `batchSize`                           | `worker_config`, with `batchSize` derived as 5 × concurrency                               |

`status` is `running`, `idle`, `paused`, `stopped`, `error` or `stalled`. A stage is `stalled` (#5038) when it has made no progress for its stall threshold (`worker_config.stall_after_minutes`, default 60, editable per stage on Settings → Workers as "Stall after (min)") while it still holds claimed work, keeps claiming work that only defers, or nothing has polled it — a batch that hangs, or no connection to Temporal for that long. A deferral is not progress, so a stage whose every claim defers ("Backup destination pending or requires reconnect") reads as stalled instead of idle. `lastError` then explains it ("No progress for N minutes while work is waiting") unless a real error is already reported. A paused stage reports `paused`, never `stalled`.

Plus library-wide `damaged` and `newlyHiddenTotal` counts and a `countsAt` timestamp. None of the counts are computed on the request path (#3491): the worker's count refresher (`workers/status-counts.ts`) runs them one query at a time and persists the result as `worker_status.counts`, and the route reads that with the same keyed read that fetches the registry snapshot. The refresher is demand-aware — the status and migration routes and the WS broadcaster bump `worker_status.counts_wanted_until`, and only while that is in the future does it refresh quickly (backing off to 3× the last pass's duration, between 5 s and 2 min); idle, stage counts refresh every 10 min and migration counts not at all.

The payload also carries `memory`: one row per long-lived server process (#4445) — the API process sampled on the request, then the worker and its native decode and face children as the worker last persisted them to `worker_status.memory` — each with `process`, `pid` and the `process.memoryUsage()` fields (`rss`, `heapUsed`, `heapTotal`, `external`, `arrayBuffers`) and the sample time. The same numbers are logged once a minute by every process under the `memory` log component (`runtime/memory-telemetry.ts`): the worker's line adds per-stage in-flight counts and the FFI pool's busy/queued depth, and any process whose RSS crosses 4 GiB logs a warning (repeated at most every ten minutes while it stays there). Always on, no toggle — the point is that an OOM kill has a named culprit in the log that preceded it.

The counts themselves are cheap now — a dead count comes from an index alone, and pending/ready are range scans of the claim index — but they stay off the request path on purpose. The contract was never about what one count costs; it is that serving a page never goes near the backlog. Each migration's `remaining` is persisted the same way on its own state row, by the refresher and by the migration worker itself on every tick of an enabled migration; `GET /api/workers/migration/migrations` returns `null` for a migration the worker has not counted yet. The response always covers the full known set (`ALL_STAGE_NAMES` plus the reaper, migration, deduplicate, and discover), so rows never vanish when the worker process restarts — an absent worker simply reports `stopped`.

The rest of the surface (see [server API](server-api.md) for the full reference):

```
GET   /api/workers/status
POST  /api/workers/:name/pause | /resume | /retry-dead
GET   /api/workers/:name/dead
PATCH /api/workers/:name/config          # concurrency 1–100, maxAttempts 1–20, paused
GET   /api/workers/damaged
POST  /api/workers/damaged/clear
GET   /api/workers/missing-reaper/prune-window
PATCH /api/workers/missing-reaper/prune-window
GET   /api/workers/deduplicate/config
PATCH /api/workers/deduplicate/config
GET   /api/workers/migration/migrations
PATCH /api/workers/migration/migrations/:id
GET   /api/workers/performance           # decode-pool size, decode memory budget, live reservation
PATCH /api/workers/performance           # ffi_workers 1–16 and/or decode_memory_budget_percent 0–90
```

`pollIntervalMs` and `batchSize` are no longer knobs and a `PATCH` carrying either is rejected with a 400 rather than silently ignored. The `preview` stage's concurrency does not govern on-demand previews: those have their own small fixed cap and take priority over the stage (see [On-demand previews](#on-demand-previews)).

On the web side, `settings/workers/workers.vm.ts` supplies `STAGE_META` — group (Ingest / Enrich / Index), icon, human description, and which enrichment config panel a row expands into. A stage the server reports but the map does not know still renders, at the bottom of Ingest with a generic icon, so adding a stage does not _require_ a UI change. That module also pins `FIXED_DESCRIBE_MODEL` to mirror the server's locked describe model, which is why the UI shows it read-only.

## Configuration

Per-worker runtime knobs (`concurrency`, `maxAttempts`, `paused`, a `pause_reason` when a stage paused itself, plus discover's `sweepDirIntervalMs`) live in the `worker_config` table keyed by name. Domain configuration — Nominatim URL and rate limit, describe server list, whisper tier, face model directory and download URLs — lives in the `enrichment` row in `app_settings`, resolved by `enrichment/enrichment-config.resolve.ts` with environment variables only as a fallback for existing deploys. Per-feature settings (missing-reaper prune window, dedupe, derivative audit, map tiles, display) each get their own `app_settings` row.

New tunables belong in this settings system, not in new environment variables: a DB-backed setting is operator-toggleable at runtime and visible in the UI. Environment variables are reserved for bootstrap that must be known before the database is open — `MAPLE_SQLITE_PATH`, the port, secrets, and `MAPLE_INDEXER_AUTOSTART`.

Because settings are saved by the HTTP process while stages run in the child, `workers/enrichment-config-refresh.ts` polls the config row every 2 s in the worker and re-applies it — dropping the describe stage's cached server pool — so an edit in `/settings/enrichment` takes effect without a restart.
