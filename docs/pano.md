# Panorama stitching

Maple stitches panoramas from RAW frames with `maple-pano`, a crate in the Rust workspace that owns the whole job: decode the frames into scene-linear pixels, find and match features with two ONNX neural networks, verify each pair geometrically, solve every camera's orientation at once, then warp, exposure-match, seam and blend the result into one canvas. The output is a scene-linear Rec.2020 composite, written as a 16-bit PNG. It has two alignment strategies — **rotation** for a camera that pivoted in place, **tile** for a camera that translated (nadir mapping strips, film scans, flatbed art) — and by default it decides between them from the image content rather than from metadata. One shared orchestration function serves both callers, the `maple-cli pano stitch` command and the `maple_pano_stitch` C-FFI entry the Apple apps use, so the CLI and the app cannot drift apart.

The dependency that makes it awkward to ship is ONNX Runtime, which the feature detector and matcher run on. It is not committed to the repo and not bundled: macOS dlopens a dylib the user provisions, iOS statically links an official ONNX Runtime xcframework at build time, and the self-hosted server shells out to a `maple-cli` binary that its Docker image bundles (an operator can point Settings at a different one). Every surface therefore has a "not provisioned yet" state, and every downloaded artifact is SHA-256 pinned.

## The pipeline

`src/raw-pipeline/maple-pano/src/stitch/mod.rs` is the single orchestration. Its stage ordinals are part of the C ABI's progress contract:

| Stage | What happens                                                                           | Modules                                            |
| ----- | -------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 0     | Decode each frame once, derive priors, keep only a downscaled proxy                    | `ingest/`                                          |
| 1     | Load the ONNX models, extract features from every proxy                                | `models`, `features/`                              |
| 2     | Nominate candidate pairs, verify each, build the match graph; then select the strategy | `graph`, `robust`, `twoview`, `strategy`           |
| 3     | Re-localize verified matches at full resolution, re-verify                             | `refine/`                                          |
| 4     | Bundle adjustment over all cameras, then level the horizon                             | `ba/`, `leveling`, `local_align/`                  |
| 5     | Canvas → gain → warp → seam → blend                                                    | `canvas/`, `gain/`, `warp/`, `composite/`, `blend` |

Both strategies share stages 0–2 — the decode, the ML pass, and the match graph — and diverge only in the tail, so choosing tile costs no second decode and no second ML run.

### Ingest and priors

`raw_core::decode_for_pano` (`src/raw-pipeline/raw-core/src/pipeline/pano/mod.rs`) is the single pixel source. Both it and `read_pano_metadata` are panic boundaries: rawler rejects some inconsistent on-file metadata with a bare `assert!` rather than an error, and the ingest runs on user-selected assets inside the Self Hosted job-runner's `maple-cli pano stitch` subprocess, so a caught panic surfaces as `raw_core::Error::DecodePanicked` → `PanoError::RawDecode` — a failed frame, never a dead process (#3230). It runs the canonical develop chain truncated **before every display-prep stage** — no auto-exposure, no capture sharpening, no view transform — so descriptors and exposure solving see unbiased pixels. `ingest/` turns that into planar f32 R/G/B in scene-linear Rec.2020 D65, plus a 1-bit-per-pixel validity mask. Validity is born at decode: the DNG DefaultCrop drops the optical-black border and demosaic margin, so every surviving pixel starts valid and later stages only ever _remove_ validity (warp marks out-of-frame, and so on).

`ingest/priors.rs` reads the EXIF focal length (converted to pixels) and, on DJI frames, the gimbal yaw/pitch/roll from the `drone-dji` XMP namespace — parsed namespace-aware, because two different namespace URI variants are in the wild. Priors are advisory throughout: they seed initialization and nominate candidate pairs, never decide anything.

`ingest/proxy.rs` produces the long-edge-capped proxy features run on. The default cap is **1600 px** and that number is measured, not chosen: 1280 (ALIKED's native input size) starved the matcher on the acceptance set, where `pano_01` regressed to the tile strategy with 19 orphans, versus rotation with zero frames dropped and mean residual 1.13 px at 1600. The proxy feeds only the match and solve phases, not the composite, so the larger cap costs essentially no memory.

### Features and matching (ONNX)

`features/aliked.rs` runs **ALIKED-N16rot** (detector plus 128-D descriptor, top-2000 keypoints baked into the graph). `matching/lightglue.rs` runs **LightGlue** paired to those descriptors, returning index pairs and confidences. `glue.rs` adapts the matcher's records into the geometry side's `PixelCorrespondence` input.

`models.toml` in the crate root is the manifest: filename, SHA-256, byte size, source URL, and license for each model. The ONNX files are **not committed**. `models::ModelDir::resolve` reads them from the directory named by `MAPLE_PANO_MODELS` (or an explicit path) and verifies size and digest before any session is created — a mismatch is a hard error, never a fallback. The manifest also records why the shipped detector is `n16rot` rather than the spec's `t16`: no public ALIKED-t16 ONNX export exists, and swapping one in later is a manifest re-pin, since the Rust side reads keypoint count and descriptor width from the tensor shapes at runtime.

ONNX Runtime itself is loaded two ways, which is why `maple-pano` has two Cargo features over the same `ort` dependency:

| Feature     | Target             | ORT linkage                                                                                                                                                |
| ----------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ml`        | macOS / host       | `ort/load-dynamic` — dylib dlopen'd from `ORT_DYLIB_PATH`, with a `libloading` preflight probe so a missing dylib becomes a typed error instead of a panic |
| `ml-static` | iOS, iOS simulator | statically linked against the official ONNX Runtime iOS xcframework via `ORT_LIB_LOCATION`                                                                 |

Static linking on iOS is not a preference — the iOS sandbox blocks `dlopen` of arbitrary paths.

### Classical fallback (no ONNX)

A third feature, `classical-features`, builds the whole stitch pipeline without ONNX Runtime or model files. `features/classical.rs` finds corners on the log of the frame's luminance (so two frames shot at different exposures still produce the same corners), across a Gaussian pyramid of several octaves. At each scale it scores corners with the Harris measure `(AC−B²)/(A+C+ε)`, rejects edge-like points, and keeps only the strongest point in each neighbourhood. It then describes each corner with a 128-value histogram of gradient directions, measured relative to the corner's dominant orientation so that a rolled camera still matches. The histogram is stored in RootSIFT (Hellinger) form, L1-normalised and then square-rooted, so that one strong edge cannot dominate the comparison. The matcher keeps a pair only when each point is the other's closest descriptor and the closest is clearly better than the runner-up. It emits the same records LightGlue does, so glue, graph and everything after it are shared.

`StitchOptions::feature_engine` picks the engine per run, defaulting to ML when that is built in. In `maple-cli`, the `pano-classical` build feature enables the classical path. When both `pano` and `pano-classical` are built, `pano stitch --features-engine classical` selects it. The CI gate `tests/classical_gates.rs` renders a synthetic pair and requires the recovered relative rotation to fall within the 0.3° two-view gate. The test uses a value-noise scene (`testkit::value_noise_source`), because the renderer's default scene has too few distinct corners for a corner detector to work with.

The classical path is clean-room code. No ICE-derived tables, binaries, or learned descriptor projections are in it.

### Match graph and pair verification

`graph.rs` builds "a graph, not a chain." Candidate pairs come from pluggable providers: `CaptureOrderProvider` (consecutive frames in input order) and `GimbalPriorProvider` (pairs whose prior view directions are closer than 1.5× the per-image field of view). Each candidate is verified by `robust::verify_pair`, a MAGSAC-style robust estimator over the closed-form relative rotation in `twoview.rs` (bearings plus a Wahba solve, backed by the Jacobi eigensolver in `eigen.rs`), and becomes a verified edge only with enough inlier support. The builder reports connected components and orphans, because the rule is to stitch the largest component and report the orphans — never silently drop a frame or force-align it.

Drone surveys and camera arrays can declare their capture layout instead (`--grid ROWSxCOLS`, `--grid-order raster|serpentine`, optional `--grid-diagonals`; `StitchOptions::grid`, #4519). On repetitive nadir terrain the global nominators misfire: descriptor top-k ranks unrelated fields and roofs as similar, and a fixed nadir gimbal puts every frame in every other frame's prior cone, so verification runs on nearly every pair and some false loop closures pass. With a grid, `graph/grid_prior.rs`'s `GridPriorProvider` replaces all of them on every graph build (rotation, focal rebuild and tile paths alike, via `stitch/graph_build.rs`). It nominates each frame's grid neighbours plus the pairs that share a neighbour, a fixed handful per frame. After verification, `graph/grid_gate.rs` always keeps neighbour edges. Any other edge survives only if both of these hold:

- **Distance.** When both frames carry a DJI GPS fix (`drone-dji:GpsLatitude`/`GpsLongitude` plus `RelativeAltitude`, parsed into `FramePriors::gps`) and an EXIF focal, their centres must be closer than the mean ground length of the frame diagonal at nadir (`altitude · diagonal_px / focal_px`). Without GPS, the frames must be at most two grid cells apart.
- **Cycle consistency.** Composing the verified edges of some triangle through a shared neighbour must reproduce the edge's own relation. On the rotation path that is the relative rotation, within 2°. On the tile path — translation-dominant nadir surveys, where the rotation verifier runs at a placeholder unit focal — it is a robust 2D similarity fitted to each edge's inliers, and the composed and direct transforms may send the edge's own inlier points at most 1 % of the frame diagonal apart (median), measured inside the overlap so per-edge noise is not extrapolated to the frame corners.

Rejected loop closures move to `MatchGraph::rejected` with their reason, and the stitch report's `match_graph` block lists candidate pairs, verified edges and every rejection. A serpentine grid's reversed passes, including a short final pass, map back to cells by index alone. Without `--grid`, nomination is unchanged.

### Full-resolution refinement

Matching happens on proxies, so match accuracy is bounded at proxy scale — the matcher's roughly half-a-proxy-pixel floor is about 3× the full-resolution residual budget at a 1600 px cap on a 5300 px frame. `refine/` closes that gap: every verified correspondence is re-localized on the full-resolution frames with a zero-normalized cross-correlation template search and a 3-point parabolic sub-pixel peak fit, so bundle adjustment consumes full-resolution accuracy in full-resolution coordinates and the residual budgets mean what the spec intended. Correspondences that fail to refine are counted separately (`fallback_matches`) rather than dropped.

### Bundle adjustment, leveling, local alignment

`ba/` refines all camera rotations plus shared intrinsics (focal, `k1`, `k2`) by minimizing symmetric reprojection error over every verified inlier, with a Huber loss at δ = 2 px. It is Levenberg–Marquardt with analytic Jacobians, rayon-parallel residual evaluation, and an in-tree dense Cholesky — no external solver, consistent with the crate's hand-rolled `math`/`eigen` and zero-dependency policy; even at 150 cameras the state is only about 500 parameters. A pure-rotation cost is invariant under a global rotation, so the gauge is fixed by freezing the first frame of the active component. Each solve runs two stages: rotations only with intrinsics frozen, then a joint solve — otherwise wildly wrong early residuals push focal and distortion off before the rotations settle. Distortion is kept inside the model's one-to-one domain: a match whose ray lands past the lens fold scores the invalid-block penalty rather than a residual, and a step that would put the fold inside any frame's corners is rejected (#5501).

`leveling.rs` then applies one global rotation to level the horizon: under a leveled sweep every camera's x-axis lies in the horizontal plane, so the up direction is the least-eigenvalue eigenvector of the scatter of solved x-axes. This is the fix for the "banana" bend in long strips.

`local_align/` (Stage F) absorbs what a pure rotation model structurally cannot: centimetre-level camera position drift. The tile path reuses the same fit for terrain parallax (see the tile section). The correction is a strongly regularized per-frame **bilinear mesh**, and the module documents why it is not an affine — an affine delta reduced dropped frames' mean residuals by only ~12% on the 21-frame DJI set and never moved their maxima under budget, because parallax displacement depends on scene depth, which varies across the frame. A bilinear mesh is the coarsest model that can represent that; it subsumes the affine exactly.

### Compositing

`composite/` orchestrates canvas → gain → warp → seam → blend.

`canvas/auto.rs` picks the projection from the camera set's angular extent — under 60° rectilinear, 60–130° cylindrical, over 130° spherical — and sizes the canvas to preserve the maximum input angular pixel density, under a total-pixel cap (default 256 megapixels).

Vertical pitch sweeps (towers, waterfalls) get a transverse surface instead, whose axis is the horizontal pitch axis rather than the world vertical, so the sweep never reaches the standard cylinder's `tan φ → ∞` pole. `canvas/transverse.rs` fits that pitch axis to the camera optical axes and measures their spread around it: when the pitch extent exceeds 55° and 1.3× the cross-sweep (yaw) extent, the set gets transverse cylindrical, and above 120° transverse spherical. A level yaw ring never qualifies, because its cross-sweep spread exceeds its elevation spread. On a transverse canvas the columns carry the bounded cross-sweep coordinate and the rows carry the periodic pitch angle, so a closed pitch ring wraps between the top and bottom rows.

`gain/` solves photometric compensation in _linear_ scene light as a per-frame gain plus a small additive bias. `gain/overlap.rs` gathers geometrically corresponding samples for every overlapping pair (each frame's strided grid reprojected into the other, thinned to at most 4096 per direction, with each sample's position in both frames) and measures each frame's signal window from its own content: white is the 99.5th percentile of the per-pixel peak channel, and samples are usable only when no channel is above 0.89× that white (ICE's 0.95 display clip decoded to linear) and the fitted value sits above about white/517 (ICE's 0.025 display floor). `gain/fit.rs` fits `I_j ≈ a·I_i + d` per pair and channel slot by IRLS with Huber weights at 1.5σ and a MAD noise scale, seeded from the median ratio so moving or misregistered content cannot lever the slope; an overlap whose intensity spread is too narrow to separate slope from offset falls back to a pure gain. `gain/solve.rs` solves log-gains over the pair graph with edge weights `min(n, 3000)/(σ² + 0.0004)` and a weak prior, gauged to geometric mean 1, then a bias per frame under those gains with a zero-shrinkage prior worth a quarter of the strongest possible overlap, clamped to ±1% of the reference white so it absorbs only black-level and flare offsets. A frame with no usable overlap keeps gain 1 and bias 0. `gain/streaming.rs` is the memory-bounded variant: it sweeps each stored frame once in 256-row bands (#5566), so no whole frame is resident, and builds the same overlap set incrementally (forward direction only). `gain/vignette.rs` is the blind falloff fallback (#4522) for frames whose ingest corrected no lens falloff (no OpcodeList3 gain opcode and no bundled lens profile): frames are grouped by lens identity (make, model, focal length, sensor dimensions), and each group shares a radial correction `V(r) = (1 + q·r²)²`, `q = k² ≥ 0`, with `r²` normalised elliptically about the frame centre (2 at a corner). `k` is solved jointly with per-frame log-gains from the overlap samples' log ratios by Gauss–Newton with Tikhonov damping and Huber reweighting, bounded to `[0, 1.5]`, seeded at 0.2, 10 iterations; a group with fewer than 256 usable correspondences keeps `q = 0`. The samples are then flattened and the affine fit and gain solve above run on them, and the warp multiplies each tap by `V(r)` at its source position. The same estimator (`gain/vignette.rs`, fed per-point correspondences) runs on the tile path: `tile/sampling.rs` makes one extra coarse canvas scan (about 250k grid points) collecting raw correspondences, the estimated falloff is divided out of every sample of the main scan before the gain, shared-ramp and residual-field layers are solved, and `warp_to_tile_region` applies it per tap. The batch `composite()` takes lens identity through `CompositeOptions::lenses`. Frames corrected at ingest never take part, and a set with no uncorrected frame skips the estimate (and the extra scan) entirely. Both stitch reports list `q` per lens group under `vignette`.

On the rotation strategy a coarse **residual exposure field** (`gain/field.rs`, `gain/field_solve.rs`, #4521) then absorbs the smooth low-frequency mismatch a per-frame gain and bias cannot express — a sky gradient, flare, leftover vignetting. Every frame is warped once onto the ~1 MP seam canvas with its photometry applied (one frame at a time, warped in 32-row canvas strips from the rows each strip taps, keeping only that frame's log-luminance), and wherever two views overlap their log-luminance difference becomes a sample at the nearest node of a coarse lattice over the canvas (periodic along the wrap axis on a full-wrap canvas: columns, or rows on a transverse canvas). The median per (pair, node) is the residual, and one log correction per view and node is solved from a data term on those residuals, a smoothness term and a small shrinkage term `μΣδ²`. A view's unknowns are only its overlap corridor — nodes with residual data, dilated by two lattice rings — and the field is held at zero on the corridor's outer boundary, so a view's interior keeps the exposure its photometry gave it. The lattice spacing keeps every view at or under 2048 unknowns, and the solve is the same matrix-free conjugate-gradient solver the tile strategy's residual fields use (`screened_cg.rs`). The tiled composite multiplies each warped strip by `exp(δ)`, sampled bilinearly — never a negative value, no extra buffer. `CompositeReport::exposure_field` records the lattice, unknown counts and the low-frequency seam step (weighted RMS log difference over the residual nodes) before and after.

`warp/` is a validity-aware inverse map: canvas pixel → world direction → camera forward projection (rotation, intrinsics, distortion) → bicubic Catmull-Rom tap on the source, with validity-weighted renormalized kernel taps so frame edges and masked holes never smear into the output. The per-frame gain and bias (`gain·v + bias`) are folded into the sampling loop.

Seam placement is one of two strategies (`seam::SeamStrategy`, #1179), chosen per run and recorded on `CompositeReport`/the CLI's `StitchReport`:

- **Voronoi** (default) is by source-border distance: each covered canvas pixel belongs to the frame whose projection of it sits deepest inside that frame. Deterministic and content-blind.
- **Graph-cut** (`--seam-strategy graph-cut`) is content-aware: `seam::pairwise::cut` builds a Boykov–Kolmogorov max-flow/min-cut (`seam::bk`, ported from the closed PR #17 prototype) over a pair of overlapping frames, with a data term that's the gradient of the two frames' _difference_ image (near-zero on a well-aligned region even under a residual exposure mismatch, spiking wherever content is misaligned or moving) and a smoothness term that discounts cost in areas of high local contrast (a handoff there blends into existing detail; the same handoff in a flat sky or wall is what a viewer's eye catches). `seam::labels` resolves the N-frame case by repeatedly applying that pairwise cut as an alpha-expansion move over every overlapping pair until the labelling converges, then feathers the result by one blend-band width. Because content-aware seam finding needs overlapping frames' actual pixels together — something the tiled path's "one frame resident at a time" streaming can't provide — `seam::masks` runs the whole label solve once on a cheap downsampled "seam canvas" (capped at 1 MP total, so any one pairwise overlap stays well under the spec's ~2 MP) and hands the tiled composite a bilinear lookup ([`SeamMasks::weight`]) instead of full-canvas-sized masks, keeping the #1254 memory bound intact. `seam::bk` follows Kolmogorov's tree conventions and is checked against a dense Edmonds–Karp reference on random heterogeneous-capacity grids, so every completed solve is an exact minimum cut. `seam::pairwise` bounds each solve at a fixed `MAX_ITER` augmenting iterations as a runtime guard; a cut that reaches it is returned as unsolved, never read as a minimum cut. The run then falls back to the Voronoi seam and `CompositeReport::seam_strategy` (the report's `seam_strategy`) says `voronoi`; with seam constraints, which Voronoi cannot honour, it fails with `SeamConstraintError::Unsolved` instead. `COST_SCALE` stays at `1e3` (a `1e6` scale once took minutes on a real pano_01 overlap; `seam::pairwise::tests::perf_probe_realistic_textured_overlap` guards that). Voronoi stays the default: every `pano-budgets.json` ratchet is measured against it, and graph-cut is opt-in until a follow-up re-baselines those budgets with it as the default.

Graph-cut seams also take **user constraints** (`seam::SeamConstraint`, #4520), for intent the cut cannot infer: `ForceInclude(frame, rect)` keeps that frame's content across a rectangle (one instance of a moving subject), `ForceExclude(frame, rect)` keeps it out (a passer-by). Rectangles are output-canvas pixels. `seam::constraints::rasterize` maps each onto the seam canvas as every seam pixel the rectangle touches, plus a halo of the feather radius and one pixel, so after feathering and bilinear upsampling the full-resolution rectangle shows exactly the included frame, or none of the excluded one. The halo is best-effort and gives way wherever it would contradict another constraint; the core never does. Contradictions in the core are typed `SeamConstraintError`s, never silently resolved: two includes for different frames on one pixel, an include outside its frame's footprint, a frame both included and excluded, or excludes that leave a covered pixel with no frame to show. During the label solve each pixel's candidate frames are restricted by its pins, and every pairwise expansion move wires a pinned pixel to its terminal at infinite capacity, so the cut routes around the region along the cheapest contour instead. With no constraints the solve is bit-identical to before (golden hashes in `seam/tests.rs`). `StitchOptions::seam_constraints` names frames by input index and the stitch renumbers them past any frames bundle adjustment dropped: an exclude on a dropped frame already holds, an include on one is an error. Constraints need graph-cut on the rotation strategy, and anything else is rejected rather than ignored. On the CLI, `maple-cli pano stitch --seam-strategy graph-cut --seam-constraints constraints.json` takes a JSON array of `{ "kind": "include" | "exclude", "frame", "x", "y", "width", "height" }`, with `frame` indexing the sorted input list.

`blend.rs` is Burt–Adelson multi-band Laplacian blending with the separable `[1,4,6,4,1]` binomial kernel, validity-weighted at every pyramid level so masked regions never bleed value in; band count is `log2(minimum overlap width)`, capped.

Compositing always runs the **tiled** path on the rotation strategy. `composite_tiled` takes already-solved gains and a strip height, reads, for each source frame in turn, only the rows that strip's warp taps (#5554), warps them into a `canvas_width × tile_rows` strip, and frees them before the next frame. Under the default Voronoi strategy the ownership mask needs only camera geometry, no pixels; under graph-cut the per-frame weight is sampled from the precomputed seam masks. Either way each strip is multi-band blended (#4524): it is processed inside a taller window, the strip plus a halo of `2·2^levels` rows on each side snapped to the coarsest pyramid level's grid, and each frame's Laplacian pyramid is built only over its own weighted columns, folded into the window's per-level accumulator and dropped. The halo covers the pyramid's full reach, so the tiled output is identical to the whole-canvas blend at the same band count and does not depend on the strip height, while blend memory stays bounded by one window. A geometric survey pass runs first because the band count (`log2` of the narrowest overlap) is a whole-canvas property. Without the tiled path, all N full-resolution frames would be resident at once. Each strip is handed to a `composite::CanvasSink` as soon as no later window can change it (#5452): the stitch saves through `PngCanvasSink`, while the quick preview, the tests and the evidence tools use `CanvasCollector` to assemble the whole image. The tile strategy hands over one full-width band of tiles at a time the same way. The Voronoi owner map is kept run-length encoded per row (`composite::OwnerRuns`) instead of one `u16` per canvas pixel, which was 512 MB at 256 MP.

Finally `stitch/save.rs`'s `PngCanvasSink` runs the same view tail raw-core uses for a RAW — **AgX** at neutral contrast, then Rec.2020 → sRGB primaries, then the sRGB transfer curve, then 16-bit quantization — 128 rows at a time, streamed into the PNG encoder (#5451). It is fed by the compositor itself, strip by strip as each one is finished (#5452), so neither the canvas nor a developed copy of it is ever whole in memory. Every step is per-pixel, so the result is identical to developing the whole image at once. A stitched pano has no embedded camera JPEG, so there is no Auto Profile to fit and AgX/Neutral is the correct fallback. This matters: written raw, the scene-linear Rec.2020 composite re-opened cold looking desaturated and flat, because a non-RAW file is assumed to be display-encoded sRGB and the data was then misread on every axis at once. `exif_embed.rs` builds a small TIFF blob for the PNG `eXIf` chunk carrying Make/Model/Software, exposure fields, and GPS when the source frames had it, so Apple's ImageIO surfaces the pano's camera and location panel. The PNG is written as `<name>.partial` and renamed into place only after every byte reached the disk, so a failed save never leaves a truncated panorama in the library. The Apple path also writes the `.maple/` thumb and preview from an area-averaged intermediate (at most 2560 px on the long edge) accumulated from the same row blocks; panos that small keep exactly the pixels a direct resize would give.

## Quick preview and reusable alignment

Before committing to a full stitch (several minutes on a 21-frame 100 MP set), the merge screen can show a quick low-resolution preview so the photographer can check framing, projection and seams, change options, and only then stitch (#4578).

1. **Preview.** `stitch::preview` runs the shared head — decode to proxies, features, matching, graph verification, strategy selection — then stops before full-resolution refinement. The solve and the composite run on the proxies already in memory, in the proxies' own pixel plane, onto a canvas whose long edge is about 2048 px (`PREVIEW_LONG_EDGE_PX`). No full-resolution frame is decoded. The scene-linear composite goes through the same AgX → sRGB view tail as the stitch's display PNG.
2. **Alignment.** The preview also returns a `SolvedAlignment`: everything stages 0–2 produced that the tail reads — per-frame sizes, proxy scales, focal seeds, priors, the verified proxy match graph and, for tile, the unit-focal tile graph — keyed by an `AlignmentKey`. It serializes to JSON (`to_json` / `from_json`) with every float stored as its bit pattern, because serde_json's default float parsing is not correctly rounded and a reused alignment must reproduce the exact pixels.
3. **Full stitch.** `stitch::stitch_reusing` takes that alignment. When the key matches, the head is skipped and the tail (refinement → bundle adjustment → composite) starts from the stored graph; `stitch::stitch` is just `stitch_reusing` with nothing offered, so both paths run the same tail over the same state and produce identical pixels.

The key is the identity of every input — canonical path, byte size, modification time — plus exactly the options that feed the head: strategy request, proxy long edge, feature engine (`ml` or `classical`), declared capture grid, models directory, CoreML. A mismatch is never used: the run re-solves and reports `AlignmentReuse::Stale` with the reason ("frame 3 changed on disk", "geometry options changed: strategy auto → tile", "geometry options changed: matcher ml → classical"). Every surface that offers an alignment back — maple-cli, raw-ffi, the Self Hosted jobs, Windows and Apple — runs the preview and the stitch with the same engine, so the engine check only fires when the user switches matchers in between. Options read only by the tail — retention, local alignment, residual budgets, canvas cap, strip height, seam strategy — are deliberately not in the key: changing them keeps the matching work and still re-runs everything they affect. The bundle adjustment is not part of the alignment either; it re-runs on full-resolution refined matches in the full stitch, which is what keeps the reused result identical to a fresh one. The preview's own solve uses proxy-accuracy matches, so its residual budgets apply in proxy pixels.

Surfaces: `maple-cli pano stitch --preview-out <png>` (plus `--alignment-out`, and `--alignment-in` on a later preview or full stitch; the report carries `"alignment": {"status": "solved" | "reused" | "stale", "stale_reason"}`), and the C-FFI entries `maple_pano_preview` / `maple_pano_stitch_aligned` below.

**Edges (#5570).** Boundary Warp stretches the panorama's ragged edge toward the full output rectangle, and Auto Crop finds the largest rectangle of the output with no empty edges. Both apply to the preview as well as the full stitch. Auto Crop never trims pixels (#5608): the image keeps its whole canvas, and the rectangle is recorded as the panorama's crop in its XMP sidecar, so the crop stays non-destructive and editable like any other. Neither is part of the alignment key, so changing one reuses the alignment and skips matching. On every outside surface the warp strength is a percent from 0 to 100, the slider's scale. At 0 with Auto Crop off, the output is byte-identical to a stitch without these options, and with Auto Crop on the written pixels are identical too. The warp is refused on a 360° panorama, where the crop rectangle spans the whole wrapping axis, and it is held below the requested strength where a stronger warp would fold the image. On the CLI, `maple-cli pano stitch --boundary-warp <0-100> --auto-crop` adds an `edges` block to the stitch and preview reports:

- `output` is the size of the image that was written, which is the whole canvas.
- `uncovered_px` counts output pixels no frame covers.
- `boundary_warp` holds `requested`, `applied` (both percents) and `status`. The status is one of `off`, `applied`, `clamped_fold`, `refused_full_wrap`, `refused_disconnected`, `refused_empty`, `refused_shape`, `refused_fold` or `refused_solve`. The block also carries `max_stretch`, `min_jacobian`, `predicted_coverage` and `solve_ms`, which are null when the status is `off`.
- `auto_crop` holds `requested`, `rect` (`{x, y, width, height}` in pixels of the written image, null when no fully covered rectangle exists) and `invalid_px`. `rect` and `invalid_px` are both null when Auto Crop is off.

The existing `canvas` block is the canvas, which is also `output`. A client turns `rect` into the crop fields by dividing by `output`: left `x / width`, top `y / height`, right `(x + width) / width`, bottom `(y + height) / height`, at six decimals (`docs/xmp-canonical-format.md` § Crop fields); a rectangle that is the whole image is no crop at all.

While a preview or stitch runs, `maple-cli` writes one `pano: progress <stage> <label> <percent>%` line to stderr each time a stage (0 decode, 1 features, 2 match_graph, 3 refine, 4 solve, 5 composite) moves by a whole percent. Decoding and feature extraction advance per frame. Matching, which dominates a preview (about 90 of 105 s on pano_01), advances with the first frame of each candidate pair as the pairs are matched in ascending order — monotone but uneven, since early frames have more candidates. Composite and refinement advance per strip or edge. The Self Hosted job runner and the Windows stitch dialog both parse these lines.

On Windows the stitch dialog previews as soon as it opens (#4581). Changing an option waits 600 ms for further changes, kills the preview still running, and starts a new one offered the last preview's alignment — so retention and local-alignment changes re-preview without matching again, while a strategy change re-solves. "Create panorama" passes the newest alignment to the full stitch, and the result message says whether it was reused. Preview images and alignment files live in a per-dialog folder under `%TEMP%\Maple\Pano`, removed when the stitch ends; folders a crashed session left behind are removed the next time the dialog opens.

## Tile strategy and exposure matching

`tile/` is the planar branch, selected when the match graph's edges are better explained by 2D similarity transforms than by camera rotations. Each verified edge gets a similarity fit from its inlier correspondences (`similarity/`, refined with the full-resolution matches), the pairwise offsets are turned into absolute canvas poses by a global anchored least-squares solve with frame 0 as the identity anchor, and then the geometry-agnostic downstream stages — gain, Voronoi seam, multi-band blend — run unchanged.

A nadir strip over relief breaks the one-similarity-per-pair assumption: a dune face, a tree line and the beach below it, or rooftops above a street, each move by a different amount between two frames. The robust fit locks onto whichever band is tightest, and when neighbouring pairs lock onto different bands, the solve spreads hundreds of pixels of contradiction over every seam. On `pano_03` (Paris rooftops) and `pano_04` (a dune strip), this was the dominant error for both feature engines (#4553). `tile/edge_consensus.rs` therefore fits up to five band hypotheses per edge, using sequential robust fits on the matches that no earlier hypothesis claimed. It then picks one hypothesis per edge by steepest descent on the graph's summed contradiction (how far each chosen hypothesis disagrees with the placement solved from all of them), one switch at a time, so the search cannot cycle. Over strong relief that landscape has many local minima, so the descent runs from the dominant fits and from 16 seeded random starts and keeps the best result. Under the final solve, an edge that still contradicts the placement by more than three times the median contradiction, and by more than the verifier's own inlier gate, is dropped (worst first) and selection reruns. Because the solve is weighted by inlier count, a conflict is blamed on its weaker side. A bridge edge is always fitted exactly, so it is never dropped.

Band selection fixes which similarity each frame gets, but a rigid similarity still cannot line up surfaces at different heights at once. With local alignment on (`--local-align mesh`, the default on every surface), the tile path then runs the same Stage-F bilinear mesh as the rotation path, through `local_align/planar.rs` (#4577). Each verified match asks its two frames to meet at the midpoint of where they currently place it; that target, mapped back through the frame's similarity, is an exact data point for the shared mesh fit. A scene point seen by three or more frames gets a different midpoint from each pair, so the fit runs five passes, each recomputing midpoints from the corrected positions. The tile warp applies the mesh as a shift of the source sample point inside its one resample. The tile envelope is wider than the rotation path's (96 px node cap, 48 px RMS), because terrain relief moves depth bands by tens of pixels on 100 MP frames; a field over it is refused, and that frame stays rigid. The report carries `mean_planar_before_local_px` / `max_planar_before_local_px` next to the corrected residuals, plus a per-frame `local_correction_rms_px`. With local alignment off, the tile output is bit-identical to the rigid placement.

Exposure matching on this branch is more elaborate than the rotation branch's scalar gains, in two layers solved in the log domain from one strided canvas scan (`tile/photometry.rs`, `tile/exposure_field.rs`, `tile/sampling.rs`):

- **Layer A — gains plus a shared ramp.** Each frame's recorded value is modelled as a per-frame log-gain _plus one within-frame linear slope shared by every frame_ — same camera, same sun, so a low-sun BRDF hotspot or decentered falloff is fixed in frame coordinates. Solving the slope jointly is what prevents the scalar-only failure mode: with scalars alone, a constant within-frame slope makes every consecutive overlap read "the next frame is dimmer," and least squares integrates that bias along the chain into an enormous cross-strip ramp — measured at 19× (4.2 EV) on a strip whose frames were actually equally bright. The slope is identifiable because pairs exist at several baselines: gain differences must agree across baselines, while slope terms scale with the frame-local offset.
- **Layer B — residual exposure fields.** What the gain-plus-ramp model cannot express (cloud shadows, genuine light changes, non-linear falloff) is aggregated as per-pair log residuals on a coarse canvas grid (canvas/128 per side) and solved as one smooth per-frame correction field — a screened-Poisson system with a data term tying overlapping frames, a gradient smoothness penalty, and a weak gauge anchor, solved matrix-free by conjugate gradients. Fields are bilinearly upsampled at composite time, so memory stays at the coarse grid.

Both corrections are applied per pixel during the warp.

### Auto strategy selection

`strategy.rs`. For every verified edge the selector runs the similarity estimator on the same inlier matches rotation verification produced, and records the rotation-model inlier RMS (angular residual converted to pixels at the frame's focal length) against the similarity-model inlier RMS. A pair votes "tile" when the planar residual is enough better; the majority decides, and a tie or bare majority selects rotation — deliberately conservative, because misclassifying a pure-rotation set as tile is the worse error. Gimbal metadata, when every frame shares an attitude, is recorded as `gimbal_corroboration` in the evidence block; it never decides and never overrides the content vote. When auto picks tile on what looks like an intended pano capture, the report carries the warning "Sideways motion detected; pivot in place for best results." An explicit `--strategy tile` is operator intent and gets no warning.

## Memory

A 21-frame 100 MP DJI set is the working reference, and peak resident memory is the design constraint throughout.

| Phase              | Bound                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------- |
| Stage 0 decode     | full-resolution buffer freed immediately; only proxy planes and metadata stay resident        |
| Stage 3 refinement | per edge, one band of matches at a time: only the rectangles its templates and searches touch |
| Gain solve         | each frame swept once in 256-row bands; no whole frame resident                               |
| Exposure field     | each frame warped onto the seam canvas in 32-row strips from the source rows they tap¹        |
| Seam masks         | same strip warp as the exposure field, one frame at a time¹                                   |
| Stage 5 composite  | tiled strips reading each frame's tap rows in turn; default 512 canvas rows, streamed to save |
| Save               | 128 developed rows at a time into the PNG encoder; sidecars from a ≤ 2560 px intermediate     |

¹ The seam canvas is about 1 MP, so one 32-row strip spans many source rows: a few hundred megabytes of a level 100 MP frame. A frame containing a pole of a spherical canvas, or one with strong roll, can tap almost every source row in one strip, so for those frames the window approaches the whole frame.

Measured on the 21-frame set, frame-processing peak dropped from about 34 GB to about 4.9 GB. End-to-end peak is around 13.6 GB with the ML matcher, dominated by ONNX Runtime's own roughly 8.7 GiB resident floor. With the classical matcher, through the Apple entry point, the peak is 2.78 GiB (Mac17,6, 256 MP output, #5452): about 2.1 GiB through stages 0–4, and the composite, now streaming straight into the PNG, adds about 0.7 GiB on top. It was 5.71 GiB when the composite still assembled the whole canvas (#5451), and 10.24 GiB when saving also made three whole-canvas copies. `maple-cli` peaked at 2.77 GiB then, and at 2.54 GiB once refinement read bands (#5563). Because encoding now overlaps the composite, the report's `write` time covers only closing the files, and the `.partial` PNG sits next to its final name for the whole composite.

A smaller output canvas lowers only the composite's share (#5454). Capped at 64 MP (13490 × 4744), the same `maple-cli` stitch peaked at 2.31 GiB when first measured (#5454), set by refinement, with the composite at 2.15 GiB. From those two points, the composite cost about 49 KB per output column on top of about 1.5 GiB the allocator still held from the earlier stages. Refinement has since stopped holding whole frames and reads bands of matches instead (#5563), so it no longer sets that floor. The capped stitch now peaks at 1.50 GiB, against 1.73 GiB just before that change and 2.54 GiB uncapped, so on pano_01 capping to 64 MP saves about 40 %.

On an iPad (#5450), with banded decode, banded refinement and a composite that reads only the source rows it needs (#5552–#5566), pano_00 (3 × 100 MP, tile, a 12315 × 12760 canvas) peaks at 1628 MB in stage 0, 749 MB in refinement and 958 MB in the composite, from 365 MB before the stitch. Before those changes the same stages peaked at 4629, 6713 and 6675 MB. So decode and matching now set the peak, adding about 1.26 GB, and the composite adds about 0.59 GB.

### The model and the memory limit

Those measurements are fitted into one model, `raw_core::pano_memory`, with F input frames (dropped or not, each costed as the largest), the largest of P pixels, its proxy of p = min(P, 1600²) pixels, its width c = ⌊√(1.5 P)⌋ (a 3:2 frame of P pixels, so a 4:3 or portrait frame is overstated) and an output canvas W pixels wide. Every measurement used the default 1600 px proxy, so a smaller `proxy_long_edge` is costed as 1600; a larger one retains a proxy of q = min(P, edge²) pixels per frame, and each of its q − p pixels past the fitted proxy adds at least its RGB f32 planes (12 bytes) to both phases. The model has two calibrations, `PanoMemoryProfile::Server` and `PanoMemoryProfile::Apple` (#5891), because the two places it is used need different things from it and the two allocators keep very different amounts of freed memory:

| Phase                              | Server (memory limit)                   | Apple (merge sheet output size)   |
| ---------------------------------- | --------------------------------------- | --------------------------------- |
| Head: decode, matching, refinement | `F × 13 × p + 226,000 × c`              | `F × 80 MiB + 12 × P`             |
| Composite                          | `F × 40 MiB + 233,500 × c + 42,300 × W` | `F × 80 MiB + 5 × P + 49,350 × W` |
| ML matcher, added to either        | `5 GiB`                                 | `5 GiB`                           |

**Server.** A memory limit must be a guarantee, so this calibration is fitted (#5891) to the whole-process peak footprint (`proc_pid_rusage`) of `maple-cli pano stitch` (classical matcher, mesh local alignment) on a Mac (Mac17,6), per phase, over eleven configurations, and every constant rounds up so each phase overstates every measurement. The head's per-frame term follows the proxy, so it stops growing at 1600² pixels; the largest frame's decode bands span its width, so they follow c, not P. 4 threads gave the same peaks as 18 (pano_00's composite reached 2.78 GB at 4 threads, which is in the table); 1 thread was lower. No Linux measurement has been made: macOS's allocator keeps freed large blocks and counts them in the footprint (`vmmap` during pano_00 showed a 2.3 to 2.5 GB footprint while the malloc zone held 0.18 to 0.69 GB live, and 386 MB of "Malloc Large (empty)" in the composite), so on Linux this calibration should overstate further, never understate.

**Apple.** The merge sheet sizes the output with the #5555 calibration, unchanged: the iPad's pano_00 adds 1263 MiB in the head and 593 MiB in the composite (#5450), about half what the Mac reports for the same stitch, and the column term is the Mac's pano_01. Fitting it to the Mac would make an iPad with less than about 4 GB available refuse a 100 MP set it stitches today in about 1.7 GB. The Mac rows below are therefore under 1 for most sets in the Apple column: they are the Mac's footprint, not the iPad's.

A stitch can be held to the model (#5835), with the server calibration (only the server sets a limit). `StitchOptions::memory_limit_bytes` (`maple-cli pano stitch --memory-limit-bytes <N>`) refuses the run with `StitchError::InsufficientMemory { needed, limit }` at two points: before any frame is decoded, when the head exceeds the limit, from the input headers alone; and as soon as the canvas is solved, when the composite at that width exceeds it, before any photometry pass or strip. The Self Hosted server passes its decode memory budget as the limit (see Server, below).

The checks read only image headers and add no measurable time: stitching the same six pano_01 frames three times each, interleaved, the median CPU time (user + sys) was 175.2 s on main, 176.8 s with this code and no limit, and 179.0 s with a 16 GiB limit, within the 166.8 to 182.1 s spread of the nine runs, and all nine wrote the same PNG.

## The C-FFI surface

`src/raw-pipeline/raw-ffi/src/pano.rs` defines the ABI; `pano_apple.rs` is the platform-agnostic body that calls `maple_pano::stitch::stitch`. Two Cargo features select the ORT linkage: `pano` (macOS, `maple-pano/ml`) and `pano-ios` (iOS and simulator, `maple-pano/ml-static`). Both also enable `maple-pano/classical-features`, so every Apple slice carries the classical matcher and can stitch with no ONNX Runtime or models on disk.

```c
int32_t maple_pano_stitch(
    const char *const *raw_paths, size_t count, const char *out_png_path,
    MaplePanoRetention retention,       // KEEP = 0, STRICT = 1
    MaplePanoLocalAlign local_align,    // MESH = 0, OFF = 1
    MaplePanoStrategy strategy,         // AUTO = 0, ROTATION = 1, TILE = 2
    MaplePanoFeatureEngine engine,      // ML = 0, CLASSICAL = 1
    MaplePanoProgressFn progress_cb, void *cb_user,
    const MapleCancelFlag *cancel);
```

`0` is success, negatives are hard errors, positives are soft errors, and `maple_last_error()` carries the human-readable reason.

| Code | Meaning                                                                                         |
| ---- | ----------------------------------------------------------------------------------------------- |
| −1   | null pointer in a required argument                                                             |
| −2   | fewer than 2 input frames                                                                       |
| −3   | unsupported platform (Linux, WASM)                                                              |
| −4   | a `raw_paths` element is null or not UTF-8                                                      |
| −5   | `out_png_path` is not UTF-8                                                                     |
| −6   | ML engine chosen but its models or ORT are missing                                              |
| −7   | pipeline error — decode, match, BA, composite, or write                                         |
| −8   | degenerate rotation geometry; retry with Auto or Tile                                           |
| −9   | not enough free space on the temp volume for the decoded frames; a smaller output does not help |
| −10  | an edge option is out of range: `edges.boundary_warp` outside 0–100 (preview pair only)         |

`MaplePanoPreviewSizes` is `{ uint32_t full_width, full_height; uint64_t largest_frame_px; uint64_t scratch_bytes; }`: the estimated full-stitch canvas under the same options and the default cap, the pixel count of the largest frame at full resolution, and the temp-volume space the stitch's decoded-frame store will need (#5555). The store holds every frame at full resolution, so `scratch_bytes` does not depend on the output size. `maple_pano_sweep_scratch()` removes stores that a terminated process left in the temp directory and keeps a live process's; every store creation already does the same, and the app also calls it at launch. On the rotation path the estimate scales each surviving proxy camera to full resolution (focal length and frame size by that frame's own proxy ratio) and runs the full stitch's `auto_canvas` on them under the cap, so with mixed input resolutions the densest frame sets the size, as it does in the stitch. On the tile path the canvas is in the anchor frame's pixels (placement fixes frame 0 at the identity), so the estimate scales the natural proxy canvas by frame 0's ratio on each axis and shrinks it uniformly to the cap. It solves on proxy-accuracy matches, so it lands within a few percent of the refined stitch (3.9 % in height on pano_01's first three frames). A canvas larger than `max_canvas_px` is shrunk uniformly to fit, on both strategies. The cap applies to the real stitched canvas, so an estimate a few percent off in shape shifts the capped width by about half that. The cap is not part of the alignment key, so a capped stitch still reuses the preview's alignment. The rotation path's degenerate-geometry guard compares the natural canvas against the larger of the requested cap and the 256 MP default. Without that, a small output cap on a wide panorama would read as runaway geometry and fail the stitch.

`MaplePanoEdges` is `{ float boundary_warp; bool auto_crop; }`, with the strength as a percent from 0 to 100. `MaplePanoEdgesReport` is `{ MaplePanoBoundaryWarpStatus boundary_warp_status; float boundary_warp_applied; bool auto_cropped; uint32_t output_width, output_height; uint32_t crop_x, crop_y, crop_width, crop_height; }`: `auto_cropped` says a rectangle was found, and the crop fields are that rectangle in pixels of the output, which is the written image's size. Its status cases are `WarpOff`, `WarpApplied`, `WarpClampedFold`, `WarpRefusedFullWrap`, `WarpRefusedDisconnected`, `WarpRefusedEmpty`, `WarpRefusedShape`, `WarpRefusedFold` and `WarpRefusedSolve`. The `Warp` prefix is there because C enum cases share one namespace. `out_edges` is written only when the return code is ≥ 0. The preview PNG comes back warped but whole: Auto Crop only reports its rectangle, in the preview PNG's own pixels. `MaplePanoPreviewSizes` is the full-stitch canvas, which is what the stitch's memory use follows.

Both return `1` (soft) when an offered alignment was stale or unreadable and matching re-ran, with the reason in `maple_last_error()`; `−5` covers any non-UTF-8 output or alignment path. The preview reports progress stage 3 complete immediately, since it skips refinement. Windows drives the same flow through `maple-cli` and does not bind these.

The progress callback is `void(*)(uint32_t stage, float frac, void *user)`, invoked from worker threads — the host must not block it. Both the callback and the cancel flag accept null. The function joins all worker threads before returning, so caller pointers only need to live for the synchronous call.

`pano_ffi_gates` (`src/raw-pipeline/raw-ffi/tests/pano_ffi_gates.rs`) is the end-to-end parity gate: it calls the actual C entry point, paths in and PNG out, and diffs the result against the reference by peak-normalized RMSE, tolerating up to 2% dimension difference from canvas rounding. It skip-passes when fixtures, `MAPLE_PANO_MODELS`, or `ORT_DYLIB_PATH` are absent. `pano_ffi_classical_gates` points both variables at paths that do not exist, checks the ML engine returns −6, then stitches all of pano_01 with the classical engine; it skip-passes only when the fixtures are absent.

`pano_preview_ffi_gates` drives the preview pair through the C ABI on three pano_01 frames: composite-only changes reuse the alignment, a geometry change does not, and a stitch from the preview's alignment is pixel-identical to a fresh `maple_pano_stitch`. A second, classical-engine case runs wherever the fixture is present. It checks five things: the reported canvas size is within 6 % of the stitched one; the largest frame is exactly pano_01's 5272 × 3948; the reported store size is exactly what the frame store will claim; a stitch capped at a quarter of that area comes out between 90 % and 100 % of the cap; and a cap at a sixteenth, past the guard's 8× ratio, still stitches. `pano_ffi_gates` (`src/raw-pipeline/raw-ffi/tests/pano_ffi_gates.rs`) is the end-to-end parity gate: it calls the actual C entry point, paths in and PNG out, and diffs the result against the reference by peak-normalized RMSE, tolerating up to 2% dimension difference from canvas rounding. It skip-passes when fixtures, `MAPLE_PANO_MODELS`, or `ORT_DYLIB_PATH` are absent.

## Apple

`src/apple/Packages/MapleCore/Sources/MapleCore/Panorama/`.

`PanoStitching.swift` is the protocol seam plus the option types (`Retention`, `LocalAlign`, `Strategy`) and the `PanoStage` enum whose raw values match the CLI's stage log prefixes; it has a `stitch` and a `preview`, both taking an optional `PanoAlignment`. `MockPanoStitcher` satisfies it for previews and tests. `RustPanoStitcher.swift` is the real conformance over `maple_pano_stitch_aligned` and `maple_pano_preview` (argument marshalling in `PanoFFICall.swift`), running off the main actor because both calls block for minutes.

Progress bridging is the interesting part. The C trampoline can fire from several rayon worker threads at once, so its hot path does exactly one thing: reconstruct a heap-allocated atom from the opaque `cb_user` pointer, take an `os_unfair_lock` for a two-word store, release. No task allocation, no main-actor hop. A timer polls that atom about 20× a second on the main run loop and publishes only when the value changed. Lifetime is a retain before the call and an unconditional release after, safe because the FFI joins its workers before returning. `cancel()` flips a Rust-allocated cancel flag, the same pattern the scene-linear render path uses.

Panorama merge works on a fresh install with nothing downloaded. `PanoProvisioning.featureEngine()` picks the ML matcher only when the user has turned on "Use ML matcher" in Settings → Pano (stored under `maple.pano.settings.useMLMatcher.v1`, off by default) and the models and runtime are on disk. In every other case the stitch uses the classical matcher, and the merge sheet never starts a download. Turning the setting on is what runs `PanoProvisioner`. Turning it off keeps the downloaded files but goes back to the classical matcher. The result summary names the matcher that ran.

`PanoMergeSession.swift` is the `@Observable` state machine with generation-counter discipline so a cancel-then-rerun can never publish stale progress. It runs two lifecycles (#4579):

1. **Preview.** Opening the merge sheet with two or more frames starts a preview at once. Changing the geometry strategy, which is part of the alignment key, cancels the preview in flight and starts a new one 600 ms after the last change, so several quick changes produce one run. A composite-only change (retention, local alignment) does not throw away matching that is under way: the running preview finishes, then a new preview starts at once from its alignment with the new options. The previous image stays on screen, dimmed, while the new one builds. A fresh preview of the 21-frame pano_01 set takes about 2½ minutes because matching dominates, so the sheet shows staged progress and stays usable throughout.

**Auto Crop in the merge sheet (#5608).** The preview image is the whole canvas; while Auto Crop is on and the report carries a rectangle, the sheet frames the image to it (`PanoPreview.displayImage(autoCrop:)`). An on-device stitch leaves the PNG whole and, right after the core renames it into place, writes `<name>.xmp` beside it with the crop fields and the `Maple Auto Crop` `tEXt` chunk into the PNG (`PanoAutoCropRecord`); a sidecar that is already there is never replaced, and the mark is appended past the old `IEND` and a failure cuts the file back, so the PNG is never damaged, and a failure to write the crop keeps the panorama, uncropped, and says so in the result summary. When cloud frames are stitched on the device, the upload sends the sidecar after the PNG (`PanoServerUpload.add`), so the server's copy keeps the crop. Thumbnails of the panorama follow the sidecar, since the non-RAW derivative path already applies the crop of an XMP snapshot. 2. **Stitch.** "Create Panorama" starts the full stitch from the latest solved alignment. If a preview is still matching for the current geometry, the sheet shows "Finishing alignment…" with that preview's progress and starts the stitch once its alignment lands, so minutes of matching are not thrown away. A re-preview still waiting out its debounce after an option change has nothing in flight, so it is dropped and the stitch starts at once.

3. **Output size** (#5454, #5555). The preview also reports what the full stitch will hold: the estimated canvas size, the largest frame's pixel count, and the decoded-frame store's size; the session adds the number of input frames, dropped or not. `PanoMemoryModel` (`PanoOutputSize.swift`) turns that into the memory the stitch adds on top of the app's footprint. The estimate is the larger of two terms. The head (decode, matching and refinement) is 80 MiB per frame plus 12 bytes per pixel of the largest frame. The composite is the same per-frame term, plus 5 bytes per pixel of the largest frame, plus 49,350 bytes per output column. The constants are fitted to the iPad's pano_00 stages and the Mac's pano_00 and pano_01 stages (see Memory), rounded up so each overstates its measurement, reading the Mac figures as GiB and the iPad's as MiB. The column term is the Mac's, whose allocator keeps more than the iPad's. This is the model's Apple calibration (`PanoMemoryCalibration.apple`); #5891 re-fitted only the server's, which reads the Mac's footprint and would refuse 100 MP sets on iPads that stitch them today. The model uses width rather than area because the composite streams fixed-height strips. The session compares the estimate, with 15 % headroom, against `os_proc_available_memory()`. On an iPhone the sheet also defaults to Smaller as soon as the full-size estimate exceeds 60 % of `os_proc_available_memory()` (`PanoMemoryModel.phoneSmallerDefaultFraction`, #5654), even where Full would still pass the 15 % check: the headroom is calibrated on a Mac allocator and iPad runs, not on a phone that also runs the backup. The smaller canvas is then sized to that 60 % budget (to the 15 % limit when the head alone exceeds 60 %), Full stays one tap away, and the caption's "system may stop the stitch" warning applies to it. If a smaller size would buy nothing (the head alone exceeds 60 % but Full still passes the hard limit), Full stays the default. iPad and Mac keep the 15 % rule only. `PanoDiskModel` (`PanoDiskFit.swift`) does the same for storage. The frame store must fit on the temp directory's volume and the PNG, at 6 bytes per output pixel, on the output folder's volume (the download's output folder when there is one; otherwise `Panoramas/` beside the first frame, else Application Support when that folder can't take it; the preflight resolves the same candidates, through symlinks and under the same security scope, as the reservation), each with a 512 MiB reserve, or together when the two are one volume. The volumes are read off the main actor, since a network share can stall. Free space is counted as the core counts it: space available now, not space the system could purge. The frame download sheet counts purgeable space too, so it can find room the merge then does not. The session reads both once, when the preview lands, so the size the sheet shows is the size the stitch uses. When full resolution doesn't fit either, and neither check says no size helps, the merge sheet's Output section defaults to "Smaller (fits this device)", the largest canvas that fits both, at the same aspect ratio, and the stitch passes its pixel count as `max_canvas_px`. The user can still pick Full resolution, and the caption then warns that the system may stop the stitch, or that the merge may fail for storage. If even the head doesn't fit in memory, or the frame store or a preview-sized PNG doesn't fit on disk, the caption says so and offers no smaller size, since none helps; for storage it names how much to free. A stitch that still runs out of temp space fails with −9, which the app reports as "free up storage" rather than a generic failure. The fit is kept with the options it was solved for. Strategy, Retention and Local alignment all reach the solver, and Retention and Local alignment decide which frames survive, so any of them can change the canvas. If the user changes one and presses Create Panorama before the new preview lands, on a device with a memory limit, or wherever the storage fit was read, the session previews the current options first and sizes the stitch from that fit, rather than from the previous canvas. The choice resets when the frames change, and changing it doesn't re-run the preview. On iPhone and iPad a stitch that runs on the device also holds a pause on the PhotoKit backup while it runs (#5653): when Create Panorama starts, the session asks its injected `PanoBackgroundPausing` host (`EnginePanoPause`, backed by `EngineHost.pauseForPanorama`) to stop the backup engine and waits until it has stopped, then keeps going. If that pause took down a running engine, the session re-reads `os_proc_available_memory()` and re-decides the default output size from the same preview before it stitches, so the backup's footprint no longer counts against the stitch; an explicit Smaller or Full choice by the user stands. The pause (`PanoBackgroundPause`) is released in a `defer` around the stitch, so success, failure, Cancel, a restarted stitch, and the window going away all give it back, and the object releases itself on deinit if a holder is dropped; the count lives in memory only, so a terminated app cannot leave the backup paused. A stitch on the server never pauses the device. macOS reports no per-process limit, so it shows the control only when storage is short. At launch the app removes the frame stores and per-call scratch directories (`maple-pano-call-<pid>-<UUID>`) whose process has exited, so a run the system terminated leaves nothing behind.

The alignment is held only in the session's memory. The FFI takes file paths, so each call writes it to a private temporary directory and deletes that directory when the call returns. Every later preview also offers it, which is why a change to a composite-only option (retention, local alignment) skips matching. When the core reports the alignment stale (return code `1`), the run re-solves and the result carries the reason. The merge sheet's footer and the result summary say whether the alignment was reused.

The two Apple slices differ in one solver setting. iOS requests the **CoreML execution provider** for both ONNX sessions, so eligible operations route to Apple silicon and unsupported ones fall back to ORT's CPU provider automatically. macOS deliberately does not: that path is parity-verified against the references and stays on CPU ORT.

Provisioning is three files. `PanoProvisioning.swift` resolves the two ML paths in priority order — UserDefaults set from Settings → Pano, then `MAPLE_PANO_MODELS` / `ORT_DYLIB_PATH` environment variables, then the default Application Support locations — and reports a status the settings UI renders. `PanoProvisionManifest.swift` pins each downloadable artifact by URL, SHA-256, and byte size, kept in sync with the Rust `models.toml` (a drift shows up as a hard error at stitch time, since the Rust loader re-verifies). `PanoProvisioner.swift` downloads and installs them: every artifact is digest- and size-verified, a mismatch deletes the partial download and fails hard, an already-verified artifact is skipped, and it installs only to the app-support default — if a higher-priority override is set, auto-download would not change what the resolver picks, so it isn't offered. iOS downloads the models only; its ONNX Runtime is the static framework embedded at build time.

### System progress and background continuation (iOS, #5663)

A stitch takes minutes, and iOS suspends a backgrounded app within seconds, so showing progress outside the app is not enough on its own: the stitch has to keep running. `PanoContinuedProcessing` (`Maple/PanoContinuedProcessing.swift`) therefore uses a `BGContinuedProcessingTask` (iOS 26, the deployment target) and no Live Activity. The system keeps the process running, draws its own progress bar with a title and subtitle on the lock screen and Dynamic Island, and its stop control fires the task's expiration handler. A Live Activity would only display progress and would need a widget-extension target and `NSSupportsLiveActivities` for nothing the system UI does not already give.

1. When the session leaves idle for `finishingAlignment` or `running`, the coordinator submits a request for `app.justmaple.aperture.pano.stitch` (declared in `BGTaskSchedulerPermittedIdentifiers` by the same build phase that declares the backup task). The system accepts a request only from the foreground app, and submission uses the fail strategy, so a refusal leaves a normal foreground stitch.
2. The stitch keeps running in `PanoMergeSession`; the coordinator observes `state` and mirrors it onto the task. `PanoSystemProgressTracker` (MapleCore) turns each state into one event. The task's progress is the merge sheet's own bar (`PanoMergeSession.stitchProgress`), so the two agree (the system value is the same fraction, stopped at 99%): when a stitch has an alignment phase ("Finishing alignment", either waiting for the preview or re-solving the alignment for the stitch's options, which now reports real progress), that phase takes the first 30% of the bar (`PanoStitchProgress.alignmentShare`) and the composite fills the rest, so the bar never falls back when the composite starts. The tracker also never lowers the value and stops at 990 of 1000 until the stitch finishes. The system expires continued-processing tasks that "appear stalled" (`BGTask.h`), and reaching the total reads as completion, so a phase that reports nothing, or a bar that reaches the end early, puts the task at risk. The owner's lock-screen "Task failed" 1 to 2 minutes after locking matches a stall of the alignment phase, which used to report a constant 0 units.
3. The system UI's stop control and a system expiry fire the same handler and cannot be told apart, so both call `PanoMergeSession.abort(because:)` rather than a silent cancel. It stops the work and leaves the session in `error` with a reason naming how long the task ran and the phase it was in (visible in the merge sheet when the app is reopened, and in the notification). Stopping from the merge sheet's own button is `cancel()` and completes the task as stopped, not failed. Every transition logs to `os_log` (subsystem `app.justmaple.aperture`, category `pano-continued`), including the system accepting or rejecting the request, the system starting the task, expiry, and the end of a run.
4. On success the task is retitled "Panorama ready" and completed; on failure it is retitled "Panorama failed" with the error text. The system removes its progress UI when a task completes, so when the app is not active the coordinator also posts one local notification with the same words. Notification authorization is requested as provisional, which shows no permission prompt and delivers quietly to Notification Center.

On iPad each window has its own merge session but the system shows one task, so `PanoSystemProgressArbiter` gives the task to the first run to begin and ignores the other sessions until that run ends or its window closes (each window's observation runs in a view `.task`, so closing the window releases it). Stop and expiry act on the owning session only.

The panorama is not in the library until the user taps Done in the merge view, so the notification and the task open the app and nothing deep-links.

The task asks for the default CPU and network resources, not background GPU. `BGContinuedProcessingTaskRequest.Resources.gpu` needs the `com.apple.developer.background-tasks.continued-processing.gpu` entitlement (the Background GPU Access capability, a provisioning-profile change in the Developer portal) and is not supported on every device, so the stitch must never need the GPU while backgrounded. The classical matcher and the compositor are CPU only. The ML matcher's CoreML sessions on iOS are created with `CPUAndNeuralEngine` compute units rather than `All`, so ALIKED and LightGlue run on the Neural Engine and CPU and never pick the GPU, whether or not the app is in the foreground; the units are fixed when the session is created, so a stitch that starts in the foreground and is then backgrounded cannot switch mid-run. Continued processing does not raise the memory limit; the stitch's memory is governed by the Memory section above. The task is iOS and iPadOS only. macOS and tvOS compile a no-op.

### Build note

`src/apple/scripts/build-xcframework.sh` defaults to a **release** build, and the script's own header explains why in pano terms: `maple_pano_stitch` runs roughly 16× slower in debug on this CPU-heavy SIMD/ONNX workload — a measured 5785 s debug versus 353 s release for the same 21-frame stitch on an M4. `--debug` prints a warning and is only for fast-recompile iteration where pano performance is irrelevant. The script builds macOS slices with `--features gpu,pano` and iOS/simulator slices with `--features gpu,pano-ios`, and provisions the ONNX Runtime iOS static xcframework into `~/.cache/maple-pano/ort-ios/` first.

## Server (self-hosted)

Stitching on the server is a **job**, not a pipeline stage — it is a one-off, user-selected action on a specific set of photos, not an "eventually every asset gets this" backlog.

`src/api/src/job-runner/handlers/pano-stitch.ts` resolves the selected assets to absolute paths, spawns `maple-cli pano stitch … --display <output.png> --report <report.json> --retention … --local-align … [--features-engine <classical|ml>] [--strategy …] [--models-dir …] [--alignment-in …]`, and on success moves the output PNG into a `Panoramas/` folder beside the first source frame (where the Apple apps put an on-device stitch), upserts it as an asset and records the report's alignment verdict in the job result. The output is the display PNG — AgX, sRGB, 16-bit, with the first frame's EXIF, the same file the Apple apps write — and the scene-linear `--out` carrier is never written, so a full-size stitch produces one large PNG, not two. The file is named `<first frame>-pano-<key>.png`, where the key hashes the selected asset ids, each source file's size and modification time, retention, local alignment, strategy and matcher (`src/api/src/pano/pano-output-location.ts`). Asking again for the same panorama — a client retrying after a dropped connection, say — therefore finds the file the earlier run wrote: the job imports it and finishes without spawning the CLI, so a retry neither repeats a multi-minute stitch nor adds a second copy. A different selection or option gets a file of its own; an existing panorama is never overwritten, since new bytes would be a new content identity while the old row kept the path. Containment is checked on real paths at the moment of use: each input frame must resolve inside a library root, the `Panoramas/` folder must resolve inside the library (a symlink out of it is refused), and the result is copied, flushed and verified under a private staging name beside its final name, then given that name by hard link (or, on a volume that cannot link, by rename once the name is confirmed free) (`pano/pano-publish.ts`). So a symlink planted at that name is neither followed nor imported, an existing file is never replaced, and a crash mid-copy never leaves a truncated panorama for a retry to import; a leftover staging file (`<name>.tmp.<pid>-<hex>`) is ignored by the indexer and the mirror. Mirrors receive it through the library's registered path. A freshly stitched asset is announced on the change feed, so open clients show it without a reload. Paths a request names are matched to the deepest library root that contains them; a file held only by a trashed photo is a 400 `path_trashed` (indexing it would revive that photo from the trash), and a file the library excludes (`.mapleignore`, `.maple/`) is a 400 `path_excluded` (`pano/pano-path-inputs.ts`).

Progress is real, not a timer: the job turns the CLI's `pano: progress` lines (see [Quick preview and reusable alignment](#quick-preview-and-reusable-alignment)) into 100 units per stage (`job-runner/handlers/pano-cli-process.ts`, shared by both pano handlers). A binary that predates the lines prints none and its job sits at zero until it finishes.

**Server stitch from the Apple apps (#5488).** Frames that live only on a Maple server have no file on the device, so the merge sheet sends them to these routes through `ServerPanoStitcher` (`MapleCore/Panorama/ServerPanoStitcher.swift`, client `MapleCloudKit/Pano/PanoServerClient.swift`). It names the frames by their server paths (`assetPaths`), like the web client, and passes the preview job as `alignmentFrom`. Frames with no local file start on the server; frames that could go either way get a "Run On" picker. Polling only watches the job, so leaving the app does not stop it. After a run of failed polls the sheet says it lost contact, and Try Again follows the same job instead of queueing another; changed settings replace it, and closing the sheet stops it. A job stopped elsewhere (the web app, another device, a newer preview) is reported as stopped rather than left spinning. Requests go to the server's LAN address when one is known and fall back to its registered URL when that address stops answering. Done reloads the server listing, where the result now sits in `Panoramas/`.

**Server and device parity.** Both run `maple_pano::stitch` — the CLI through `maple-cli pano stitch`, the apps through the `maple_pano_stitch` C entry point — so the same frames and options give the same panorama, and the `pano_ffi_gates` parity gate covers that shared function. Three things differ by design. The server always stitches at full resolution; only the device offers a smaller output when full size would not fit in memory (#5454). The server names its result `<first frame>-pano-<key>.png` so a retry finds it, while the device names its file by time. The device writes the `.maple/` thumb and preview itself; on the server the thumb and preview stages make them.

**Quick preview (#4580).** `pano_preview` is a second job (`handlers/pano-preview.ts`): the same payload — matcher included, since both routes take it from one `planStitch` and both handlers build their flags with `panoOptionArgs` — spawning `--preview-out … --alignment-out … --report …` into a directory from `src/api/src/pano/pano-previews.ts`. A finished preview's directory holds the PNG served by `GET /api/pano/jobs/:id/preview` and the solved alignment. A stitch (or a re-preview) that names the preview job in `alignmentFrom` gets that alignment as `--alignment-in`; the path is rebuilt from the server-written payload and must be a direct child of the previews directory, so a client cannot point the CLI at an arbitrary file. Whether the alignment was actually used is the CLI's call — a changed file or geometry option makes it `stale` and matching re-runs — and the stitch's job result carries the verdict (`alignment.status`: `reused` means no second matching pass). Preview directories are short-lived: a failed or cancelled preview removes its own, the stitch that consumed one removes it once the panorama is imported, and anything older than an hour is swept when another preview starts or a stitch finishes. A configured binary without the preview flags (probed from `--help`, like `--strategy`) reports `preview_supported: false` and the dialog simply does not preview.

**Edges: Boundary Warp and Auto Crop (#5576).** Both routes accept `options.boundaryWarp` (a number from 0 to 100, in percent, the slider's own scale) and `options.autoCrop` (a boolean); out-of-range or mistyped values are refused by the body schema with 422, and absent values mean 0 and false. They reach the CLI as `--boundary-warp <PCT>` and `--auto-crop`, and only when chosen, so a request at the defaults spawns exactly what it did before. Neither is part of the alignment key, so a re-preview after changing one re-composites from the alignment it already has. The report's `edges` object (`boundary_warp.{requested, applied, status, …}`, `auto_crop.{requested, rect, invalid_px}`, `output`, `uncovered_px`) is returned unchanged as `result.edges` of both the `pano_preview` and `pano_stitch` jobs, or `null` from a binary that predates it. The two options are part of the stitched panorama's file name identity, so a warped or cropped result never reuses an earlier unwarped file; the unwarped, uncropped default keeps the name it had. With `autoCrop` on and a rectangle that is smaller than the image, the job writes the panorama's sidecar beside it (`<name>.xmp`, `src/api/src/pano/pano-crop-sidecar.ts`) holding the standard crop fields, before the PNG takes its name so the indexer never sees the panorama without its crop; a sidecar that is already there is left alone, since it may carry edits. The PNG is the whole canvas either way, but a PNG that carries a crop also gets a `tEXt` chunk (`Maple Auto Crop`: `x,y,width,height`) before `IEND`: the library identifies a file by its bytes, so without it the cropped and uncropped stitches of the same frames would be one asset and the crop would never reach the one the job returns. Server thumbnails and previews of a bitmap original read the crop from its sidecar (`src/api/src/xmp/sidecar-crop.ts`, applied in `thumbs/render.ts`), so a cropped panorama's derivatives show the crop; a straightened crop (`CropAngle` other than 0) is not applied there. A binary whose `--help` lacks the flags reports `edges_supported: false`, and a request that asks for either option from it is refused with 409 `pano_edges_unsupported` instead of silently stitching without it.

`src/api/src/routes/pano.ts`:

| Route                            | Behaviour                                                                                                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/pano/stitch`          | Creates the job and cancels any active preview. 409 `pano_not_provisioned` when disabled or no binary; 409 `pano_cli_outdated` when a pre-classical binary lacks the ML model paths; 409 `pano_job_running` when one is queued or running. |
| `POST /api/pano/preview`         | Creates a `pano_preview` job, cancelling any preview it supersedes. The same matcher 409s as the stitch; 409 `pano_preview_unsupported` for an older binary, 409 `pano_job_running` while a stitch is queued or running.                   |
| `GET /api/pano/jobs/:id/preview` | The finished preview PNG (~2048 px long edge, display sRGB).                                                                                                                                                                               |
| `GET /api/pano/jobs/:id`         | Job status.                                                                                                                                                                                                                                |
| `DELETE /api/pano/jobs/:id`      | Request cancel.                                                                                                                                                                                                                            |
| `GET /api/pano/config`           | Effective config plus probes of whether the configured binary supports `--strategy`, `--features-engine` and the preview flags (`strategy_supported`, `features_engine_supported`, `preview_supported`).                                   |
| `PUT /api/pano/config`           | Upsert settings and re-probe.                                                                                                                                                                                                              |

The single-concurrency rule checks both `queued` and `running`, not just running: close-together requests could otherwise enqueue several jobs that workers later execute concurrently, and a pano run holds the whole decode memory budget and every core for minutes, so concurrent runs would take the box out. The rule lives in the job store's insert statement (`db/repos/jobs.sql.ts`, `NO_ACTIVE_PANO_STITCH`), not only in the route's read before it, so two requests that race past that read still create one job; the loser rejoins the winner when it asks for the same stitch and gets 409 `pano_job_running` otherwise (`src/api/src/pano/pano-admission.ts`). A preview is fenced the same way, and a new stitch cancels any queued or running preview so it does not hold the single-worker runner. The CLI process is always stopped before its job ends — on cancel, on a lost job lease, or on an error — with SIGTERM, then SIGKILL after ten seconds, and the decode memory budget it held is released only once it has exited (`pano-cli-process.ts`). The hourly preview sweep never removes the preview whose alignment the sweeping job is about to read.

**Memory and disk admission (#5835).** A stitch waits its turn and is then held to the server's own limits, rather than started and left to the kernel. `runPanoCli` takes the whole decode memory budget, a percent of the container's cgroup limit (`ffi/container-memory.ts`; [api](api.md) § Native decoding), so the job waits ("Waiting for the server…" in the Apple merge sheet) until every in-flight decode has finished, and no decode starts beside it. When that budget is capped and the binary lists `--memory-limit-bytes` in its help (probed at the route with the other flags, carried in the job as `memoryLimitSupported`), the budget's bytes go to the CLI as that flag. `maple-pano` then estimates its own peak with the model under [Memory](#memory): from the frames' headers before anything is decoded, and from the solved canvas width before anything is composited. A stitch over the limit stops there. One whose decoded frames do not fit the temp volume stops at the frame store's free-space check, as it always did. Either way the CLI writes `{"refused": {"reason": "memory" | "scratch_space", "needed_bytes", "available_bytes"}}` to its `--report` and exits non-zero, and `pano/pano-refusal.ts` turns that block into the job's error: one sentence with both figures (what is needed rounded up, what there is rounded down, in tenths of a GB) and what to do about it, which for memory is to merge fewer photos or raise "Decode memory budget" in Settings → Workers. The web merge dialog and the Apple merge sheet show a job's error as it is, so that sentence is what the user reads. Any other failure keeps the general message, with the details in the server log. A preview is checked the same way before it decodes. A budget of 0 (no cap) passes no limit, and a binary from before the flag stitches unchecked, as before. The server does not shrink the output to make it fit; only the device offers a smaller size.

`src/api/src/pano/pano-config.repo.ts` stores the settings as one document in `app_settings` — `maple_cli_path`, `enabled`, `matcher`, `models_dir`, `ort_dylib_path`. The Docker image builds `maple-cli` with `--features pano,pano-classical` and ships it at `/app/native/maple-cli`, named by `MAPLE_PANO_CLI` (#5493). With no saved path, the config uses that bundled binary (source `bundled`), and `enabled` defaults to on, so a stock image stitches with no setup; a path saved in Settings > Pano still wins, and an operator can turn pano off. Outside Docker there is no bundled binary, so `enabled` defaults to off until a path is saved. The matcher defaults to `classical` (#4555), so a server stitches with nothing but that binary, and nothing is downloaded. `ml` (ALIKED + LightGlue) is an opt-in setting that needs both model paths. When either path is empty in settings, the legacy `MAPLE_PANO_MODELS` / `ORT_DYLIB_PATH` environment variable fills it, so setups from before #4555 keep working. That fallback is deprecated: the server logs a notice once and the settings page labels the value. Path inputs are validated absolute and rejected if they start with `-`, so a configured value cannot smuggle a flag into the spawned command line. The binary, the ONNX Runtime library and the models directory must also resolve (through symlinks) outside every library and mirror root, since the server runs or loads them (`pano-config-paths.ts`).

`pano-cli-probe.ts` reads `maple-cli pano stitch --help`, cached by binary path and modification time, to learn whether the binary accepts `--strategy` and `--features-engine`. `pano-engine.ts` then decides how the stitch runs. With a current binary, classical runs as `--features-engine classical`. ML runs as `--features-engine ml` with `--models-dir` when both paths are set; otherwise the stitch runs classical instead (#5487), and the job's result records `matcher: 'classical'` with a `matcherNote` saying why, which the merge dialog shows under the preview and the finished panorama. A binary from before #4523 has neither the flag nor the classical matcher, so it is ML-only: it runs ML without the flag when both paths are set, and otherwise gets 409 `pano_cli_outdated`, whose message tells the user in plain language that the server's panorama tool needs updating. The settings page shows the operator the rebuild command.

The web surfaces are `PanoService` (`src/web/projects/maple-common/src/lib/api/pano.service.ts`), the merge dialog (`maple-common/src/lib/pano/pano-dialog.component.ts`, whose `PanoPreviewStore` previews the selection as soon as the options open and re-previews, debounced, on every option change, and whose "Create panorama" passes the last finished preview as `alignmentFrom`; and the `mui-panorama-merge-modal` component), and the owner-gated settings page at `/settings/pano` (`src/web/projects/maple/src/app/settings/pano/`). When the config reports `edges_supported`, both web surfaces show an Edges group (`mui-panorama-edges`: a Boundary Warp slider and an Auto Crop toggle, #5576) as the last item of the options list, while the preview stays pinned above the scrolling options (#5609); the Apple merge sheet pins the preview the same way and lists Edges last. While the full stitch runs (#5639), its stage text and progress bar render inside that pinned preview, under the image, the preview's own status text is hidden (and, on the Web dialog, the options are locked); on both surfaces the preview image is capped by height (Web: the smaller of 240 px and 26% of the window, so it stays under 35%; Apple: 35% of the sheet's height, 220 pt until the sheet has been measured), and a cropped preview keeps the same cap. A server without preview support keeps the standalone progress screen. In the dialog the preview re-runs when a Boundary Warp drag ends (the slider's `commit`, not every step) and immediately when Auto Crop changes; at the defaults (0% and off) nothing new is sent. The preview image is always the whole canvas; while Auto Crop is on and the report carries a rectangle, the dialog frames the image to that rectangle (`pano/pano-preview-crop.ts`), and turning Auto Crop off shows the whole canvas at once. The reason line under the slider comes from the newest report's `edges.boundary_warp.status` (`panorama-edges/pano-edges-reason.ts`), is replaced only by a newer report, never shows at 0%, and an unknown status shows no reason; without a preview it appears in the dialog's done state instead. The stitch request references assets by absolute server-side path where possible — the server resolves each to an asset row, indexing on demand — and by asset id for cloud-hosted assets with no local path.

The merge dialog cancels a stitch it stops watching (#5517, #5641): "Cancel job", the host hiding the dialog, and the dialog being destroyed each send `DELETE /api/pano/jobs/:id` while the job is queued or running, using the id from the create response (so it works before the first status poll, and a create response that lands after the dialog went away is cancelled on arrival); a job that already finished, failed or was cancelled gets no request, and neither does one whose status poll failed.

## Fixtures, harness, and gates

Fixture sets live at `test-fixtures/raws/pano_<NN>/` (gitignored, ≥ 2 `.dng` frames each) with references at `test-fixtures/references/<set>/<set>.png`. The tracked ratchet is `test-fixtures/pano-budgets.json`.

```bash
# Full harness (skip-passes without fixtures)
src/scripts/test_pano_pipeline.sh
FILTER=pano_01 src/scripts/test_pano_pipeline.sh

# One set, by hand
cd src/raw-pipeline
cargo build --release --bin maple-cli --features pano
MAPLE_PANO_MODELS=~/.cache/maple-pano/models \
ORT_DYLIB_PATH=/path/to/libonnxruntime.dylib \
  ./target/release/maple-cli pano stitch <frames…> \
    --out pano.png --display pano-srgb.png --report pano.json \
    --strategy auto --retention keep --local-align mesh
```

`test_pano_pipeline.sh` runs two things unconditionally, fixtures or not: it validates that `pano-budgets.json` parses and has the expected shape, and it runs `pano_metrics.py --self-test` (an identical pair scores near zero, a perturbed pair clearly non-zero, and a wrap-shift is recovered). With fixtures present it discovers the sets, writes an effective manifest, invokes `maple-cli pano stitch --manifest … --out-dir … --features-engine <engine>`, and gates each set. It builds `maple-cli` with `--features pano,pano-classical` itself if no binary is present, or honours `MAPLE_CLI`.

The harness gates one matcher per run (#5896), chosen by `PANO_ENGINE`: `ml` gates each set's `stitch` budgets and needs `MAPLE_PANO_MODELS` (without it the candidate gates skip), `classical` gates its `stitch_classical` budgets and needs no models. The default is `ml` when `MAPLE_PANO_MODELS` is set and `classical` otherwise, so a machine without the models still gates the matcher Apple, Windows and Self Hosted use by default. A `MAPLE_CLI` built without the chosen matcher skips the candidate gates with a notice.

The `stitch_classical` budgets were first recorded from one run per set on `main` (2026-11-12, Mac17,6), ceilings at the observed value plus 6 to 7 %, the coverage floor 0.9 % under it as for the ML case, and the signed, near-zero seam steps and pano_02's tilt at the observed value plus 0.001 because a percent margin on a value near zero is meaningless. Budgets are a one-way ratchet — ceilings only go down and the coverage floor only goes up, in the same commit that delivers the improvement.

Crate-level gates:

```bash
cd src/raw-pipeline
cargo test -p maple-pano                    # geometry unit tests (no ML modules, no testkit gates)
cargo test -p maple-pano --features ml      # + the ALIKED/LightGlue stitch pipeline (skip-passes without models)

```

The `testkit` feature generates synthetic correspondences with exactly known camera parameters, which is what makes the two-view, graph, BA, refine, motion, local-alignment, and composite gate suites real geometry rather than regression snapshots. `tests/ml_smoke.rs` (`--features ml`) runs ALIKED and LightGlue on a synthetic overlapping pair rendered by the crate's own ground-truth renderer and reprojects every match through the known rotations; it skip-passes with an explicit message when models or the ORT dylib are absent, and fails loudly on anything else — digest mismatch, interface drift, geometric garbage.

CI (`.github/workflows/raw-pipeline.yml`) runs a `--features pano` compile gate on `maple-cli` and the `pano-pipeline` job, which executes the harness. Without the gitignored corpus the candidate gates are a no-op and only the metrics self-test runs, so CI stays green without fixtures.

Two diagnostic binaries ship with the crate: `pano-ingest-probe` decodes real frames through `decode_for_pano` and prints per-channel statistics plus the EXIF/gimbal priors table, and `pano-gt-render` renders synthetic frame sets from exactly known cameras.

## Geometric conventions

These are binding across the crate (`src/raw-pipeline/maple-pano/src/lib.rs`), and worth knowing before touching any geometry module.

- **World frame:** right-handed, +X east, +Y down (nadir), +Z forward; "up" is −Y. Cameras share the world origin — pure rotation, no translation.
- **Camera frame:** +X right, +Y down, +Z along the optical axis.
- **Rotation:** stored as a Rodrigues axis-angle vector of the _camera-to-world_ rotation. Positive yaw turns the view east; positive pitch tilts it up.
- **Pixels:** continuous coordinates with the origin at the top-left corner; texel `(ix, iy)` covers `[ix, ix+1) × [iy, iy+1)` with its centre at `(ix + 0.5, iy + 0.5)`. The principal point is fixed at the image centre.
- **Equirect:** `u = (λ/2π + 0.5)·W`, `v = (0.5 − φ/π)·H`; row 0 is the zenith, horizontal wrap, vertical clamp.
- **Distortion:** radial polynomial `r_d = r·(1 + k1·r² + k2·r⁴)`, inverted by Newton iteration. With `k2 < 0` the polynomial peaks at a finite radius and then falls again, so a ray far outside a frame would project back inside it. The forward projection refuses rays past that fold radius (`distortion::fold_radius_sq`, checked per pixel by `distortion::before_fold`), the same domain the Newton inverse already enforces; bundle adjustment keeps to it too (#5501).
- **Light:** everything is scene-linear. PNG inputs are normalized without a transfer decode; outputs are 16-bit.

Determinism is a property the crate maintains deliberately: the PRNG is pinned in-tree (SplitMix64), blending is sequential row-major per plane, the exposure-field solver iterates ordered maps, and warp rows are rayon-parallel over pure per-pixel work. Identical inputs produce identical bytes on a given platform and toolchain.
